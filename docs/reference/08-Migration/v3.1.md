# Migrating to Arranger 3.1

This release represents a dramatic evolution in Arranger's internal architecture. It also introduces "multicatalogue" support, support for OpenSearch deployments, improvements to the network search federation, preliminary implementation of an MCP server (work in progress), and significant infrastructure improvements alongside several breaking changes.

This guide covers what you need to change when upgrading from 3.0.x. The companion [**Helm chart 0.4.0**](https://github.com/overture-stack/helm-charts/pkgs/container/helm-charts%2Farranger/956115858?tag=0.4.0) reflects the same breaking changes for Kubernetes deployments, and you may use it as additional reference for any values that changed.

<a id="arranger-server-package"></a>

### The `@overture-stack/arranger-server` package is replaced by `@overture-stack/arranger-graphql-router`

**What changed.** 3.0.x published the server as `@overture-stack/arranger-server`, whose default export built an Express router from environment variables and configuration files. 3.1 publishes the router as `@overture-stack/arranger-graphql-router`, which reads no environment variable and no file: it builds a router for one catalogue from the options it is given. The search server is the application that reads the environment and the configuration files, and it ships as an image (see [Docker image renamed](#docker-image-rename)), not as a package to import.

What each 3.0.x export became:

| `@overture-stack/arranger-server` 3.0.x | `@overture-stack/arranger-graphql-router` 3.1 |
| --------------------------------------- | --------------------------------------------- |
| Default export, `arrangerServer(options)` | Default export, `arrangerRouter(options)`; see the options below |
| `App(rootPath)`, which built an Express app from the environment and listened on `PORT` | Nothing: mount the router in an Express app of your own |
| `getGraphQLRoutes`, `createSchemasFromConfigs` | The same names. They now take a `configs` object and the index mapping as `mappingFromIndex`, which `getIndexMapping` fetches, in place of `configsSource`, and require `getServerSideFilter` |
| `buildSearchClient({ node, user, password, client })` | `buildSearchClient({ client, node, password, username })`: `user` is now `username` |
| Anything else, reached by importing a path inside the package, such as `dataStream`, `getAllData` or `getDefaultServerSideFilter` | Only the package's declared entry points can be imported. `dataStream` and `InvalidExportRequestError` come from `@overture-stack/arranger-graphql-router/download`; `getAllData` from `@overture-stack/arranger-graphql-router/utils`, or as `utils.getAllData` from the package root; `includeEverything`, and `getDefaultServerSideFilter`, now its deprecated alias, from the package root |

The package root also exports `AccessControlError` and `ACCESS_CONTROL_FAILURE_MESSAGE`, `getIndexMapping`, `catalogueErrorCodes` and `classifyCatalogueFailureReason`, `wrapElasticSearchClient` and `wrapOpenSearchClient`, `resolveCatalogueFields`, `logSeparator`, and `utils`, which holds `ajax`, `addContext`, `getAllData`, `noops` and `runGraphQLQuery`. Configuration and callback types, such as `ConfigsObject` and `GetServerSideFilterFn`, come from `@overture-stack/arranger-types/configs`.

What each 3.0.x option became:

| `arrangerServer` option, 3.0.x | `arrangerRouter`, 3.1 |
| ------------------------------ | --------------------- |
| `configsSource`, a path for the package to read configuration files from, by default `CONFIG_PATH` | `configs`, the configuration as an object. `configsSource` loads nothing: passed with no `configs`, it makes `arrangerRouter` reject, naming `configs`; passed beside `configs`, it is ignored, with a deprecation warning |
| `esHost`, `esUser`, `esPass` | `configs.esHost`, `configs.esUser`, `configs.esPass` |
| `searchClient`, the engine type | `configs.searchEngine` |
| `setsIndex` | `configs.sets.index` |
| `enableAdmin` | `configs.enableAdmin` |
| `enableNetworkAggregation` | None: network search applies when `configs.network` is present, in the form [Federated search](../../federated-search.md) describes, which differs from 3.0.x's list |
| `enableLogs`, which added request logging | None: the router logs no requests, so add logging of your own where wanted |
| `pingPath`, which set the path of the router's liveness route | None: the router serves no liveness route, so serve one of your own |
| `esClient` | `esClient`, a `SearchClient`, as `buildSearchClient` returns; wrap a client of your own with `wrapElasticSearchClient` or `wrapOpenSearchClient` |
| `getServerSideFilter` | `getServerSideFilter`, under a new contract; see [`getServerSideFilter` must return a filter for every request](#server-side-filter-contract) |
| `graphqlOptions` | `graphqlOptions` |
| | `catalogueId`, new: the catalogue's name in the router's log output |

Every default 3.0.x took from the environment, such as `ES_HOST`, `ES_INDEX`, `DOCUMENT_TYPE` or `CONFIG_PATH`, is gone from the package. `configs` must carry `documentType` and `esIndex`, the index's name, which 3.0.x's configuration called `index`, and `esUser` and `esPass` unless the router is given an `esClient`.

The router serves `/graphql`, `/download` and a new `GET /introspection`. It keeps its per-request state in `res.locals` (see [Per-request state moves from `req.context` to `res.locals`](#per-request-state-res-locals)). In 3.0.x, a router whose mapping could not be read, or whose schema failed to build, still resolved, and mounted a handler that answered every request with `500`. `arrangerRouter` now rejects instead, with `Failed to initialize Arranger server` and the reason as its `cause`. `classifyCatalogueFailureReason` sorts that reason into the codes [Catalogues that fail to load](#partial-catalogue-availability) lists.

**Who is affected.** Node applications that depend on `@overture-stack/arranger-server`, import its default export or `App`, or import paths inside it. Deployments that only run the search server image are not affected.

**How to tell.** Look for `@overture-stack/arranger-server` in your `package.json` and in your imports.

**What to do.**

1. Replace the dependency on `@overture-stack/arranger-server` with `@overture-stack/arranger-graphql-router`, and add `@overture-stack/arranger-types` where you import its types.
2. Change the imports by the export table above, the default export included.
3. Read the environment and the configuration files in your own code, and pass the result to `arrangerRouter` as `configs`, renaming `index` to `esIndex`, and moving the options listed in the option table into `configs`.
4. Handle `arrangerRouter`'s rejection, which now reports a catalogue it cannot build.
5. Mount your own Express app around the router, with the request logging and liveness route it needs.
6. Then work through the sections on what the router does differently: [the `getServerSideFilter` contract](#server-side-filter-contract), [the server-side filter on every read path](#server-side-filter-every-read-path), [download requests](#download-requests) and [per-request state](#per-request-state-res-locals).

<a id="download-row-limit"></a>

### Exports apply a row limit only where one is set, and mark an export it cuts short

An export, whether through `/download`, `getAllData` or `dataStream`, returns every row matching its filter unless a row limit is set:

| Setting | Rows exported |
| ------- | ------------- |
| No limit set: neither `DOWNLOAD_MAX_ROWS` nor the catalogue's `downloads.maxRows` | Every matching row |
| `DOWNLOAD_MAX_ROWS`, or a catalogue's own `downloads.maxRows`, set to a positive number | At most that many |
| Either set to `0` | Every matching row: `0` cancels the limit |
| `ALLOW_CUSTOM_DOWNLOAD_MAX_ROWS` on (`downloads.allowCustomMaxRows`), and the request names a positive `maxRows` | At most the request's `maxRows`, in place of the configured limit. A request's `0` asks for the configured limit |

An export cut short by the limit is now marked, and the exported file is unchanged:

| Where | Marked by |
| ----- | --------- |
| `/download` | The response headers `Arranger-Export-Truncated: true` and `Arranger-Export-Matching-Total`, the number of documents matching the filter, both listed in `Access-Control-Expose-Headers` so a browser page can read them. An export not cut by the limit carries neither |
| `getAllData` | Each chunk carries `matchingTotal`, the number of documents matching the filter, and `truncated`, beside `hits` and `total`, which is capped at the limit |
| `dataStream` | It also returns `exportTotals()`, giving `{ matchingTotal, truncated }` once the first row is formatted, and `undefined` before then or for an export that matched nothing |

**Who is affected.** Only deployments that set a limit under the 3.1 names, `DOWNLOAD_MAX_ROWS` or a catalogue's `downloads.maxRows`, which 3.1 applies. Everything else exports as 3.0.x did:

- **3.0.x never applied its configured row limit.** It read `MAX_DOWNLOAD_ROWS` but looked for the value where it was not stored, so an export returned every matching row.
- **An unset limit still exports every row**, and so does `MAX_DOWNLOAD_ROWS`, which 3.1 no longer reads (see [Variables no longer read](#environment-variables-no-longer-read)). An environment copied from 3.0.x's `.env.schema`, which listed `MAX_DOWNLOAD_ROWS=100`, keeps exporting every row.
- **A request's own `maxRows` still applies where custom row limits are allowed**, as it did in 3.0.x.

**How to tell.** Check whether the environment sets `DOWNLOAD_MAX_ROWS`, and whether a catalogue's configuration sets `downloads.maxRows`. A server started with `MAX_DOWNLOAD_ROWS` set warns that it has no effect. An export the limit cut short carries `Arranger-Export-Truncated: true`.

**What to do.** Remove `MAX_DOWNLOAD_ROWS`. Where exports should keep returning every row, leave `DOWNLOAD_MAX_ROWS` unset or set it to `0`. Where a cap is meant, set `DOWNLOAD_MAX_ROWS` to it. A client that saves exports can read `Arranger-Export-Truncated` and `Arranger-Export-Matching-Total` to tell its users when a file holds fewer rows than the filter matched.

<a id="environment-variable-renames"></a>

### Environment variables renamed

Seven environment variables were renamed. Each 3.0 name keeps working in 3.1 as a deprecated alias. Update your `.env` files, container environment configurations and Helm values to the new names.

| Old name | New name | Purpose |
| --- | --- | --- |
| `ALLOW_CUSTOM_MAX_DOWNLOAD_ROWS` | `ALLOW_CUSTOM_DOWNLOAD_MAX_ROWS` | Whether a download request may set its own row limit (default: `false`) |
| `CONFIG_PATH` | `CONFIGS_PATH` | Directory holding the catalogue configuration files (default: `./configs`); see [The 3.0 configuration location](#configs-directory) |
| `DEBUG` | `ENABLE_DEBUG` | Verbose debug logging (default: `false`) |
| `ES_ARRANGER_SET_INDEX` | `ES_ARRANGER_SETS_INDEX` | Index holding saved sets (default: `arranger-sets`) |
| `ES_ARRANGER_SET_TYPE` | `ES_ARRANGER_SETS_TYPE` | Saved sets' type (default: `arranger-sets`); read, but no longer used |
| `PORT` | `SERVER_PORT` | HTTP port the server listens on (default: `5050`) |
| `SEARCH_CLIENT_TYPE` | `SEARCH_ENGINE` | Search engine type: `opensearch` or `elasticsearch`, detected when unset |

A 3.0 name set alone sets its 3.1 variable, and the server prints one warning for it at startup, naming the new name:

```
[ARRANGER_ENV_RENAMED] DeprecationWarning: PORT is deprecated: set SERVER_PORT instead. See ...
```

How the old names behave:

- **An old name's value means what 3.0 read it as**, so the alias changes nothing beyond what the upgrade already changes. A flag is on only for `true`, in any case, and a number of `0`, or text that is no number, takes the default.
- **Moving to the new name can change a value's meaning**, since the new name reads `1` as `true` and keeps a `0`. So where an old name holds such a value, the warning says to remove the old name rather than copy its value across.
- **A blank value counts as unset.**
- **Where both names are set, the new name wins**, and the warning says the old one was ignored. Where both hold the same value, as where `SERVER_PORT` is set from a `PORT` injected by the platform, nothing is printed.
- **`DEBUG` counts as the old name only when it holds `true`.** Other tools read `DEBUG` for settings of their own, such as `express:*`, so any other value is left to them, with no warning.

These are Node deprecation warnings, so `--no-deprecation` hides them, and under `--throw-deprecation` a server still setting an old name stops at startup.

<a id="environment-variables-no-longer-read"></a>

These 3.0.x variables are no longer read. Setting one prints a warning at startup, code `ARRANGER_ENV_UNREAD`, saying it has no effect:

| Variable | What to do |
| --- | --- |
| `ES_LOG`, `MAX_LIVE_VERSIONS` | Remove them: nothing in 3.0.x read their values either |
| `MAX_DOWNLOAD_ROWS` | Remove it: 3.0.x read it but never applied it, so no 3.0.x export was limited by it. To limit exports, set `DOWNLOAD_MAX_ROWS`; see [the row limit](#download-row-limit) |

`ENABLE_NETWORK_AGGREGATION` and `NETWORK_AGGREGATIONS` are still read, as deprecated: see [Network search configured for 3.0](#network-config-shape).

### Docker image renamed

The search server Docker image was renamed to reflect that it is one of several server applications in the monorepo:

```
ghcr.io/overture-stack/arranger-server  ->  ghcr.io/overture-stack/arranger-search-server
```

<a id="max-results-window"></a>

### `MAX_RESULTS_WINDOW` is now enforced

In 3.0.x, `MAX_RESULTS_WINDOW` did not cap the hits returned by a query. The server served it through the GraphQL `configs` query as `table.maxResultsWindow`, and the components used it to limit how many pages a table offered. In 3.1 the server also caps the number of hits returned per query by it, defaulting to `10000`.

If your deployment returns more than 10,000 documents per query, set `MAX_RESULTS_WINDOW` explicitly in your environment, or override it per catalogue via `table.json`:

```json
{
	"table": {
		"maxResultsWindow": 50000
	}
}
```

Per-catalogue config always wins over the environment variable. Use this with caution, to prevent overloading your search engine.

<a id="boolean-environment-flags"></a>

### Boolean environment flags accept only `true`/`1` and `false`/`0`

Every boolean flag read by the search server from its environment follows one rule. Values are trimmed and read in any case:

| Value | Reads as |
| ----- | -------- |
| `true` or `1` | `true` |
| `false` or `0` | `false` |
| Unset, empty, or whitespace only | The flag's default |
| Anything else, `yes`, `no`, `on` and `off` included | The flag's default, with a startup warning naming the value, under the event `config.boolean_value_ignored` |

The rule covers `ALLOW_CUSTOM_DOWNLOAD_MAX_ROWS`, `DISABLE_DOWNLOADS`, `DISABLE_FILTERS`, `DISABLE_GRAPHQL_INTROSPECTION`, `DISABLE_GRAPHQL_PLAYGROUND`, `ENABLE_ADMIN`, `ENABLE_DEBUG`, `ENABLE_GRAPHQL_BATCHING`, `ENABLE_LOGS` and `ENABLE_SETS`. Each defaults to `false`, except `DISABLE_GRAPHQL_INTROSPECTION`, which defaults to `true` when `NODE_ENV=production`.

**Who is affected.** 3.0.x read a flag as `true` only when its value was exactly the word `true`, in any case. `1`, or `true` with a space around it, read as `false`; both now read as `true`. Of the flags above, `ENABLE_ADMIN` and `ENABLE_LOGS` keep their 3.0 names, so a 3.0.x deployment that set either to `1` or to a padded `true` now has it on. `ENABLE_DEBUG` and `ALLOW_CUSTOM_DOWNLOAD_MAX_ROWS` follow this rule under their new names, while their 3.0 names keep 3.0's reading (see [Environment variables renamed](#environment-variable-renames)). The other flags are new in 3.1.

**How to tell.** Look for `config.boolean_value_ignored` in the server's startup output, and for `ARRANGER_ENV_MEANING_CHANGED`, which the server prints once where `ENABLE_ADMIN` holds a value 3.0.x read as off, since admin exposes each catalogue's index mapping; setting it to `true` keeps admin on without that notice. Look through `.env` files, container environments and Helm values for flags set to `1`, to a padded or blank value, or to a word other than `true` or `false`.

**What to do.** Set each flag to `true` or `false`, or leave it unset for its default. Wherever introspection must stay on under `NODE_ENV=production`, such as on a node serving as a network search remote, set `DISABLE_GRAPHQL_INTROSPECTION=false` explicitly. In a catalogue's `base.json`, keep giving flags JSON booleans: this rule applies to environment variables only.

`stringToBool`, exported from `@overture-stack/arranger-types/tools`, applies the same rule for integrations that read flags of their own, and also accepts the booleans `true` and `false` and the numbers `1` and `0`. `ENABLE_ACCESS_CONTROL` is the exception: see the next section.

<a id="enable-access-control"></a>

### `ENABLE_ACCESS_CONTROL` refuses startup on a value it does not recognize

`ENABLE_ACCESS_CONTROL`, new in 3.1, says whether the search server applies access control. It does not follow the boolean flag rule above, because a mistyped value taking a default could leave access control off unnoticed. Values are trimmed and read in any case:

| Value | Effect | Startup log |
| ----- | ------ | ----------- |
| Unset | No access control, unless a host application passes its own `filters` option, which then applies | `access control source: defaulted (unset)`, or `access control source: configured by host` |
| `false` or `0` | No access control, stated explicitly | `access control source: explicit (set to false)` |
| `true` or `1` | The server refuses to start: this build does not include the Usher adapter that access control needs | `access_control.startup_refused`, saying so |
| Anything else, an empty value included | The server refuses to start, quoting the value | `access_control.startup_refused` |

A host application that passes its own `filters` option alongside `ENABLE_ACCESS_CONTROL=false` is also refused at startup, since the two contradict each other. A refused server exits with status `1`.

**Who is affected.** Any deployment whose environment sets `ENABLE_ACCESS_CONTROL` at all, and in particular one where a template or `.env` line renders it with an empty value. 3.0.x did not read it.

**How to tell.** Look for `ENABLE_ACCESS_CONTROL` in `.env` files, container environments and Helm values, and for `access_control.startup_refused` in the output of a server that exits at startup.

**What to do.** Leave it unset, or set it to `false`, for a deployment with no access control. Remove it entirely rather than render it empty. See [Feature flags](../07-feature-flags.md#access-control) for the full rule.

<a id="numeric-environment-values"></a>

### Numeric environment values keep an explicit `0`

A numeric environment value is read like this:

| Value | Reads as |
| ----- | -------- |
| Unset, empty, or whitespace only | The variable's default |
| Not a finite number | The variable's default, with a startup warning naming the value |
| Any finite number, `0` included | That number |

**Who is affected.** 3.0.x replaced a `0`, and text that is no number, with the variable's default. A renamed variable's 3.0 name still does under 3.1 (see [Environment variables renamed](#environment-variable-renames)), but every 3.1 name, and every name 3.1 kept from 3.0, now keeps an explicit `0`:

| Variable | What `0` does |
| -------- | ------------- |
| `SERVER_PORT` | Binds a free port assigned by the operating system, and the startup line reports that port. 3.0.x's `PORT=0` bound `5050`, and still does under that name |
| `PING_MS` | Kept as `0`. It sets how often the engine probe runs, which only a host application passing its own search client enables. 3.0.x read `PING_MS` but used it nowhere |
| `MAX_RESULTS_WINDOW` | Caps hits at zero, so record queries return no hits. 3.0.x read `0` as `10000`, and its server did not cap hits by the value at all (see [`MAX_RESULTS_WINDOW` is now enforced](#max-results-window)) |
| `DOWNLOAD_MAX_ROWS` | Cancels the export row limit, as leaving it unset does (see [the row limit](#download-row-limit)) |

**How to tell.** Look for numeric variables set to `0` or to whitespace only, and for a startup warning that a value "is not a finite number".

**What to do.** Leave a variable unset for its default, or set the value you mean.

<a id="mapping-extension-log"></a>

### A failure to extend a catalogue's mapping logs a new line

When the GraphQL routes cannot combine a catalogue's `extended` configuration with its index mapping, they now log at error level, beginning `Could not extend the index mapping for catalogue "<name>".`, and say what degrades and what does not. The line `Something happened while extending the ES mappings.` is no longer logged. Through `arrangerRouter`, and so in the search server, the same failure stops the catalogue from loading instead, and it is reported as `failed` (see [Catalogues that fail to load](#partial-catalogue-availability)), so the new line appears only where an integration builds the GraphQL routes itself. A facet failure now logs `Something happened while extending the facet mappings.`, where 3.0.x logged the column line's text for it too, and both the facet and the column line (`... the column mappings.`) are indented by four spaces rather than two.

**Who is affected.** Log matchers and alerts keyed on the old line.

**How to tell.** Search alert rules and log queries for `extending the ES mappings`.

**What to do.** Match `Could not extend the index mapping for catalogue` instead where an integration builds the GraphQL routes itself, and `failed to load` in the search server.

<a id="partial-catalogue-availability"></a>

### A catalogue that fails to load is reported as `failed`, and the server keeps running

At startup, the search server builds each catalogue on its own. A catalogue that cannot be built is marked `failed`, with an error `code` and `message`, while every other catalogue is served as usual. This covers a catalogue whose index is missing or unreachable, whose mapping cannot be read, or whose GraphQL schema fails to build. Such a catalogue is never mounted as available. Its routes answer like this:

| Request | Answer |
| ------- | ------ |
| `GET /ping` (`PING_PATH`) | `200` and `{"message":"Reporting for duty..."}`, whatever state the catalogues are in |
| `GET /ready` (`READY_PATH`) | `200` while at least one catalogue is available, and `503` when every catalogue failed. The body is `{"status": ..., "engineReachable": ...}` |
| `GET /introspection` | `200`, with a server-wide `status` of `healthy`, `degraded` or `unhealthy`, and each catalogue's `status`, plus its `error` when it failed |
| `GET /introspection/{catalogueId}` for a failed catalogue | `200`, with its `catalogueId`, `documentType`, `description` when one is configured, `status: "failed"` and `error` |
| Any other route of a failed catalogue, `/graphql` and `/download` included | `404`, with the same body plus `details`, the path of its introspection endpoint |

A server with one catalogue mounts it without a prefix, so when that catalogue fails, every path other than `/ping`, `/ready` and `/introspection` answers the `404`. A failed catalogue is distinct from an unknown one: `GET /introspection/{name}` for a name matching no catalogue answers `404` with `{"error":"Catalogue \"{name}\" was not found."}`, and its other paths get Express's default `404`, without the `status` body.

`engineReachable` comes from a probe that runs every `PING_MS` only when a host application passes the server a search client of its own, and `/ready` also answers `503` while that probe finds the engine unreachable. The published image passes none, so there `engineReachable` is always `true`, and `/ready` follows catalogue status alone.

The `error.code` says why the catalogue failed:

| `code` | Means |
| ------ | ----- |
| `connection_error` | The search engine could not be reached in time |
| `index_not_found` | The configured index does not exist |
| `mapping_fetch_error` | The engine answered, but the index mapping could not be fetched or read |
| `nesting_prefix_not_found` | The catalogue's `nestingPrefix` matches nothing in the mapping |
| `permission_denied` | The search-engine user was refused, with `401` or `403` |
| `schema_build_error` | The GraphQL schema or endpoint failed to build. The message names the problem, such as two fields colliding on one GraphQL name |
| `unknown_error` | Anything else |

The server logs, for each failed catalogue at error level, `Catalogue "{catalogueId}" failed to load ({code}: {message}); continuing with the remaining catalogues.` A server with several catalogues also logs `- Catalogue mounted at /{catalogueId} (failed)`. Then, unless `ENABLE_DEBUG` is on, it logs one summary line: `Catalogue availability: {status}`, followed by `({catalogueIds} unavailable)` when any failed. The full error, with its cause chain and stack trace, is printed only with `ENABLE_DEBUG`.

**A failed catalogue does not recover without a restart.** Catalogue status is decided once, while the server starts. A catalogue that failed keeps answering `404`, even after its index is created or its permissions are fixed, until the server restarts. `/ping` keeps answering `200` all the while, so a liveness probe on it never restarts the process.

In the image, a check before startup waits for the engine at `ES_HOST` and exits when it never answers, so an engine that is down at startup still stops the container, as it did in 3.0.x.

3.0.x answered differently. When its index or mapping could not be read, or its schema failed to build, the server kept running, and every route, `/ping` included, answered `500` with `{"detail":"Please notify the systems admin - ","message":"...","type":"system/unspecified-internal-error"}`. 3.0.x had no `/ready` and no `/introspection`.

**Who is affected.** Operators whose health checks or alerts rely on 3.0.x's behaviour:

- a liveness probe on `/ping`. 3.0.x answered it with `500` when the catalogue's index was missing, so the probe failed and restarted the process; it now answers `200`, so the probe passes and nothing restarts;
- alerts that count `500` responses from catalogue routes, since a failed catalogue now answers `404` with a JSON body;
- a readiness probe on `/ping` or on a GraphQL query, since `/ready` is the endpoint that reflects catalogue state;
- monitoring that reads a successful startup as every catalogue having loaded.

**How to tell.** `GET /introspection` reports a `status` other than `healthy`, and lists each failed catalogue with its `error.code`. The server log carries `failed to load` for each one. `/ready` answers `503` once every catalogue has failed. A `404` from a catalogue route whose body holds `"status":"failed"` comes from a failed catalogue, not a mistyped path.

**What to do.** Keep the liveness probe on `/ping`, and point the readiness probe at `/ready`. Alert on `GET /introspection` reporting `degraded` or `unhealthy`, or on the `failed to load` log line, since neither a degraded server nor a `/ready` that answers `503` makes a liveness probe restart anything. Once the cause is fixed, whether that means creating the index, granting the permission or correcting the configuration, restart the server so the catalogue loads.

<a id="download-requests"></a>

### `/download` exports one file per request, and validates the request first

`POST /download` takes `params` as one form field holding JSON, and checks it against these rules before any search runs:

| Field | Rule |
| ----- | ---- |
| `files` | An array holding exactly one file object. A client wanting several files sends one request for each |
| `columns` | A non-empty array of column objects |
| `chunkSize` | A positive integer, sent as a JSON number |
| `maxRows` | A non-negative integer, sent as a JSON number. It applies only where the catalogue allows custom row limits, and `0` asks for the configured limit |
| `fileType` | `tsv` or `json`. Absent, `null` or empty names none, and `tsv` applies when nothing names one |
| `sort` | An array of entries, each with a non-empty `fieldName` and an `order` of `asc` or `desc`, in any case |
| `fileName` | A well-formed string |
| `uniqueBy`, `valueWhenEmpty` | Strings |
| `sqon` | A filter that can be compiled into a query |

The file's fields are read by name, and anything else it carries is ignored. A top-level `chunkSize`, `fileName` or `fileType` follows the same rule, and applies where the file names none. With no name given, the file is named `file.tsv` or `file.json`.

Every failure from reading `params` onward is answered as plain text:

| Outcome | Status | Response text | Logged on the server as |
| ------- | ------ | ------------- | ----------------------- |
| The request breaks a rule | `400` | The rule it broke, naming the field at fault and never a value carried by the request. For a filter that cannot be compiled, the SQON rule it broke, where the compiler names one | `download.invalid_request` |
| Access control cannot be evaluated | `500` | "The server could not apply its access control because of a problem in its configuration, not in this request." | `download.failed`, and `access_control.evaluation_failed` |
| Any other server fault | `500` | "The download failed because of a problem on the server, not in the request." | `download.failed` |
| A failure after output has started | The response is aborted | None | `download.stream_failed` |

Response headers wait for the first formatted row, so a failure before any output answers with its status rather than with a partial file.

**Who is affected.** Clients that ask for several files in one request, which 3.0.x answered with one `.tar.gz` archive; that send `chunkSize` or `maxRows` as a string, or `params` as anything other than one form field holding JSON; or that read the body of a failed download.

Integrations serving their own export route are affected too. `dataStream` validates `params` by the same rules, so it can be given the client's object whole, and `getAllData` rejects with `InvalidExportRequestError` before any search when its `chunkSize` or `sort` breaks them, or its `sqon` cannot be compiled. On a context the router did not build, both need `getServerSideFilter` passed explicitly, either the function the deployment's router is configured with or `includeEverything` where the deployment applies no access control; passing nothing is refused before any output. See [Export routes](https://github.com/overture-stack/arranger/blob/main/modules/graphql-router/README.md#export-routes) in the router's README.

**How to tell.** Check the code that posts to `/download` for the number of files it sends and the types of its fields, and any code that reads a failed download's response.

**What to do.** Send one file per request, with numbers as JSON numbers. Treat `400` as a request to fix, and `500` as a problem on the server. An integration with its own export route can answer the same way: `InvalidExportRequestError`, exported from `@overture-stack/arranger-graphql-router/download`, is a `400` answered with its message, while `AccessControlError` and any other error are a `500` answered with fixed text, such as the exported `ACCESS_CONTROL_FAILURE_MESSAGE`.

<a id="export-shard-failures"></a>

### A failed search or shard fails an export

An export, through `/download`, `getAllData` or `dataStream`, pages through the search engine with `search_after` on the export's sort plus an `_id` tiebreaker, and takes its total from the first page. A failed search, or a page reporting a failed shard, now fails the whole export:

| When it fails | `/download` answers | Logged on the server as |
| ------------- | ------------------- | ----------------------- |
| Before any output | `500`, "The download failed because of a problem on the server, not in the request." | `download.failed` |
| After output has started | The response is aborted | `download.stream_failed` |

For `getAllData` and `dataStream`, the stream errors instead. The chunks keep `hits` and `total`, beside the fields [the row limit](#download-row-limit) adds, and the TSV and JSON output is unchanged.

**Who is affected.** Deployments whose search engine sometimes answers with failed shards. 3.0.x exported such a page with whatever the shards that answered returned, so the file could be missing rows without any sign of it.

**How to tell.** Look for `download.failed` or `download.stream_failed` in the server log. The logged error reads "A page of the export failed on some shards, so the export would be incomplete.", with the engine's shard report attached as its cause, or "The search engine failed to return a page of the export.", with the engine's error as its cause.

**What to do.** Treat it as a search-engine problem: check the cluster's health, then retry the export.

<a id="export-nested-filters"></a>

### Exports filter nested fields as search does

An export takes its list of nested fields from the catalogue's index mapping, as hits, aggregations and saved sets already did, and that list decides whether a clause compiles to a `nested` query. So a filter on a nested field returns the same documents in an export as in search.

**Who is affected.** 3.0.x exports took nested fields from the catalogue's extended field configuration instead. The two agreed wherever the mapping extended cleanly at startup. Where it failed to extend, 3.0.x fell back to the raw `extended` configuration, in which a field counts as nested only where it declares `type: "nested"`, so an export that filtered on a nested field could return a different number of rows than search. In 3.1, the search server reports such a catalogue as failed instead (see [Mapping-extension log line](#mapping-extension-log)).

**How to tell.** Compare an export's row count with the hit total for the same filter on a nested field. Look in 3.0.x logs for `Something happened while extending the ES mappings.`, the line that marked a mapping that failed to extend.

**What to do.** Nothing for the search server. An integration calling `getAllData` on a context the router did not build must give it configs that carry `nested_fieldNames`, as the router builds them: `getAllData` now refuses to build a query without that list, with an error naming the catalogue.

<a id="mock-endpoint-removed"></a>

### `/mock/graphql` and the download `mock` option are removed

The `/mock/graphql` endpoint no longer exists, and `/download` ignores a `mock` field, as it ignores any field it does not read. Nothing replaces either. In code, `createSchemasFromConfigs()` no longer returns a `mockSchema`, and `getAllData` and `dataStream` ignore a `mock` argument.

**Who is affected.** Only clients, gateways or integration code that called `/mock/graphql`, sent `mock` to `/download`, or read `mockSchema`. A deployment that never used them sees no change.

**How to tell.** Search clients, gateway routes and integration code for `mock/graphql`, `mockSchema`, and a `mock` field in download params.

**What to do.** Remove those calls and routes.

<a id="server-side-filter-contract"></a>

### `getServerSideFilter` must return a filter for every request

`getServerSideFilter` is how an integration built on `@overture-stack/arranger-graphql-router` applies access control. Its contract is now total: it must be a synchronous function that returns a SQON filter for every request it receives, unauthenticated ones included. There is no "no filter" return value. Each intent has its own:

| Intent | Do this |
| ------ | ------- |
| Apply no access control at all | Leave `getServerSideFilter` out of `arrangerRouter`'s options, or pass `includeEverything` itself to state it explicitly |
| Allow this request without restricting it | `return includeEverything(context);` |
| Deny this request | `return SqonBuilder.matchNothing(fieldName).toValue();` |
| Restrict this request | Return a filter selecting what it may see |

`includeEverything` comes from `@overture-stack/arranger-graphql-router`, and `SqonBuilder` from `@overture-stack/sqon`. `matchNothing` returns a builder, so call `.toValue()` on it: the builder itself is not a filter, and is refused. Its `fieldName` has no effect on the result, and any field will do. `includeEverything` takes the request context, so pass it on. `getDefaultServerSideFilter` is now a deprecated alias for `includeEverything`, and a call to `getDefaultServerSideFilter()` with no argument, as earlier examples showed, no longer typechecks.

**What is refused at construction.** `arrangerRouter` rejects a `getServerSideFilter` that is neither left out nor a non-async function, `null` included, naming what it received. `getGraphQLRoutes` and `createSchemasFromConfigs` require one, and throw at build even with `rethrowOnError: false`.

**What is refused per request.** A callback that throws or returns a promise, or a returned filter that:

- is `null`, `undefined`, or anything else that is not a SQON node;
- holds an empty combination (`and`, `or` or `not` with `content: []`) anywhere, alone or beside clauses;
- holds an `all` with an empty value list;
- holds a range (`gt`, `gte`, `lt`, `lte` or `between`) with no bound, where a bound is a finite number, a non-empty string or a valid date;
- holds a `not-in` or `some-not-in` whose value list is missing or `null` (an empty list is accepted, and excludes nothing);
- holds a clause naming no field, such as one keyed by `field` rather than `fieldName`;
- holds an entry that is not a SQON node, such as a hole in a list.

A refused request fails rather than being served. GraphQL clients receive the fixed text "The server could not apply its access control because of a problem in its configuration, not in this request.", exports answer `500` with the same text (see [Download requests](#download-requests)), and network search reports it in a failing node's `errors`. The server logs the full reason under `access_control.evaluation_failed`, naming the problem and where it sits, such as an empty `or` at `content[1]`.

**Who is affected.** Every integration that passes `getServerSideFilter`. Coming from 3.0.x, a callback returning nothing meant no restriction, and 3.0's default filter returned `{ "op": "not", "content": [] }`, an empty combination, which is now refused wherever it appears. A deployment that applies no access control and leaves the callback out needs no change.

**How to tell.** Find every `getServerSideFilter` you pass, and check each of its return paths, the unauthenticated one included, against the list above. At startup, the router logs each catalogue's decision: `access control: filter configured`, `access control: none (explicit)` when the function given is `includeEverything` itself, or `access control: none (defaulted)` when none was given. After upgrading, watch the server log for `access_control.evaluation_failed`.

**What to do.** Return one of the values in the table above from every path. Make an `async` callback synchronous, by resolving whatever it awaits in middleware that runs before the router.

<a id="server-side-filter-every-read-path"></a>

### The server-side filter applies on every read path

The filter `getServerSideFilter` returns applies to every path that reads documents on this server: record queries, aggregations, saved sets and the export route. The GraphQL router applies it where every query is compiled, so a read path cannot be added without it. Network search forwards it to each remote node with the query, and a remote node applies it only if it honours the filter it receives.

**Who is affected.** Integrations that pass `getServerSideFilter` and expect a facet count, a saved set or an export to cover more than the filter admits.

**How to tell.** Compare facet counts, saved-set sizes and export row counts with the hit total for the same request: each is computed within the filter.

**What to do.** Nothing, where the filter states what each request may see. Otherwise, widen the filter to admit what that path must return.

<a id="saved-set-filters"></a>

### Saved-set filters need read access to the sets index

A filter value of the form `set_id:<id>` selects the saved set's records on hits, aggregations and exports, on Elasticsearch and OpenSearch alike. The set is looked up in the catalogue's own sets index: `sets.index` in the router's configs, set by the search server from `ES_ARRANGER_SETS_INDEX` (default `arranger-sets`). The search engine fetches the set's document by id while it runs the query, so Arranger's search-engine role needs `indices:data/read/get` on the sets index. The built-in `read` action group (`indices:data/read*`) covers it.

**Who is affected.** Deployments whose clients filter by saved sets, and whose search-engine role is written by hand rather than granting `read` on the sets index. 3.0.x looked a set up in two ways: hits and exports used this lookup, naming the sets' document type as well, while aggregations searched the sets index themselves, which needs `indices:data/read/search`. Every path now uses the lookup, without a type, so a set filter on facets needs `indices:data/read/get` too.

**How to tell.** Check the role's index permissions on the sets index. Permission to write sets there (`indices:data/write/index`) does not include permission to read them.

**What to do.** Grant `indices:data/read/get`, or the `read` action group, on the sets index to Arranger's search-engine role.

<a id="filters-compile-as-written"></a>

### Filters compile as written

The query compiler now gives several SQON shapes the meaning they state. A saved or bookmarked query holding one of them can return different documents or facet counts after the upgrade, or an error. The table lists what to look for, and the sections after it give the detail.

| Look in a saved query for | It now | Detail |
| ------------------------- | ------ | ------ |
| A group whose `content` is `[]`, anywhere but the root or directly under `and` | Matches every document in its place, so an `or` holding it matches everything and a `not` holding it matches nothing | [Empty combinations](#empty-combinations) |
| A `not-in` or `some-not-in` whose value list mixes ordinary values with `__missing__`, a `*` pattern or a `set_id:` reference | Excludes every value it lists | [Exclusions with special values](#exclusions-with-special-values) |
| A `some-not-in` holding a `set_id:` reference | Excludes the set's records | [Exclusions with special values](#exclusions-with-special-values) |
| A `pivot` on an `and` or a `not` | Holds its conditions on the pivot path to one nested item, in whatever order the children come | [Pivoted groups](#pivoted-groups) |
| A `some-not-in` with `__missing__` on a nested field | Keeps the records where no nested item lacks the field | [Pivoted groups](#pivoted-groups) |
| A `gt`, `gte`, `lt` or `lte` whose `value` is a list of more than one entry | Applies every bound, so the strictest decides | [Range bounds](#range-bounds) |
| A `pivot` naming a field that is not nested in the catalogue | Is refused, as in 3.0.x, with a new message | [Pivots must name a nested field](#pivot-must-name-nested-field) |
| A `not` directly inside a `not` | Applies its own negation, so `not[not[X]]` matches what `X` matches | [Nested negation](#nested-negation) |
| A clause on a field nested inside another nested field, with facets on the outer one | Narrows those facets' counts | [Nested facets](#nested-facets-deeper-clauses) |

Searching stored queries' JSON for an empty `content` list, `pivot`, `some-not-in`, `__missing__`, `set_id:`, `"not"`, and range operators whose `value` is a list narrows the candidates for every row but the last. Exports apply the same rules; see also [Exports filter nested fields as search does](#export-nested-filters).

<a id="empty-combinations"></a>

#### An empty combination means every document, wherever it sits

An empty combination, an `and`, `or` or `not` whose `content` is `[]`, matches every document in its place:

| Where it sits | The filter holding it |
| ------------- | --------------------- |
| At the root, as `and[]` | Means no filter |
| Directly under `and` | Is unchanged |
| Under `or`, as in `or[X, or[]]` | Matches every document |
| Under `not`, as in `not[X, or[]]` | Matches nothing, since `not` keeps only the documents that match none of its children |

Facets read an empty combination the same way, whatever `aggregations_filter_themselves` is set to. A `pivot` naming a nested field has no effect on an empty group.

**What to check.** Look in saved and bookmarked queries for an empty group anywhere but the root or directly under `and`, and remove it, or restore the condition it was meant to hold. Among Arranger's own interfaces, the AdvancedSqonBuilder could leave such a group behind; see [The AdvancedSqonBuilder removes what a deletion empties](#advanced-sqon-builder).

<a id="exclusions-with-special-values"></a>

#### A `not-in` or `some-not-in` with special values excludes every value it lists

`__missing__`, a value containing `*`, and a `set_id:` reference are special values, and each compiles to a clause of its own. When a value list mixes them with ordinary values, those clauses are joined by what the operator means:

| Operator | Matches a document that |
| -------- | ----------------------- |
| `in` | Matches any of the listed values |
| `not-in`, `some-not-in` | Avoids every listed value |

A `some-not-in` given a `set_id:` reference now excludes the set's records, as `not-in` does. On a nested field, each part of such a `not-in` is tested on its own, so different nested items can satisfy different parts.

**What to check.** Queries of these shapes can return different documents. A `some-not-in` holding a `set_id:` reference now returns the records outside the set.

<a id="pivoted-groups"></a>

#### A pivot holds its conditions to one nested item

A `pivot` names a nested field, and requires the conditions under it on that path to hold for the same nested item. That now holds in whatever order a group's children come:

- A pivoted `and` matches a record when one nested item meets all of its conditions on the pivot path.
- A pivoted `not` excludes the records where one nested item meets all of its conditions on the pivot path, while each of its other children is negated on its own.

`some-not-in` with `__missing__` on a nested field keeps the records where no nested item lacks the field, records with no nested items included.

**What to check.** A pivoted group whose first child is not a condition on the pivot path, and a `some-not-in` with `__missing__` on a nested field, can return different records.

<a id="range-bounds"></a>

#### A range given several bounds applies every one

`gt`, `gte`, `lt` and `lte` accept a list of bounds as their `value`, and every bound in the list applies, so the strictest decides: the largest for `gt` and `gte`, the smallest for `lt` and `lte`. An entry that cannot bound a range, such as `null` or an empty string, is left out when the list also holds one that can.

**What to check.** Look for range clauses whose `value` is a list of more than one entry, and confirm that the strictest bound is the one meant. A list mixing a usable bound with `null` or an empty string applies the usable bound alone.

<a id="pivot-must-name-nested-field"></a>

#### A pivot naming no nested field is refused with a new message

A `pivot` must name a field mapped as `nested` in the catalogue being queried. As in 3.0.x, a filter whose pivot names anything else, wherever it sits and empty groups included, is refused. The message is now "A filter's pivot must name a nested field of this catalogue; it requires the filter's conditions to hold for the same nested object.", where 3.0.x's was `Invalid pivot field "{pivot}", not a nested field`. GraphQL clients receive it as an error, and export clients as a `400`.

**What to check.** Update anything that matches 3.0.x's message, and compare every `pivot` in saved queries against the fields mapped as `nested` in the catalogue's index.

<a id="nested-facets-deeper-clauses"></a>

#### Facets on a nested field honour clauses nested deeper inside it

A facet on a nested field now applies a clause on a field nested deeper inside it. For a catalogue whose `donors` are nested, each holding nested `specimens`:

| Filter | A facet on `donors.donor_id` counts |
| ------ | ----------------------------------- |
| `in:donors.specimens.tissue['Solid']` | The donors holding a Solid specimen, where it came back empty |
| `not-in:donors.specimens.tissue['Solid']` | Only the donors holding a specimen outside the list, where the clause was ignored |

A clause on the facet's own level or outside its nested objects, and a facet on the deeper level itself, count as before.

**What to check.** Facet counts change for catalogues with nested fields inside nested fields, wherever a query filters on the inner level and shows facets on the outer one.

<a id="nested-negation"></a>

#### A `not` directly inside a `not` applies its own negation

Every `not` negates its own children, including one that sits directly inside another `not`. So `not[not[X]]` matches the documents `X` matches, and `not[A, not[B]]` matches the documents that do not match `A` and do match `B`.

**What to check.** A saved query holding a `not` directly inside a `not` can return different documents than it did on 3.0.x. Confirm each such query states the negation meant.

<a id="is-array-null"></a>

### A field's `isArray` can be `null`

`isArray` says whether one document can hold more than one value for a field, and now has three states:

| Value | Means |
| ----- | ----- |
| `true` | A configuration declared the field multi-valued |
| `false` | A configuration declared it single-valued |
| `null` | Nothing declared it either way |

`GET /introspection/{catalogueId}` reports `isArray` for every field, always present and `null` when undeclared. In `@overture-stack/arranger-types`, a column configuration's `isArray` (`ColumnConfigs`) is typed `boolean | null`, and the router's extended fields, returned by the GraphQL `configs` query under `extended`, carry `null` for an undeclared field. The one exception is an integration that builds the GraphQL routes itself from an `extended` configuration they cannot read: those routes fall back to the configuration's raw entries, which carry `isArray` only where it is declared. Arranger's own GraphQL schema reads `null` as single-valued, so the field types it publishes are unchanged.

**Who is affected.** Code that reads `isArray` from a catalogue's extended fields, from column configurations or from introspection, and treats it as a plain boolean: `null` reads as falsy, and so as single-valued, which is what the third state exists to prevent. 3.0.x gave an undeclared field `false`, and had no `/introspection`.

**How to tell.** Search code that consumes introspection responses or Arranger's configuration types for `isArray`.

**What to do.** Check for `null` explicitly. Which reading is the cautious one depends on the use: an `all` clause needs `true` to be satisfiable at all, while combining two `in` clauses on one field is safe only when it is `false`. To have a field reported as `true` or `false`, declare `isArray` for it in `extended.json`.

<a id="sqon-package-consumers"></a>

### `@overture-stack/sqon` replaces `sqon-builder` in Arranger's packages

3.0.x's server and components depended on `@overture-stack/sqon-builder`, and the components on `sqon-builder` as well. In 3.1, the GraphQL router, the components and `@overture-stack/arranger-types` depend instead on `@overture-stack/sqon`, which is new in 3.1, and on neither `sqon-builder` package. Their TypeScript types describe a SQON as `SqonNode` from `@overture-stack/sqon`. They take and return SQONs as plain JSON objects, so nothing in 3.1 requires your own code to stop using `sqon-builder`. Network search now validates each query's `filters` with `@overture-stack/sqon`, which refuses a SQON nested more than 62 combinations deep.

**Who is affected.**

- Code that imports `@overture-stack/sqon-builder` or `sqon-builder` without declaring it in its own `package.json`, relying on the copy installed by the components. Arranger's packages no longer install it, so the import can fail after the upgrade.
- TypeScript projects whose types reach a SQON type through the GraphQL router, the components or `@overture-stack/arranger-types`. `@overture-stack/sqon`'s declarations reference Zod 4's, which TypeScript 4 cannot parse, `skipLibCheck` included. Zod 4's declarations use `NoInfer`, which arrived in TypeScript 5.4.
- TypeScript code that types SQON values with `@overture-stack/sqon-builder`'s `SQON` and passes them to the components. The components' `SQONType`, built in 3.0.x on that `SQON`, is now built on `SqonNode`, so check that such values still typecheck.
- Browser applications. `@overture-stack/sqon` installs Zod 4, where `@overture-stack/sqon-builder` 1.1.0 brought Zod 3, so a bundle that keeps `@overture-stack/sqon-builder` holds both majors.

**How to tell.** Search your code for imports of `sqon-builder` and `@overture-stack/sqon-builder`, and check that your own `package.json` declares each one imported. Check your build's TypeScript version.

**What to do.** Declare whichever `sqon-builder` package you import in your own dependencies to keep using it, or move to `@overture-stack/sqon` by its [migration notes](https://github.com/overture-stack/arranger/blob/main/modules/sqon/docs/sqon-builder-absorption.md). `@overture-stack/sqon`'s builder keeps two same-field `in` filters under `and` as two clauses, both of which must match, so a facet selecting several values of one field is built with it as an `or`, or as one `in` listing every value. It keeps an empty group where it sits, matching every document there (see [Empty combinations](#empty-combinations)). Compile with TypeScript 5.4 or later, or 5.0 or later with `skipLibCheck`.

<a id="advanced-sqon-builder"></a>

### The AdvancedSqonBuilder removes what a deletion empties

The `AdvancedSqonBuilder` in `@overture-stack/arranger-components` no longer leaves an empty group or an empty operand behind, since either would mean every document (see [Empty combinations](#empty-combinations)):

| Action | What it now removes |
| ------ | ------------------- |
| Deleting a group's last condition, under `and`, `or` or `not` | The group, and any group above it emptied by the deletion. A query emptied to its root is removed as a whole |
| Deleting a query | Every reference to it, then every reference to a query that this empties, and so on |
| Applying a term filter whose values Clear has removed | Its condition, the same way as deleting it, rather than leaving an `in` with no values, which matches nothing and would empty the results of the whole query it sits under |

A term filter that is the whole query has no group to be removed from, so it is applied as it stands.

**Who is affected.** Applications that render the `AdvancedSqonBuilder`, particularly those that store its query lists. The cleanup happens when a user deletes or clears something; a stored list is not cleaned when it is loaded.

**How to tell.** Look in stored query lists for a group with an empty `content` list, a reference to a query whose `content` is empty, or an `in` with an empty `value` list.

**What to do.** Upgrade `@overture-stack/arranger-components`, and clean those shapes out of stored lists, or ask users to review queries saved before the upgrade.

<a id="components-catalogue-scoping"></a>

### Component requests follow the resolved `apiUrl`

`DataProvider` in `@overture-stack/arranger-components` resolves one base URL: its `apiUrl` prop, joined with the `catalogue` prop, new in 3.1, when that is set. `apiUrl` defaults to `ARRANGER_API`, which is the first value set of `STORYBOOK_ARRANGER_API` and `REACT_APP_ARRANGER_API` in the environment and `localStorage.ARRANGER_API`, else `http://localhost:5050`. More of the components' requests now go to that URL, passed to the fetcher as `url`:

| Request | 3.0.x | 3.1 |
| ------- | ----- | --- |
| Table rows, and downloads | The resolved URL | The resolved URL |
| The configs request, `/graphql/Arranger-ConfigsQuery`, which loads the facet, table and download configuration and the extended mapping | No `url`, so the fetcher's own default | The resolved URL |
| `Aggregations` and `QuickSearch` | No `url` | The resolved URL |
| `ChartsProvider`, in `@overture-stack/arranger-charts`, new in 3.1 | | The resolved URL |
| The AdvancedSqonBuilder's extended-mapping lookups | No `url` | No `url`, still |

**Who is affected.**

- Applications where the resolved URL differs from where the fetcher sends a request given no `url`. With the default fetcher, that is an `apiUrl` other than `ARRANGER_API`. With a custom fetcher that has a fallback of its own, it can be any setup: one given no `apiUrl` sent the configs, facet and quick-search requests to its fallback, and now sends them to `ARRANGER_API`, `DataProvider`'s default.
- Applications that pass a `customFetcher` to `DataProvider`. It must use the `url` it receives as the base of the request, rather than a fixed base URL, or every request keeps going to that fixed URL, whatever `apiUrl` and `catalogue` say.
- Custom fetchers that always send a `POST` with a body. When `catalogue` is given without `documentType`, `DataProvider` first sends a `GET` with no body for `{catalogue}/introspection`, with the unscoped `apiUrl` as `url` and the catalogue in `endpoint`.

**How to tell.** Compare the `apiUrl` given to `DataProvider`, or `ARRANGER_API` where none is given, with where your fetcher sends a request that names no `url`, and read how your `customFetcher` builds its request.

**What to do.** Set `apiUrl` where the fetcher's own default was the address meant. Build a custom fetcher's request from `url`, `endpoint`, `endpointTag` and `method`, as the default fetcher does, sending no body when it is given none. A fetcher that rebuilds URLs from `catalogue` must not add it a second time to the introspection request. The AdvancedSqonBuilder's extended-mapping lookups still go wherever the fetcher sends a request with no `url`.

<a id="arranger-theme-merging"></a>

### Theme changes take effect, and theme arrays are replaced whole

In `@overture-stack/arranger-components`, the theme read by a component is built from these layers, in order:

1. Arranger's base theme, unless the provider is given `useArrangerTheme={false}`;
2. the theme of an enclosing `ArrangerThemeProvider`, if there is one;
3. the provider's own `theme` prop, which `DataProvider`'s `theme` prop also sets, since `DataProvider` renders an `ArrangerThemeProvider` with it;
4. each themed component instance's current contribution, from a `theme` prop through `withArrangerTheme` or a custom theme passed to `useArrangerTheme`, in the instances' mounting order. An instance's contribution is dropped when it unmounts, so one that remounts contributes last.

Layers 1 to 3 are merged again on every render of the provider. Each layer is merged over the ones before it into a fresh object, so no provider changes a theme shared with another, Arranger's base theme included:

| In a theme you pass | Is merged over what is below it by |
| ------------------- | ---------------------------------- |
| An object | Key by key, recursively |
| An array, such as `components.Table.defaultSorting` | Replacing the array below it whole |
| A theme function, `(theme) => newTheme` | Using what it returns |

A component's contribution is replaced whole when it changes. An object counts as changed when anything in it changes. A theme function counts as changed when the theme it produces changes, so one rebuilt with new state takes effect, as in 3.0.x, and one rebuilt with the same result causes no update. In a contribution of either kind, swapping one function for another in a function-valued property, with nothing else changed, is not detected. In layers 1 to 3 such a swap applies on the next render.

What an application passing a partial theme now sees:

| When | Now | `@overture-stack/arranger-components` 3.0.x |
| ---- | --- | ------------------------------------------- |
| A component re-renders with a key removed from its `theme` | The key reverts to the value below it | The removed value stayed, since merging never deleted a key |
| A component's `theme` changes, adds or removes a nested value | The change applies, with a re-render | A change or addition landed with no re-render, and a removal never applied. 3.0.x merged into the current theme's own nested objects, so its comparison of the theme as JSON found both sides already equal |
| An array is shorter than the one below it: the provider sets `defaultSorting: [A, B]` and a component sets `defaultSorting: [C]` | `[C]` | Merged by index: `C` merged over `A`, then `B` |
| The provider's `theme` prop changes after it mounts | The new value applies | A change under `palette`, `colors` or `shape` reached consumers, since 3.0.x merged it into Arranger's base theme's own objects; a change under `components` did not, since only the first value was kept |
| A provider stops passing a key, under `palette`, `colors` or `shape` included | The key reverts to the value below it | Under `palette`, `colors` and `shape`, the value stayed in Arranger's base theme, and reached every provider that read it |

Two limits remain:

- **A contribution applies to the whole provider, not only to the instance that made it.** Every instance's contribution is merged into the one theme that every component under the provider reads. So two instances of one component given different themes both apply to every component, and where they set the same key, the instance mounted later wins, whichever of them last changed its theme.
- **A theme function must return the same theme for the same input.** One whose result changes between calls, such as one reading a clock or a counter, never compares equal, so it updates the theme on every render.

**Who is affected.** Applications that theme Arranger's components through `ArrangerThemeProvider`, `DataProvider`'s `theme` prop, `withArrangerTheme` or `useArrangerTheme`, and in particular those whose themes:

- hold arrays that were meant to merge with an array set elsewhere;
- change while mounted, such as a theme toggled between light and dark, or one built afresh on every render;
- depended on a value persisting after the theme that set it stopped passing it;
- set a value in one provider that another provider read, which 3.0.x's merging into Arranger's base theme allowed under `palette`, `colors` and `shape`.

**How to tell.** Look through the application's themes for arrays, `components.Table.defaultSorting` being the common one, for themes computed from state or props, and for components rendered more than once with different themes. Then compare the rendered components with each layer's theme.

**What to do.** Pass every array whole, with every element it should hold. Keep in the theme any value you want to stay, since a key you stop passing now reverts to the one below it, and set in each provider the values it needs. Keep theme functions pure. To theme one instance differently from the others, wrap it in an `ArrangerThemeProvider` of its own, which keeps its contribution within that provider. To replace one function-valued property with a different function in a component's contribution, remount the component or the provider, since a change of function alone does not register there.

## Deprecations

A deprecated feature keeps working, and its section says what replaces it and how to migrate.

<a id="per-request-state-res-locals"></a>

### Per-request state moves from `req.context` to `res.locals`

**What changed:** the GraphQL router keeps its per-request state in Express's own store, `res.locals`, with its keys (catalogue configuration, search client, schema, debug flag and access-control decision) under `res.locals.arranger`. `req.context`, which earlier releases used, is now a view of `res.locals.arranger`: reading it returns that object, and assigning an object to it merges the object's keys in. It is deprecated, and `addContext` is deprecated with it. A `getServerSideFilter` callback receives an application's own `res.locals` keys, with the GraphQL router's keys over them, on every read path. Keys an application sets on `res.locals` for its own use, such as for templates, reach the callback and the GraphQL context the same way.

**Who is affected:** an application that reads or writes `req.context`, calls `addContext`, or passes `ctx: req.context` to `getAllData` or `dataStream`, and TypeScript code that declares `req.context` on Express's `Request` itself. A deployment that only runs the search server, or mounts the GraphQL router without its own middleware or export routes, is not affected.

**How to tell:** the first time application code uses `req.context`, Node prints one warning for the whole process:

```
[ARRANGER_REQ_CONTEXT] DeprecationWarning: req.context is deprecated: Arranger keeps per-request state in res.locals, ...
```

Start Node with `--trace-deprecation` to see where it came from, or with `--no-deprecation` to silence it. Under `--throw-deprecation` the warning is thrown as an uncaught exception, which stops the process, so finish this migration before enabling that flag.

**What to do:**

| Before | After |
| --- | --- |
| Middleware before the router sets `req.context.user = ...` | It sets `res.locals.user = ...` |
| `app.use(addContext({ user }))` | A middleware that sets `res.locals.user` |
| An export route calls `getAllData({ ctx: req.context, ... })` or `dataStream({ ctx: req.context, ... })` | It passes `ctx: res.locals` |
| Code reads the router's own keys, such as `configs`, from `req.context` | It reads them from `res.locals.arranger` |
| TypeScript declares `context` on Express's `Request` | Remove the declaration: the package declares `arranger` on Express's `Locals` |

Everything that uses `req.context` keeps working, apart from these details:

- **Adopting a `req.context` set before the router copies its own enumerable keys.** An object set there as a class instance loses its prototype's methods, and its getters are read once, when the GraphQL router adopts it.
- **Assigning an object to `req.context` after the router merges its keys into `res.locals.arranger`** rather than replacing anything, so `req.context = {}` no longer clears a key. Delete the key from `res.locals.arranger` instead.
- **With access control, an export route that passes `ctx: req.context` hands the filter callback the GraphQL router's keys alone**, without what middleware recorded at the root of `res.locals`. The callback then sees a request carrying no identity, and answers it by its own rule. Pass `ctx: res.locals` there.

<a id="configs-directory"></a>

### The 3.0 configuration location is deprecated

3.0.x read the configuration directory from `CONFIG_PATH`, still read by 3.1 as a deprecated alias of `CONFIGS_PATH`, with a warning (see [Environment variables renamed](#environment-variable-renames)). A relative path, though, the default `./configs` included, resolves from a different place. 3.1 resolves it from the server's starting directory, which in the image is `/app`, so the default is `/app/configs`; 3.0.x resolved it from its `modules/server` directory, `/app/modules/server/configs` in the image. Where a relative path names no directory from `/app` but does from `/app/modules/server`, the server reads that one, which is deprecated, and prints one warning at startup naming both paths:

```
[ARRANGER_CONFIGS_LOCATION] DeprecationWarning: Reading the configuration from /app/modules/server/configs, where 3.0 resolved it, since /app/configs does not exist. ...
```

An absolute path never falls back. Rename `CONFIG_PATH` to `CONFIGS_PATH`, and where the deployment relies on the default or on a relative path, set `CONFIGS_PATH` to the absolute path where the configuration is mounted, or mount it where the relative path now points, `/app/configs` for the default.

<a id="config-index-key"></a>

### A configuration file's `index` key is deprecated

3.0.x named a catalogue's search index with a top-level `index` key in its configuration files, usually in `base.json`, where 3.1 reads `esIndex`. Where a catalogue's files set `index` and no `esIndex`, the search server reads `index` as `esIndex`, overriding `ES_INDEX` as a file did in 3.0.x, and prints one warning at startup naming the files' directory:

```
[ARRANGER_CONFIG_RENAMED] DeprecationWarning: In /app/configs, "index" is deprecated: name it "esIndex" instead. See ...
```

Where the files set both, `esIndex` wins, and the warning says `index` was ignored. Rename `index` to `esIndex` in each catalogue's files. The alias is the search server's alone: an application passing `configs` to `arrangerRouter` names the index `esIndex` itself (see [The `@overture-stack/arranger-server` package is replaced](#arranger-server-package)).

<a id="network-config-shape"></a>

### Network search configured for 3.0 is deprecated

3.0.x turned network search on with `ENABLE_NETWORK_AGGREGATION=true`, and took the remote nodes as a list, set to `network` in the configuration files or to `NETWORK_AGGREGATIONS` as JSON, with the files' list laid over the variable's, position by position. 3.1 needs no flag: it lists the nodes under `network.remoteNodes`, and applies network search to each catalogue whose configuration lists them (see [Federated search](../../federated-search.md)).

Where `ENABLE_NETWORK_AGGREGATION` is `true`, in any case, the search server reads nodes listed the 3.0.x way, combined as 3.0.x combined them, as `network.remoteNodes`, so each catalogue keeps its network search over the same nodes. The server prints a warning at startup, code `ARRANGER_NETWORK_CONFIG`, for each of the two variables set and for each catalogue listing nodes the 3.0.x way:

```
[ARRANGER_NETWORK_CONFIG] DeprecationWarning: Catalogue "files" lists its remote nodes in the 3.0 shape, which is deprecated: list them under "remoteNodes" instead. See ...
```

How each 3.0.x configuration is read:

| 3.0.x configuration | In 3.1 |
| --- | --- |
| `ENABLE_NETWORK_AGGREGATION=true`, with nodes listed in the files, in `NETWORK_AGGREGATIONS`, or in both | Network search over those nodes, as in 3.0.x |
| Nodes listed, with `ENABLE_NETWORK_AGGREGATION` unset or anything but `true` | No network search, as in 3.0.x, and a warning that the list has no effect |
| `NETWORK_AGGREGATIONS` holding anything but a JSON list | No nodes from it, as in 3.0.x, and a warning that it has no effect |
| `ENABLE_NETWORK_AGGREGATION=true`, with no node listed for a catalogue | That catalogue is served without network search, where 3.0.x refused to start, and a warning names it |
| A catalogue whose files list nodes under `network.remoteNodes` | Read as 3.1 configuration, whatever `ENABLE_NETWORK_AGGREGATION` holds. `NETWORK_AGGREGATIONS` is not read for it, and a warning says so |

A 3.0.x node, with its `displayName`, `documentType` and `graphqlUrl`, is a 3.1 node as it stands, and network search covers the remote nodes alone, as in 3.0.x.

**What to do.** In each catalogue's `network.json`, move the list under `remoteNodes`, so that

```json
{
	"network": [{ "displayName": "Montreal", "documentType": "file", "graphqlUrl": "https://montreal.example.org/graphql" }]
}
```

becomes

```json
{
	"network": {
		"remoteNodes": [{ "displayName": "Montreal", "documentType": "file", "graphqlUrl": "https://montreal.example.org/graphql" }]
	}
}
```

Move any nodes listed in `NETWORK_AGGREGATIONS` there too, then remove `NETWORK_AGGREGATIONS` and `ENABLE_NETWORK_AGGREGATION`. Convert the list before removing the flag: a list under `remoteNodes` needs no flag, while a 3.0.x list without it has no effect, so removing the flag first turns network search off. 3.1's network configuration also takes a `localNode`, which adds the catalogue's own data to network search, and headers to forward to remote nodes; see [Federated search](../../federated-search.md).

### `facets.json`'s `__`-escaped nested field names are deprecated

`facets.json` entries for a nested aggregation field previously had to be written with dots replaced by `__` (e.g. `"fieldName": "donor__age"` for a mapping field `donor.age`), matching the internal GraphQL name. As of 3.1, `facets.json` can reference nested fields by their natural raw path (`"fieldName": "donor.age"`) the same way `extended.json`/`table.json` already do. The legacy `__`-escaped form is still accepted, and is deprecated. Update `facets.json` entries to use the raw dotted path.

## Recommended migrations

These changes are not required (existing behaviour still works), but they align your integration with 3.1's recommended patterns and will make future upgrades easier.

### Replace `hasValidConfig` with the introspection API

If your UI performs a startup check against Arranger using the `hasValidConfig` GraphQL query, switch to `GET /introspection` instead. `hasValidConfig` ties your frontend to the ES index name and is a candidate for deprecation.

The introspection endpoint returns the registered catalogues and their document types, which is what the check actually needs:

```
GET /introspection
```

```json
{
  "catalogs": {
    "participants": { "documentType": "participant", ... },
    "variants":     { "documentType": "variant",     ... }
  }
}
```

Replace the per-catalogue `hasValidConfig` calls with a single preflight fetch:

```ts
const checkArrangerCatalogues = async () => {
  const response = await fetch(urlJoin(apiUrl, 'introspection'));
  if (!response.ok) throw new Error('Arranger introspection endpoint unavailable');

  const { catalogs } = await response.json();
  const documentTypes = Object.values(catalogs).map((c: any) => c.documentType);

  const expected = [PARTICIPANTS_DOCUMENT_TYPE, VARIANTS_DOCUMENT_TYPE];
  const missing = expected.filter((dt) => !documentTypes.includes(dt));
  if (missing.length > 0) {
    throw new Error(`Expected catalogues not registered: ${missing.join(', ')}`);
  }
};
```

Your gateway or BFF layer will need a `GET /introspection` route that forwards to Arranger's introspection endpoint. Once this is in place, the `INDEX_NAME` env vars (which held ES index names that were never queried directly by the UI) can be removed from the frontend config.

See [Introspection API](../05-introspection.md) for the full response schema.

### Lock down CORS in production

3.1 adds `ALLOWED_CORS_ORIGINS` to control which origins may access Arranger. When unset, all origins are permitted: suitable for local development but not for production.

```bash
ALLOWED_CORS_ORIGINS=https://your-portal.example.com,https://admin.example.com
```

The value is a comma-separated list. When present, Arranger passes it to the `cors` middleware as an `origin` allowlist: a response to any other origin carries no CORS headers, so a browser page served from that origin cannot read it.

**CORS limits what browser pages can read, and nothing else.** The server still receives and answers a request from any origin, and a client that is not a browser ignores CORS entirely. It is no substitute for access control. Set this variable for any deployment a browser can reach from an untrusted site; behind a backend-for-frontend or reverse proxy that is the only caller, open CORS may be acceptable.

### Set GraphQL query complexity limits

3.1 introduces two optional query validation limits:

| Variable              | What it limits                                           |
| --------------------- | -------------------------------------------------------- |
| `GRAPHQL_MAX_ALIASES` | Maximum number of aliased fields per query               |
| `GRAPHQL_MAX_DEPTH`   | Maximum nesting depth of a GraphQL selection set         |

If left unset, both still default to conservative limits: 15 aliases and a nesting depth of 7. These defaults are enforced in code (not visible via the GraphQL schema itself), so a client that was working against an older Arranger version, or against a deployment that hasn't set these variables, may start seeing validation errors on queries that exceed them after upgrading. Set `GRAPHQL_MAX_ALIASES`/`GRAPHQL_MAX_DEPTH` explicitly to override the defaults for your deployment's actual query shapes.

These can also be set per catalogue in `base.json` under `maxAliases` and `maxDepth`, which takes precedence over the environment variables.

Whether the built-in defaults (15 aliases, depth 7) suit your deployment depends on your frontend's queries. Check your GraphQL operation depth and alias count against them before relying on the defaults, or before overriding them, to avoid breaking production traffic in either direction.

## Consolidating multiple single-catalogue instances

If you run one Arranger instance per catalogue today, you can optionally consolidate them into a single multicatalogue server. This is optional: the one-instance-per-catalogue pattern continues to work unchanged after upgrading.

### How multicatalogue routing works

`apps/search-server` reads `CONFIGS_PATH`. When that directory contains **subdirectories**, each subdirectory becomes a named catalogue, and routes include the catalogue ID as a prefix:

- GraphQL: `/{catalogueId}/graphql`
- Download: `/{catalogueId}/download`
- Fields introspection: `/introspection/{catalogueId}`

When `CONFIGS_PATH` contains `.json` files directly (the flat layout), the server continues to behave as a single-catalogue deployment and routes remain at `/graphql` with no prefix.

The catalogue ID defaults to the subdirectory name. To override it, add `"catalogId"` to `base.json`.

### Steps

**1. Plan your catalogue IDs.** The subdirectory name becomes the URL prefix: use something stable and URL-safe, for example `file`, `analysis`, or `clinical`.

**2. Restructure your config files into subdirectories:**

```
Before (separate instances, flat layout):

arranger-file/configs/          arranger-analysis/configs/
├── base.json                   ├── base.json
├── extended.json               ├── extended.json
└── table.json                  └── table.json

After (single instance, subdirectory layout):

arranger/configs/
├── file/
│   ├── base.json
│   ├── extended.json
│   └── table.json
└── analysis/
    ├── base.json
    ├── extended.json
    └── table.json
```

**3. Move per-instance env vars into `base.json`.** If `ES_INDEX` and `DOCUMENT_TYPE` were set at the container level for each instance, move those values into each catalogue's `base.json`. Use `"esIndex"` as the config key: not `"index"`, which refers to the Sets feature index and is silently ignored for catalogue config:

```json
{ "esIndex": "file_centric", "documentType": "File" }
```

**4. Point `CONFIGS_PATH` at the parent directory.** Each subdirectory is then an independent catalogue.

**5. Update clients and downstream services.** With more than one catalogue, the GraphQL path includes the catalogue ID prefix. Update any hardcoded paths:

```
Before: /graphql
After:  /file/graphql
        /analysis/graphql
```

> **Tip:** A server with exactly one subdirectory routes at `/graphql` with no prefix, the same as the flat layout. You can migrate one catalogue at a time: start the consolidated server with one subdirectory, validate all clients, then add the remaining catalogues.

**6. Retire the extra instances** once traffic is cut over.
