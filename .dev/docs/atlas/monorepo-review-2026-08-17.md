# Monorepo review: 2026-08-17

Full, requested review of the whole repo, not triggered by a specific bug report. Eight parallel review agents each covered one area (`modules/sqon`+`modules/types`, `modules/graphql-router`, `modules/components`, `modules/charts`, `apps/search-server`+`apps/mcp-server`, `integration-tests`+monorepo tooling, `/docs` accuracy, admin-ui deprecation blast radius), each instructed to check existing `tech-debt.md`/`roadmap.md` first and report only genuinely new findings or corrections to stale ones, and to verify every claim against actual current code, not speculate. All ~50 findings that survived are now written into `tech-debt.md`'s existing per-package sections, and four stale/incorrect roadmap.md items were corrected along the way. This doc is the triage entry point; the actionable detail lives in `tech-debt.md`.

A handful of the highest-stakes claims (the ones below marked "independently verified") were re-run directly, not just trusted from the agent's report, before being written up as confirmed.

## If you only fix five things

1. **`SqonBuilder.not([...])` inverts AND/OR semantics for exclusion filters** (`modules/sqon/src/builder/reduce.ts`). A public, documented builder call produces a silently wrong, broader result set. Independently verified. See [tech-debt: `SqonBuilder.not([...])` inverts AND/OR semantics](../../tech-debt.md#sqonbuildernot-inverts-andor-semantics-when-merging-same-field-exclusion-filters).
2. **`disableDownloads` does nothing; `disableFilters` doesn't cover `/download`** (`modules/graphql-router/src/router.ts`, `accessControl/disableFilters.ts`). Both independently verified. A deployment that believes it has disabled downloads or arbitrary filtering has not, for the export path. See [tech-debt: `disableDownloads`](../../tech-debt.md#disabledownloadsdisable_downloads-is-fully-documented-and-threaded-through-config-but-never-actually-checked-anywhere) and [tech-debt: `disableFilters`](../../tech-debt.md#disablefilters-protects-graphql-but-not-download-a-deployment-disabling-arbitrary-filters-can-still-get-a-fully-filtered-export).
3. **`SqonSchema` has no recursion-depth limit**: a ~25KB payload throws an uncaught `RangeError` out of `safeParse()`, which the MCP server calls on untrusted input assuming it can't throw. Cheap DoS-shaped vector on an endpoint that already has no auth or rate limiting. See [tech-debt](../../tech-debt.md#sqonschema-has-no-recursion-depth-limit-a-25kb-nested-payload-throws-an-uncaught-rangeerror-out-of-safeparse).
4. **`MCP_HOST` is parsed but never used to bind the server**, and the MCP SDK's own Host-header protection silently misfires as a result. Independently verified. See [tech-debt](../../tech-debt.md#mcp_host-is-parsed-and-validated-but-never-actually-used-to-bind-the-server-and-the-sdks-own-host-header-protection-silently-misfires-as-a-result).
5. **`modules/graphql-router/src/admin/`**: a complete legacy admin GraphQL backend with unauthenticated Elasticsearch write mutations, unreachable from any live code path but still compiling into the published `dist/`. Found independently by two separate review agents (the graphql-router review and the admin-ui-deprecation review), converging on the same ~30-file subtree without being told about each other's work, that cross-confirmation is stronger evidence than either report alone. See [tech-debt](../../tech-debt.md#modulesgraphql-routersrcadmin-is-a-fully-disconnected-legacy-admin-backend-still-compiled-into-the-published-package-with-no-access-control-of-its-own).

## Cross-cutting patterns

A single review surfacing the same root cause more than once, in packages that don't share code, is worth naming as a pattern rather than N unrelated bugs:

- **`apiUrl`/context value not forwarded to a nested query call.** Confirmed instances: `Aggregations`, `QuickSearch`, `useNetworkQuery`/`ChartsProvider` (all already fixed), `AdvancedSqonBuilder`, `Stats`/`CombinedStatsQuery` (still open, logged pre-existing). Same shape every time: a component correctly pulls `apiFetcher` from context but forgets `apiUrl`, so it silently queries the wrong catalogue in multicatalogue mode. Worth asking, next time a new data-fetching component is added: is there a lint rule or a shared hook that could make forgetting `apiUrl` structurally impossible instead of relying on remembering it per component?
- **A plain-JS component with a real, working prop/callback and zero corresponding TypeScript interface**, making the API invisible to type-based discovery. Confirmed instances: `DownloadButton`'s custom exporter function, `Aggregations`'s `onValueChange`, `useChartsContext`. This is a natural side effect of the JS→TS migration being incremental; worth a dedicated sweep once the pattern is confirmed a third and fourth time, rather than fixed one component at a time as each is independently discovered by a confused consumer.
- **A hand-maintained copy of a canonical lookup table drifts and nobody notices**, because the copy's key type is widened (`| string`) specifically to paper over a type mismatch that would otherwise have caught the drift at compile time. Confirmed: `modules/charts`'s `esToAggTypeMap` (`bytes`/`byte` typo) traces back to `ExtendedMappingInterface.type` being mistyped as a UI display-type union when it actually holds raw ES type strings. Fixing the root-cause mistyping is more valuable than fixing the individual duplicated map, since it's what let the typo ship silently instead of failing a build.
- **A feature flag is documented and threaded through config, but the code path it's supposed to gate never checks it.** Confirmed: `disableDownloads`. Every sibling flag in the same group (`disableFilters`, `disableGraphQLIntrospection`, `disablePlayground`, `enableGraphQLBatching`) is correctly wired; this one silently isn't. Worth a single test asserting *every* flag in `configArrangerFeatureFlagProperties` has at least one test that proves it changes behaviour when toggled, so a future flag addition can't repeat this by omission.
- **A stale tech-debt/roadmap entry survives because nobody re-checks it once the code moves on.** Six separate stale entries were caught and corrected in this pass (the `.env.arrangerDev` setup-guide entry, the `typeFns.ts` half of a types entry, the components rendering-coverage test-file count, the `esToAggTypeMap` severity, a roadmap pointer to a tech-debt entry that was never created, and the charts Phase 1.1 "skip tests" framing). None of these were wrong when written; all were overtaken by later work that didn't loop back to update them. No process fix proposed here beyond what already exists (this review itself); noting it because six stale entries in one pass is a real rate, not a rounding error.
