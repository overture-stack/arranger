# MCP host: connection authentication

This document describes the MCP host app, not Arranger. It is drafted here because the host's design conversation currently lives alongside Arranger's. It moves with the host app to its own repo once that exists, unchanged in scope.

This file covers each connection's authentication from the host's side. The delegated-access contract any Usher-protected application's client (this host, a portal backend, a pipeline) has to meet is its own: see `.dev/design/delegated-access.md` in Usher's repository.

Each section below says whether it records a decision, a recommendation awaiting the team, or mechanism already settled by existing design documents.

Terms used throughout:

| Term                                   | Meaning here                                                                                                                                                                           |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Principal                              | Whoever a request is made for: the person whose grants decide it.                                                                                                                      |
| Actor                                  | The software making the request on the principal's behalf, such as the host.                                                                                                           |
| Grant                                  | Usher's record of what a person may do with which data.                                                                                                                                |
| Usher's controller, bridge and adapter | Usher's central service; its library inside each application, which asks the controller for a person's permissions; and the part that applies them to a query.                         |
| Rule A, rule B                         | Rules in Usher's delegated-access design. A: a request made for a person is decided by that person's grants alone. B: a sign-in token works only at an application it is addressed to. |
| Token exchange                         | Trading a token at Keycloak, Overture's sign-in service, for one addressed to a different application.                                                                                 |
| Audience (`aud`)                       | The application a token is addressed to.                                                                                                                                               |
| `azp`                                  | The client a token was issued to.                                                                                                                                                      |
| Confidential and public clients        | An application that can keep a secret, such as a server, and one that cannot, such as a desktop app.                                                                                   |
| PKCE                                   | A one-time proof that stops a stolen sign-in code being used by a different app.                                                                                                       |
| Refresh token                          | A longer-lived token used to obtain new short-lived access tokens.                                                                                                                     |
| Realm                                  | Keycloak's container for one community's accounts and settings; Overture's is `overture`.                                                                                              |

## 1. The chain today

Person → host → `apps/mcp-server` → search server (bridge and Usher adapter) → Usher's controller.

`apps/mcp-server` calls the search server over plain HTTP with no credential today. It is a client of an Usher-protected application, the same as any other, not an enforcement point itself. Enforcement stays where the Usher adapter work already puts it, at the search server.

**Everything from §2 on describes a target with Usher enabled.** Usher is not a universal expectation: most of today's Arranger deployments, the Human Cancer Models Initiative (HCMI) portal among them, run with no access-control layer at all, and that keeps working unchanged. Against such a target, `apps/mcp-server` needs no identity from the host at all. It calls the search server exactly as it does today, whether it runs centrally or locally on the person's own machine. The evaluation harness already runs it locally (`mcp-platform-testing.md`), which is safe because no token is involved. §3 covers a local instance that does hold one. Nothing below applies until the target actually sits behind Usher.

## 2. Principal and actor

A request made for a person is decided by that person's grants alone; the client never gains access by acting for someone, and a client reading for nobody is a service account with grants of its own (`delegated-access.md`'s rule A). **Decided 2026-10-08:** the host never reads Overture data as itself. Every read is for a signed-in person, or anonymous and limited to open data; the host holds no grants of its own.

## 3. Identity propagation to Arranger-backed servers

**Token exchange, which shape (i) below uses.** The MCP authorization spec forbids token passthrough: a token issued for the MCP server must not be forwarded to whatever it calls downstream. Token exchange at the identity provider (RFC 8693, which Keycloak supports as Standard token exchange, on by default from Keycloak 26.2) is the pattern: `apps/mcp-server` exchanges the person's token for one whose audience is the search server. Keycloak performs this exchange only when the original token's audience already names the requester, and the requester must be a confidential client with Standard token exchange enabled. Standard exchange does not add an `act` claim: the exchanged token's `azp` names the requesting client instead, and Usher records `azp` as the actor, which is how §2's trail is produced. An `act` claim appears only where the identity provider adds one, for Keycloak its delegation feature, still a preview. The threat token exchange defends against: a token stolen at one hop replayed at another. Usher's rule B, decided 2026-10-16, makes this fail closed at Usher's own controller too, not only by the spec's convention: a sign-in token works only at an application it is addressed to, so the controller accepts one only when its `aud` names the application presenting it. Addresses are set per client at registration, not per sign-in: Keycloak writes them with an audience mapper naming every application that client is built to call. A client missing its mapper fails closed, refused rather than wrongly accepted. Deployments without Usher are unaffected by any of this, consistent with §1.

The host's own sign-in is the same under both shapes, wherever a target needs one. It is native-app OAuth, the standard way for a desktop app to sign someone in (RFC 8252):

- **The system browser, never the app's own webview.** RFC 8252 forbids an embedded webview for sign-in. Electron makes it the tempting path, so it is a rule rather than a default.
- **A public client in Keycloak**: Authorization Code with PKCE (S256), and no client secret.
- **A loopback or private-use URI redirect.** The loopback form is `http://127.0.0.1` on an ephemeral port, and RFC 8252 requires the authorization server to accept any port for it.
- **Consent required on the client.** Any app can present a public client's ID and claim its redirect. The consent screen is the person's only check that the app asking is the one it claims to be, so sign-in never completes silently.
- **Signing out revokes the refresh token at Keycloak** (RFC 7009), then deletes it locally. Deleting it locally alone leaves it valid at Keycloak, so any copy taken from the device still works.
- **No back-channel logout reaches a desktop app.** It learns of a revoked session only at its next refresh, which the `overture` realm's 5-minute access tokens bound.

**Two shapes satisfy an Usher-enabled target, and the deployment's own Keycloak decides which are allowed, not the host:**

- **(i) An operator-run `apps/mcp-server`,** a confidential client doing the token exchange described above. The actor in Usher's trail is a client Keycloak has verified.
- **(ii) A local `apps/mcp-server`,** using the desktop app's own public-client sign-in directly, presenting a token already addressed to the search server rather than exchanging one. Access is unchanged, since rule A never lets the actor widen a grant, but the actor becomes claimed rather than proven: any app can present the same public client's ID. Every installed copy of the app shares one `clientId`, so `clientId` alone identifies the app, never the person.

(ii) works only if the operator's Keycloak lets the desktop app's public client receive a token audienced to the search server; nothing in the host forces either answer. Under Usher's rule B, the controller accepts a sign-in token only when its `aud` names the search server's application. Both shapes meet that: (i) through the exchange, and (ii) through the token the operator's Keycloak issues. **Decided 2026-10-16:** a deployment holding controlled data allows only (i), so its Keycloak never issues the desktop app's public client a token addressed to the search server. A deployment holding nothing controlled may allow both. What (i) protects: a token stolen from a person's machine works only through the operator's `apps/mcp-server`, where the operator can watch, throttle or cut it off, which Usher's rule B guarantees. Neither shape stops a lookalike desktop app that the person signs in to; the consent screen is the check for that.

**Transport matters in exactly one case: a local `apps/mcp-server` that holds a person's token**, as (ii) does. A loopback HTTP port is reachable by every process and every user on the machine, and by a web page in the person's own browser through DNS rebinding, a trick that lets a web page reach services on the person's own machine. A stdio pipe, the private input and output channel between a program and the program that started it, reaches only those two. The MCP spec's Streamable HTTP security requirements already reflect this: a server MUST validate the `Origin` header against rebinding, SHOULD bind to localhost only, and SHOULD authenticate every connection, which is why `apps/mcp-server`'s own Host and Origin guards exist today. Those guards stop a web page, not another program: the Origin guard passes any request carrying no `Origin` header, which is every non-browser client. So a local server holding a token under (ii) needs more than the guards: either stdio, or a per-connection credential, such as a secret the parent process hands it at launch, on top of Origin validation. Against a no-auth target there is no token to protect, so the evaluation harness's existing loopback pattern needs none of this; the rule begins the moment a token is present. This `stdio` is distinct from the rule that already stops the CRE's main process from spawning a process named in user configuration ([mcp-host-plan.md](../mcp-host/mcp-host-plan.md) §2.1): that rule stops an arbitrary, user-supplied MCP server from being reached this way, while this is about protecting one specific, operator- or app-bundled `apps/mcp-server` instance that is not user-configured. The two do not conflict.

## 4. Third-party connections (cBioPortal-shaped)

The host holds tokens for each person, for connections to services outside Overture entirely.

**Decided 2026-10-17: consent, refresh and revocation.** The CRE's main process shows its own screen before the first sign-in to any third party, naming the service and what it sees on every call, requiring an affirmative action; like the approval and confirmation dialogues, this is owned by the main process, so the renderer can neither fake nor answer it. It sits alongside the third party's own OAuth consent screen, not in place of it. On a 401, the CRE's main process refreshes the connection's token using its own refresh token from the keychain, never surfacing either to the renderer or the model. A per-connection "Disconnect" action in the CRE's renderer has the main process call the provider's own revocation endpoint where one exists, then delete the keychain entry regardless of whether that call succeeds, the same order already decided above for Overture sign-out. Under [mcp-host-plan.md](../mcp-host/mcp-host-plan.md) §5, question 4, a third-party connection appears only in a conversation without controlled data. This closes three gaps: a person connecting without understanding what a third party sees per call, since that party's own screen is its own consent, not the host's; a connection silently breaking with no refresh path; and "disconnect" meaning nothing if it is only a local delete, the same reasoning already applied above to the Overture refresh token.

**Firm rule, not negotiable per connection:** an Overture token never reaches a third party, and a third party's token never reaches Overture.

**Decided 2026-10-15: tokens are stored in the OS keychain** on the person's own machine: Keychain on macOS, Credential Manager or DPAPI on Windows, Secret Service on Linux. That includes the person's own Overture refresh token, not only third-party tokens.

- **What it removes.** No server holds every person's tokens, so no single breach exposes them all.
- **What it leaves.** A keychain protects a token at rest, and from the machine's other users. It does not protect it from another process running as the same user: Windows' stores and Secret Service both let such a process read a stored item, and only macOS can bind an item to the signed app. Same-user malware is the remaining threat, which argues for short-lived tokens and narrow scopes.
- **The refresh token is the valuable target**, because it outlives a session. The access token handed to a connection matters less.
- **No token reaches the model**: not its context, a config file, a log or a crash report, the crash-reporting mechanism for which is in [mcp-host-plan.md](../mcp-host/mcp-host-plan.md) §2.4. §6 needs the same rule for a different reason: a token in the model's context is one prompt injection away from leaving through the next connection the model is told to use.
- **Revocation that counts happens at each provider.** Each device holds its own copy, and only the provider can end the tokens on a lost or compromised device. Deleting a device's copy cleans up that device alone.
- **Decided 2026-10-17: DPoP-bound refresh tokens for the desktop app's public client.** DPoP, Demonstrating Proof of Possession, binds a token to a private key held on the device, so a copy of the token is useless without that key. Keycloak's own specifications page lists RFC 9449 as supported, not preview, and the 26.8.0 release notes fix a bug where `DPoPBindEnforcerExecutor` required full DPoP on client create/update, defeating the lighter refresh-token-only binding RFC 9449 frames around public clients specifically ([26.8.0 release notes](https://github.com/keycloak/keycloak/releases/tag/26.8.0)). Adopt it once implementation starts, and confirm the deployed Keycloak is 26.8.0 or later first, since the bug affects exactly this use case on earlier builds. Where the platform offers one, that key is created non-extractable in hardware, the Secure Enclave on macOS or a TPM on Windows, so malware running as the person cannot extract it, stopping the token being used anywhere else, though not its use on the device while that malware runs there as the person. Where the platform does not offer that, the key sits in the same keychain as the refresh token, and DPoP then still defeats a token merely leaked without its key, through a backup, a log, or a copied file, but not malware already running as the person, which already reaches that keychain.
- **Linux needs an explicit check, not an assumption, and which `safeStorage` API is used decides what can even be checked.** Electron's synchronous API (`encryptString`/`decryptString`) supports `kwallet`, `kwallet5`, `kwallet6` and `gnome-libsecret` on Linux, and exposes `getSelectedStorageBackend()`, returning `basic_text`, `gnome_libsecret`, `kwallet`, `kwallet5`, `kwallet6` or `unknown`, none of which is the Freedesktop Portal Secret interface. The asynchronous API (`encryptStringAsync`/`decryptStringAsync`), which Electron's own docs recommend over the synchronous one, is the one that reaches Portal Secret (used when the app is sandboxed, a Flatpak package, for instance), but has no documented equivalent to `getSelectedStorageBackend()`, so the degraded case cannot be detected the same way. Either API falls back to a hardcoded plaintext password when no backend is running, rather than failing, which a minimal or headless Linux setup, plausible for this audience, would hit silently. Which API the app uses needs deciding first; if it is the async one, detecting the degraded case at all is undocumented and needs the same empirical check this project's own spikes already applied elsewhere, not an assumption that a check is even possible. Whichever Linux packaging format is chosen:
    - Check the backend at startup.
    - Under a degraded backend, store nothing. Keep tokens in memory for that session only, and tell the person why. They then sign in again at each launch, which is the cost of failing secure.

**cBioPortal, as checked on 2026-10-09.** Its hosted MCP servers, the database server at `https://mcp.cbioportal.org/db/mcp` and the navigator at `https://mcp.cbioportal.org/navigator/mcp`, require sign-in. The database server publishes protected-resource metadata, as the MCP authorization specification asks, naming cBioPortal's own authorization server, `https://mcp.cbioportal.org/`, which signs people in with Google, its only provider so far. A token it issues is valid at cBioPortal's servers alone.

The host's first connection for a person, traced:

1. The host calls the MCP server without a cBioPortal token, and receives a 401 pointing at its metadata.
2. The host reads the metadata and finds cBioPortal's authorization server.
3. The host registers itself there as a client, automatically, on first contact.
4. The person signs in through the browser with Google, and approves.
5. cBioPortal's authorization server issues a token for its MCP server, and the host stores it in the OS keychain (§4), alongside the person's Overture tokens.
6. Later cBioPortal calls carry that token, and Overture calls carry the person's Overture tokens. Neither is ever sent in place of the other.

Neither Usher nor Keycloak takes part. Usher governs Overture's data and accepts no outside token, and Keycloak signs the person in to Overture alone. Keycloak could offer Google as a way to sign in to Overture too, a convenience that still leaves two sign-ins and two tokens, since cBioPortal accepts only its own authorization server's tokens.

What the host needs for it: discovery, automatic client registration, the browser sign-in with PKCE, encrypted per-person token storage, refresh, and a way for the person to disconnect. cBioPortal records the person's Google email and account ID on every tool call, so connecting also tells cBioPortal who asked what; see §6.

Sources: [cBioPortal MCP documentation](https://docs.cbioportal.org/ai-integrations/mcp/), [the database server's discovery document](https://mcp.cbioportal.org/.well-known/oauth-protected-resource/db/mcp).

## 5. A remote or separate Usher instance

Token-level trust between two Usher instances is the federation question, and it hasn't been decided yet (network search is itself refused under access control until that lands). Until it does, this plan treats a remote Usher-governed server exactly like any other external OAuth resource under §4: its own sign-in, its own identity provider, no assumed trust with the host's own Usher instance. **Developer decision:** the federation posture, when it's time to revisit this section.

## 6. Data crossing connections in one conversation

Once a record enters the model's context from one connection, a later tool call to a _different_ connection can carry it out as an argument, with a third-party server's own (possibly untrusted) response as the likely injection point, and the receiving server may log what it was never meant to see. The same opening runs the other way: injected instructions in a third party's answer can make the host read _more_ Overture data with the person's authority than was actually asked for, a confused deputy rather than an exfiltration. Usher's guarantee ends at its applications' own answers, the same limit Usher states for exported files; it does not follow the data past that boundary into a model's context. Relevant given iMicroSeq's Indigenous data is explicitly in scope for this host. **Decided:** the model can never get data from an authenticated connection, one that carries the person's credential, into a request to another, and never proposes such a crossing. Data from an unauthenticated connection, which holds only what anyone may read, is not restricted. Only the person can carry restricted data across, through an action of their own that opens empty, shows exactly what goes where, opens a new conversation with the servers they picked, and is shown and recorded in the notebook ([mcp-host-plan.md](../mcp-host/mcp-host-plan.md) §5, question 4, which walks through what the researcher sees and does, and the two ways a conversation can keep servers apart). The options weighed before that decision, with worked examples: [MCP Host: Data Crossing Connections](../mcp-host/data-crossing-options.md).

- §3's native-app sign-in is settled mechanism. The exchange, the actor, and the trail apply only against a target with Usher enabled (§1); against a no-auth target, where `apps/mcp-server` runs is an ordinary deployment choice with no auth consequence. For an Usher-enabled target, two shapes are possible depending on the deployment's own Keycloak configuration: an operator-run confidential client with a verified actor, or a local instance using the desktop app's own public-client token with an actor that is claimed rather than proven. A deployment holding controlled data allows only the operator-run shape (decided 2026-10-16); one holding nothing controlled may allow both. A local instance holding a token also needs stdio, or its own Origin validation and per-connection authentication, never a bare loopback port. Check the decided parts of §3 and §4 against Usher's `delegated-access.md` rather than re-deciding them here.
- None of this blocks or reorders the Usher adapter's own work; `apps/mcp-server` sits downstream of that seam, not on its path.
