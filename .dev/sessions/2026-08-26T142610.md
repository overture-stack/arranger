Fixed hits and aggregations resolving to `null` for any field whose raw Elasticsearch name GraphQL disallows. Both resolvers sent the sanitized GraphQL name to Elasticsearch instead of the raw path. Verified against a live cluster across single-catalogue and both multicatalogue contexts.

- **The fix is two inverse maps on `graphqlNameRegistry`, because the two call sites need different key spaces.** `_source` selects top-level names, so `rawTopLevelNamesByGraphqlName` covers root fields only: including a raw object path pulls its children, which makes deeper entries unnecessary there. Aggregations flatten a whole dotted path into one name, so `rawPathsByGraphqlFlatName` maps that back to the full path. Putting both on the registry rather than deriving them per call site is what the registry already exists for.
- **`buildAggregations` changes only `esFieldName`, never `fieldName`.** The file already separates the Elasticsearch path from the response key, and the response key has to keep coming from the GraphQL name or `flattenAggregations` and the layer above it would need to learn about raw names. Undoing `__` recovers the nesting but not the characters sanitization replaced, which is why the string transform alone was never enough.
- **That change fixed two things it was not aimed at.** The SQON self-filter comparison and the nested-path lookup in the same function both compare against raw field names, so both were also wrong for awkward names while `esFieldName` carried the sanitized form.
- **The negative control earned its cost, and not by catching a bad fix.** Running the assertions before any resolver changed showed hits returning `null` and aggregations returning a single `__missing__` bucket, which is Elasticsearch reporting that no document carries the requested field: the precise signature of the defect rather than a malformed query. It also exposed a wrong expectation: two fixture records share an `_id`, so three documents index rather than four, and bucket counts written from the record count were off by one. **Fixing first would have meant correcting the test to match its own output**, which is tuning expectations to behaviour rather than deriving them.
- Verified that SQON filtering is genuinely unaffected rather than assuming it. Argument and configuration values carry raw names and are never sanitized, unlike the selection set, so sort clauses, `top_hits` `_source`, and the export path's `columns` are all outside this defect. Existing tests only ever filtered on names that sanitize to themselves, so nothing had actually demonstrated it; a filter on a hyphenated raw name now does.
- **A separate defect surfaced while building the inverse map, and it is not reachable by any encoding.** Two distinct raw paths can claim one aggregation name, and build-time detection covers sanitized leaves within a shared parent, which is a different space from the whole-path one. Logged in `.dev/tech-debt.md` with the concrete case and the reason a different separator cannot help: GraphQL names allow only `[_A-Za-z0-9]`, a subset of what Elasticsearch permits in a field name, so any separator emitted can also occur literally. Escaping schemes either rename every existing field containing an underscore or stay ambiguous where a run of underscores meets a dot.
- Worth keeping the layer distinction that took a while to state clearly: **translating the name for Elasticsearch and choosing the name for the schema are different problems.** The first is unconstrained and a lookup solves it. The second is constrained to the GraphQL alphabet and is lossy by construction, so it can only be detected, never encoded around.
- Coverage gaps left open and logged rather than closed: nested-type fields, the `nestingPrefix` branch, and aggregation types other than `buckets`. A plain object was used deliberately so a nested failure could not be confused with the separate `should`/`must` defect in `injectNestedFiltersToAggs`.
