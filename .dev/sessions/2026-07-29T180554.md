- Three factual errors found in the README's network section by reading it against the code, all corrected:
    1. **Union documented as an intersection.** The README claimed "fields unique to one node are excluded from federation". `combineAllFieldTypes` (`network/setup/fields.ts`) flatMaps every node's supported aggregations and dedupes, so it is a union: a field on only one node does appear in the schema. Nodes lacking a requested field are queried without it (`createNetworkQuery` filters per node) and contribute an `___aggregation_not_available___` sentinel bucket carrying their total hits (`AggregationAccumulator.emptyAggregation`). Documented the actual behaviour in both the README and the new page, since the sentinel bucket is load-bearing for anyone doing arithmetic on the response.
    2. **Config shown at the wrong layer.** The README presented `remoteRequests.headers` and `remoteNodes[].requests.headers` as `arrangerRouter` options. Neither exists in `NetworkConfig`; they are `search-server` config-file properties (`ExternalNetworkConfig`) that `normalizeNetworkConfig` converts into a `customizeRemoteRequest` function before the library sees them. Passing them to `arrangerRouter` directly is a silent no-op. README now separates the two layers explicitly and states this. Also corrected the precedence claim: per-node `requests.headers` **replaces** `remoteRequests.headers` for that node (`matchingConfig?.requests?.headers ?? allRequestsPassthroughHeaders`), it does not merge with it as the README said.
    3. **Wrong `documentType` in the example.** The README used `documentType: 'FileAggs'`. `fetchNodeAggregations` interpolates `` `${documentType}Aggregations` ``, so that value would resolve to `FileAggsAggregations` and fail discovery. Corrected to the bare document type (`file`), with an inline comment explaining the interpolation, and the field table now says so.
