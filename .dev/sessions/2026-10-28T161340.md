Moved the data-crossing rule into `mcp-host-core`, so `chat`, `eval` and the CRE all get it rather than each consumer's approval policy, since a rule each consumer can leave out is optional and no one agrees to an attack. Built way (b) of the plan's question 4, ahead of the team's confirmation, because switching to (a) later only drops one check and leaves the saved state unchanged, while the reverse would strand saved multi-server conversations.

- `modules/mcp-host-core/src/state.ts`: `assertServersApart` refuses a server not flagged `containsOnlyOpenData` beside any other, and a restore putting any server beside another whose data is restricted, before anything connects; `restrictedDataFrom` names any other server whose restricted data a call would carry out, replacing `carriesRestrictedData`
- `src/host.ts`: `create` applies way (b); `#runCall` ends a call as `crossing_refused` before the policy is asked, so no one is asked to approve a crossing; the policy's `{ refuse: reason }` decision and its `history`, `connections` and `carried` inputs are removed, so it sees only the call
- `src/toolMessages.ts`: the refusal has fixed wording naming both servers, so transcripts compare across consumers
- A restore could bring back a server the conversation held before another server's data became restricted, after a flag was turned off and on again; the model would see its tools and never be able to call them. `assertServersApart` now refuses that restore, so under (b) the call refusal guards only against a fault in the start checks, and is covered by unit tests of `restrictedDataFrom` and the tool message rather than at host level
