Addressed the two review points on PR #1108 about `OpenAiCompatibleProvider`, after checking both against the code.

- The constructor refuses an `apiKey` over plain HTTP to a non-loopback host unless `allowInsecureHttp` is set, as `mcp-client` already does for MCP servers. A function-form key counts, since its value is unknown until request time. A malformed base URL now fails at construction rather than as a `network` error
- `mcp-client` exports `isLoopback`, so both modules share one definition
- `extra` can still override the sampling fields, the documented way to swap `max_tokens` for `max_completion_tokens`, so it was not moved first. Setting `model`, `messages`, `tools`, `stream` or `stream_options` is now an `unknown` error before sending, since each sent something other than what `model_request` records or broke reading the reply
- A body `JSON.stringify` rejects, such as a BigInt in `extra`, is now `unknown` rather than `network`
- The rest of host-core needed neither fix: MCP connections already go through `mcp-client`'s guard, and `run.ts` and `connections.ts` already spread caller fields before their own
- Open: no test covers whether Node's `fetch` drops `authorization` on a cross-origin redirect, such as an https-to-http downgrade

An adversarial review of the fixes above raised five findings. Each was reproduced before fixing, and each fix was prototyped outside the repo and checked by removing it and watching its test fail.

- `n` is reserved, and `foldChunk` reads only the first choice. With `n: 2`, a server's two replies merged into one text and one malformed call. A choice without a numeric index counts as the first, so a server sending `"index": null` loses nothing
- Both fetches use `redirect: 'manual'`, so a redirect is an `http` error with its status. Following a 307 re-sent the whole conversation to the new origin, with only `authorization` dropped. `'manual'` was chosen over `'error'`, which surfaces as an unhelpful `network` error
- The new `outputLimitField` option names the field that carries the reply cap, `max_tokens` by default since Ollama ignores `max_completion_tokens`. `seed` and both cap fields are now reserved, since overriding them defeated the context fitting and the retry seed. `toWireRequest` drops reserved keys from `extra` and spreads the rest last, restoring the earlier field order
- The README no longer says the provider refuses every key it sets, and an empty `apiKey` is no longer refused
- Open: whether OpenAI's reasoning models accept the `temperature` and `top_p` host-core always sends is unverified. Node 20 and 22 were not tested, though `'manual'` does not depend on how each strips headers

A re-review raised two more points, both checked before fixing.

- A refused redirect's error now names its target, without credentials, query or fragment, and suggests https when a plain HTTP base URL redirects to it on the same host. The bare status left a keyless `http://` base URL behind an https-redirecting proxy unexplained, a setup that worked while redirects were followed
- `outputLimitField: 'max_completion_tokens'` with `ollama` is refused at construction. On local Ollama 0.34.3, `max_completion_tokens: 5` gave `stop` and 131 tokens where `max_tokens: 5` gave `length` and 5, so the cap, the output-limit retry and the context reserve all lapsed. A server reached without `ollama` is not caught

Settled the three items a follow-up proposal left open, each checked against the code first.

- A reserved `extra` key now fails `McpHost.create`, before anything connects, rather than the first request. `LlmProvider` gained an optional `assertSettings`, which `validateOptions` calls last, and the provider's message names what to use instead of each key. `generate` keeps the refusal for a caller without a host. `validateOptions` also requires a positive whole `maxOutputTokens`, and a `context_window` ending now says how much of the estimate is the reply cap. The proposed `maxOutputTokens < contextWindow.tokens` check was left out: a cap just under the window passes it and still fails every turn, and the window Ollama reports is only known once a run starts
- `model_request` is documented as an attempt, not a request the server received, with exactly one `model_response` or `model_error` after it, or `done` when the run is stopped. A host test pins the pairing, and the loop diagram shows the event. No behaviour changed
- `mcp-client` exports `InsecureTransportError`, a `TypeError` subclass with the `host`, and a generalised `assertCredentialTransport`, and no longer exports `isLoopback`. The provider and `validateOptions` use the same guard, so both packages throw one class with one wording, and an insecure server fails `create` before any server connects. Its own class matters because `fetch` reports a network failure as a `TypeError` too. `mcp-host-core` re-exports the class, so a consumer can catch what `create` throws without depending on `mcp-client`

A further re-review raised three points, each checked against the code first.

- The `model_request` contract missed truncation: `#generate` emits `model_response`, then the backstop emits a `model_error` of kind `truncated` for the same turn. The event's doc, the loop section and the plan's `model_error` row now say so, and a host test pins that order
- `validateOptions` now refuses a `maxOutputTokens` of at least `contextWindow.tokens`. A request fits only when its estimate, the prompt plus the cap, is at most the window, and the prompt is never empty, so such a cap can never fit. This reverses the earlier decision to leave the check out, since it claims only that case. The bound does not count the system prompt, because the tools and server instructions are unknown until the servers connect
- The PR reply should say how to switch the cap field, now that `extra` cannot set it. The `max_tokens: undefined` pattern never reached the code under review, so the reviewer never saw it, but that code let `extra` override `max_tokens`
- `.dev/docs/atlas/mcp-client-landscape.md` no longer lists Ollama's handling of `max_completion_tokens` as unverified
