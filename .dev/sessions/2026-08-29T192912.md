Extracted `modules/sqon`'s same-field merge rules into their own README section, then found and fixed a second, unrelated `not`-scope defect while designing a proposed builder addition, and left that addition itself as an open design pending one more round of review.

- **The merge rules previously lived only as a supporting detail inside `matchNothing`'s justification, invisible to a reader not already reading about match-none filters.** The exact rule that changed reduction behaviour this cycle (`in` merges under `or` only) was stated as one bullet among three explaining a different feature entirely. Moved to its own "Same-field merge rules" section stating all six operator groups (`in`, the `not-in` family, the four range operators, `between`, and the `not` exclusion) directly, with `matchNothing` now referencing that section instead of restating it, so there is one statement rather than two that happen to agree today. Closes with the positive framing rather than the prohibition: a facet union is `or`, and `or` produces the identical SQON before and after the change, which is the sentence a reader upgrading actually needs. Points at the 3.1 migration guide for anyone whose results changed, rather than duplicating its content.

- **Found, while designing a proposed value-widening builder method, that `setFilter` silently inverts the caller's requested condition when the current SQON's top level is a `not` combination.** `not`'s children are each independently negated (`not[A, B]` means `¬A ∧ ¬B`, confirmed against the actual compiled query rather than assumed, since a backwards application of exactly this fact was caught and corrected once already during the design work itself). `setFilter('a', 'in', ['z'])` against `not[in a:['x'], in b:['y']]` produced `not[in a:['z'], in b:['y']]`: the caller asked to assert `a is in ['z']` and silently got `a is not in ['z']` instead. Confirmed this affects both the replace path and the append path (no existing match on the target field also lands inside the `not`, negated the same way). No silently-correct rewrite exists for every operator: only `in`/`not-in` and `gt`/`lte`/`gte`/`lt` have a clean single-leaf inverse, and the alternative of treating the `not` as opaque and composing the new condition alongside it can produce an always-false query when the new value collides with one the `not` already excludes. `setFilter` now throws when the current SQON's top level is a `not`, rather than producing an incorrect result silently. `removeFilter` needed no equivalent fix: confirmed correct as-is, including its partial-value-removal path, since dropping a value or a whole clause from `not`'s content only ever widens the match.

- **A proposed `addToFilter` builder method remains an open design, not yet implemented.** Motivated by a downstream consumer hitting this cycle's `in`-under-`and` correctness fix as an unannounced breaking change: chaining `.in()` for the same field has always `and`-composed rather than widened, which the old (incorrect) merge rule silently repaired until now. One round of adversarial review complete: an `all`-cardinality hazard (unsatisfiable on a single-valued field once a second value is added) is now the leading argument for scoping the first version to `in` only, and the method's name, its interaction with a same-field filter of a different operator, and whether `.in()` itself should warn on its own footgun remain open. Full detail, including the rejected alternatives and the reasoning for each, in `.dev/docs/sqon-widening-primitive.md`.

Reviewed a downstream `isArray`-aware cardinality gate (`apps/mcp-server`'s `build_sqon` tool) adversarially, found a real gap and a real schema defect, verified both fixes sound before recommending them, then found and fixed an unrelated defect while closing out the recommended sequencing.

- **The gate scans `existingSqon`'s raw, pre-reduction shape, but the tool's own fold implicitly reduces it before combining a new clause.** A same-field collision hidden inside a nested single-item group (invisible to the gate's one-level scan) becomes a top-level sibling the moment reduction runs, so the gate can silently pass exactly the shape it exists to catch. Confirmed by executing it end to end, for both `in` and `all`. Fix: reduce `existingSqon` once, immediately after validation, so the gate and the fold share one already-reduced view. Verified access-control-safe first: the tool has no path into `compileFilter`/`serverSideFilter` at all, so reordering when reduction runs cannot have an access-control consequence, and the fold always runs regardless (`clauses` requires at least one entry), so the change is provably output-neutral, it only changes what the gate sees.
- **A schema field meant to accept an old, pre-cardinality Arranger server instead rejected it outright.** `isArray: zod.boolean().nullable()` had no `.optional()`, so a response missing the key failed validation entirely, contradicting its own inline comment and inconsistent with the sibling `unit` field two lines below using the correct pattern for the identical need. Fixed; both downstream cardinality checks already treat "missing" the same as "null" (the cautious branch), so this only widens which servers can be talked to, nothing about how permissively their responses are read.
- **Both fixes were checked against data access control standards before being recommended, not just for correctness.** Confirmed empirically rather than assumed: `compileFilter`/`serverSideFilter`/`getServerSideFilter` appear nowhere in the tool's source, and the one schema field that could have carried access-control signal (`meta.authFiltered`) is parsed but read by no code on the consuming side, and hardcoded `false` on the serving side today, so tightening or loosening around it changes nothing live.
- **Before recommending the reduce-earlier fix, extended `reduce.property.test.ts` to cover `all`, `some-not-in`, `between`, and a pivot dimension**, none previously modeled, precisely because they overlap the merge mechanism the gate exists to police. Doing so surfaced a real, independent defect: `reduceSqon`'s value deduplication ran unconditionally on every array-valued leaf, including `between`'s `[min, max]` pair, a fixed-position tuple rather than a set of options. `SqonBuilder.between('age', [30, 30])` deduplicated to a one-element array, one short of what the schema itself requires, so the result failed re-validation on its next parse. Fixed by excluding `between` from deduplication; confirmed clean across repeated runs afterward.

Both fixes implemented directly in `apps/mcp-server` (not just recommended) once verified, alongside the `modules/sqon` fix the verification work surfaced. 168/168 `modules/sqon` tests, 270/270 `apps/mcp-server` tests, clean typecheck, clean build.
