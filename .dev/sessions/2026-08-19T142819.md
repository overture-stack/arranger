# 2026-08-19

## MCP server platform testing plan

Wrote `.dev/docs/mcp-platform-testing.md`: a plan (not an implementation) for an end-to-end
platform test suite that runs a fixed harness, corpus, and pinned model against a changing
`apps/mcp-server`, producing metrics that can justify keep-or-revert decisions.

### Key decisions recorded in the plan

- **Three layers, not one suite.** L1 contract tests (no LLM, gates every PR), L2 agent runs (LLM,
  on demand / nightly), L3 judge (replayable offline from stored L2 transcripts). Most regressions
  in this server are schema, description, validation, and error-text regressions, which L1 catches
  for free.
- **Runner decision is small and deferrable.** No framework covers the hard part (seed ES, start
  Arranger multi-catalogue, start MCP server, drive an elicitation-capable MCP client, bridge tool
  schemas, assert SQON semantics). Recommended: extend `integration-tests/mcp-server` with
  `node:test` for L1, new `integration-tests/mcp-evals` workspace with a bespoke TS runner writing
  JSONL plus an `evals:compare` CLI for L2. Defer Evalite/Langfuse until reading JSONL is the actual
  pain point. promptfoo adopted separately for MCP red-teaming (aimed at the two URGENT auth and
  rate-limit tech-debt items).
- **The MCP connector (`mcp_servers` + `mcp_toolset`) cannot be used.** It runs server-side from
  Anthropic and needs a public HTTPS URL, so a localhost MCP server in CI is unreachable, and
  tunnelling out an unauthenticated server is not acceptable. Bridge tools locally instead, which
  also keeps elicitation visible to the harness.

### Objections raised against the originally-framed approach

- One prompt, one run, assert tool calls will not work: sampling variance exceeds the effect size of
  most description changes. Measuring the noise floor (R2) comes before authoring any cases.
- Sampling can no longer be pinned at all: `temperature`/`top_p`/`top_k` are rejected with a 400 on
  Opus 5, Sonnet 5, Opus 4.7/4.8, and Fable 5. `output_config.effort` is the only controlled knob.
- Exact tool-call sequence assertions overfit; grade required tool *set* plus forbidden patterns,
  and score outcome separately from trajectory.
- The existing fixture corpus (5 docs / 3 fields, and 2 docs / 2 fields) cannot discriminate field
  selection quality. A purpose-built corpus with deliberate traps is a Phase 1 deliverable.
- Stale `modules/sqon/dist` would silently misattribute benchmark results to the wrong commit
  (already logged in tech-debt). Mandatory rebuild plus recorded module hashes.

### Metric notes worth keeping

- Static surface token cost via `messages.countTokens` over instructions plus `tools/list` is
  deterministic, near-free, and the single best CI-gateable regression metric. `instructions.ts`
  already documents that this cost is "billed on every session" with no way to observe it.
- Invalid-call rate and error-recovery-within-k are the highest signal-per-dollar metrics and need
  no judge. The `build_sqon` batched-errors change (`b6a9ff82`) was justified entirely on
  "fewer re-submissions", which is exactly error-recovery-within-k and was never measured.
- Reuse the Answerable / Unanswerable / Ambiguous / Improper taxonomy already in `prompts.ts` as
  eval case categories, so the negative cases exist from the start.

### Cross-references to existing debt this plan touches

- Corpus should include a hyphenated and a leading-digit field name: tech-debt notes the partial
  `sanitizeGraphqlFlatName` reimplementation in `queryBuilder.ts` and that "no existing fixture has
  one". The eval corpus becomes a regression net for it.
- Harness should read `SEARCH_ENGINE` rather than hardcoding Elasticsearch, per the OpenSearch-first
  migration.
- `integration-tests/mcp-server` is still never typechecked; a new sibling eval workspace should not
  repeat that.

### Revision: corrected environment assumptions

Two of the plan's premises were wrong and the doc was rewritten. Recorded because the corrections
changed the design, not just the config.

- **Models are open-weight, self-hosted on team-controlled hardware, in small/medium/large tiers,
  with settable sampling.** Consequences worked through in the revision:
  - Two decoding regimes replace "handle variance statistically": greedy plus batch invariance as a
    low-variance regression channel, and sampled at production settings with **seeds derived from
    the trial index** so baseline trial *i* and candidate trial *i* pair up. Paired seeds are a real
    methodological upgrade over any hosted API.
  - Temperature 0 plus a fixed seed is still not deterministic on a batching server (batch-size
    dependence of reduction kernels). vLLM's `VLLM_BATCH_INVARIANT=1` is the only online-mode route,
    requires compute capability 8.0+, and costs throughput, so it **cannot be on during the latency
    pass**. Two passes, or latency only from the sampled regime.
  - The serving stack became part of the system under test. Chat template and `--tool-call-parser`
    are now manifest-pinned, and invalid-call rate had to be split three ways
    (`parse_failures` = serving-stack, run-invalidating; `schema_invalid` = schema clarity;
    `semantically_invalid` = introspection/description quality). A parser mismatch would otherwise
    read as an MCP regression.
  - Token metrics are tokenizer-relative, so cross-tier totals are meaningless. Added context
    consumption **as a fraction of the served window**, which is the metric that will say whether
    the surface is usable on the small tier at all.
  - Dollar cost per task replaced by tokens per task, GPU-seconds, and **tier-crossover** (the
    smallest tier a case passes reliably on). Tier-crossover is the headline metric multi-tier
    serving makes available and a single hosted model does not.
  - Constrained decoding (xgrammar / guided JSON) collapses `schema_invalid` to zero, so it hides
    the signal that measures schema clarity. Run both ways deliberately.
- **Data lives on a separate testing ES + Arranger instance with real data, not repo fixtures.**
  - The "fixtures are too thin" objection is withdrawn.
  - **Second correction: that corpus is frozen.** So exact-outcome assertions (totals, primary keys,
    buckets) are valid everywhere, gold expectations are a one-time derivation rather than ongoing
    maintenance, and `driftTolerance` / degraded-mode / bounded-property assertions were all cut
    from the plan. `evals:refresh-expectations` became `evals:bootstrap-expectations`.
  - The fingerprint check survives the simplification, deliberately and in reduced form: it is no
    longer defence against expected drift but against a silent accident (unannounced reindex,
    catalogue config edit on the testing server, `ARRANGER_BASE_URL` pointed at the wrong instance).
    All three would present as an MCP regression and are indistinguishable from one without it. One
    request at run start, recorded in every manifest.
  - Fingerprint **through Arranger, not ES**: needs no ES credentials, covers catalogue config as
    well as data (a config change is the thing most likely to change on a testing server even when
    the data is frozen, and would otherwise be misattributed to the MCP server), and exercises the
    same path the MCP server uses.
  - Real data will not contain the pathological field shapes that guard open tech debt (hyphenated
    and leading-digit names, arrays, `nestingPrefix`). Proposed a small synthetic trap catalogue
    alongside the real ones; otherwise record explicitly what the suite cannot see.
  - Transcripts will contain real record values. Rules out third-party hosted eval platforms
    (Braintrust and similar), argues against committing transcripts, and adds an `EVAL_TRANSCRIPTS`
    toggle. Needs an explicit retention decision before Phase 2.
- **Latency retained as requested**, but with fixed concurrency, recorded serving-load context, and
  the decomposition. Reported, never gated: it now moves with our own GPU load rather than a
  vendor's. Turn count is the unconfounded proxy, and when the two disagree, believe turn count.
- **MCP server may be remote**, so the suite supports `MCP_MODE=inprocess|remote`. Surfaced a real
  blocker: **nothing in the MCP surface reports a build identifier**, so a remote-mode result cannot
  be tied to a commit and the comparison premise fails. Until the server reports a version (ties to
  the roadmap's Arranger version exposure item), remote mode is smoke-testing only. Also needs
  `MCP_API_KEY` header plumbing built in from the start.
- **Model client recommendation changed** from the Anthropic SDK to the `openai` npm package pointed
  at the serving base URL, since every mainstream open-weight serving stack exposes that API. The
  MCP-connector objection is moot. AI SDK noted as the alternative if hosted-model comparison is
  ever wanted.
- Added a full env-var contract (§ 7) with a single Zod-validated config module and an `.env.schema`,
  per the repo convention. Deliberately no ES credentials.
- Phase 0 spikes reordered: **serving-stack shakeout (R2) now precedes the noise floor (R3)**,
  because a high baseline parse-failure rate makes every downstream metric uninterpretable.

### Revision 2: session variance promoted to a first-class metric

Developer proposed freezing everything *except* the session (many fresh sessions, same server, same
prompts) and treating the resulting variance as the metric of interest, rather than freezing all but
the MCP server. Evaluated as: wrong on mechanism, wrong as a substitute, right on importance, and it
exposed a real gap in the plan.

- **Mechanism correction.** Two fresh sessions against the same server start byte-identical:
  `SERVER_INSTRUCTIONS` is static by deliberate design and the tool list is static. There is no
  session-setup nondeterminism. Observed divergence is sampling variance *amplified by the agent
  loop* (one different token at turn 1 changes the tool call, which changes the tool result, which
  changes every later turn), plus minor genuine tool-result nondeterminism (ES does not guarantee
  ordering for equal sort keys). Exception worth noting: `query_arranger` in `prompts.ts` does build
  its text from live introspection at call time, unlike the static instructions path.
- **Not a substitute.** Variance is a scalar with no direction: a change that is uniformly worse but
  *consistently* worse scores as a variance improvement. And variance is only attributable to the MCP
  server when the server is held fixed within a condition, which is the freeze-all-but-the-server
  design at N greater than 1. The two framings are the same experiment.
- **But it was under-weighted, and the reason is specific to this server.** Variance reduction is
  close to the server's primary design goal: the "Never guess" rules exist to stop the model
  freelancing, and `build_sqon` exists to remove the LLM from SQON synthesis, justified in the
  roadmap on the grounds that SQON generation was "hit-or-miss in practice", which is a variance
  complaint and not a mean-accuracy complaint. A suite reporting only mean success would have failed
  to measure what the central design decision was aimed at. For a portal whose answers are counts,
  inconsistency is also a correctness failure rather than a polish issue.

Plan changes made:

- New § 1.2 "One experiment, three readings": mean (is it better), spread (is it trustworthy),
  divergence point (which part of the surface caused it). All three from the same N sessions.
- New § 3.4 with `pass^k` promoted to a headline number, plus two new metrics that came directly from
  the developer's instinct: **answer dispersion** (count of distinct final totals / catalogues /
  filter field sets across N sessions, which catches a model that uses tools correctly every time but
  reports a different defensible number each session) and **divergence point** (first turn at which
  the N trajectories stop agreeing, bucketed by what diverged, which localizes inconsistency to a
  specific part of the MCP surface and makes it actionable). Plus an L1 surface-stability assertion
  (M sessions, identical surface hash) to catch accidental nondeterminism in the session prefix.
- New § 3.5: consistency metrics need meaningfully more sessions than proportions do. Expect N=10+ on
  a designated consistency subset, N=5 across the breadth.
- § 4.1 rebalanced: greedy suppresses the variance being measured, so it cannot produce a consistency
  number. Sampled regime becomes primary for quality and consistency; greedy demotes to a cheap
  nightly smoke channel.
- Guardrail added in two places: variance is never reported without its paired success rate, and the
  comparison CLI should refuse to render one without the other.
- Phase 3 gains an aggregate-scorer seam (consistency scorers operate across the N sessions of a
  case, not per session). Flagged to design that interface *before* the per-trial scorers rather than
  retrofitting.
- R3 extended to produce the first divergence-point histogram, since where sessions currently stop
  agreeing is a finding in itself and will likely reshape which cases get written in Phase 1.

### Revision 3: automation boundary (§ 9)

Added in response to "how much of this can be automated". Answer: everything that runs, almost
nothing that decides. A full run is one unattended command; the human cost is front-loaded into case
authoring and recurs at a low rate.

Three design constraints recorded, because automating them actively degrades the suite:

- **L2/L3 must not gate CI.** Model-layer variance produces false failures, and a gate that cries wolf
  gets disabled within a fortnight, leaving no gate at all. Only L1 gates; L2/L3 report. This is the
  load-bearing reason for the layer split.
- **Baselines must not auto-promote.** A post-merge job that overwrites the baseline with the latest
  run launders every regression into the new normal, and the suite then reports "no detectable effect"
  forever while quality drifts down. Promotion is a deliberate reviewed act with a stated reason.
- **Cases must not have model-generated ground truth.** Generating prompts is fine; generating expected
  answers means measuring agreement with the generator's beliefs about the corpus instead of
  correctness, and it makes the suite immune to the exact failure mode it exists to catch (a model that
  misreads the catalogue the same way in both places scores a pass).

Also recorded: the effort shape. Harness code is a few hundred lines and is not the bottleneck; Phase 0
spikes and Phase 1 case authoring are. Ongoing cost is low but does not reach zero, and a suite nobody
adds cases to stops detecting anything within a couple of quarters.

### Revision 4: terminology (2026-08-20)

"Corpus" removed from the plan entirely. It appeared nowhere else in the project, carries a
linguistics connotation (a body of *text*) that mismatches structured records, and was being used for
four different referents at once, which was the actual problem. `docs/concepts.md` already uses
**dataset** in this plain sense ("A **catalogue** is one searchable dataset in Arranger"), so no new
vocabulary was needed.

Split applied throughout `.dev/docs/mcp-platform-testing.md`:

| Referent | Term |
| --- | --- |
| Documents in the testing indices | **dataset** (matches `concepts.md` prose) |
| Dataset *and* catalogue configuration together, i.e. the fingerprint scope | **test environment** |
| The evaluation cases and their expectations | **case set** |
| Small, committed, suite-controlled data files (the synthetic trap catalogue) | **fixtures** (matches existing repo usage in `integration-tests/mcp-server/test/assets`) |

The dataset/test-environment distinction turned out to be load-bearing rather than cosmetic: the
fingerprint deliberately spans data *and* configuration, because either changing invalidates a
baseline identically, and "corpus" was quietly hiding that. A terminology note was added to § 0 so the
distinction survives future edits.

Renames worth noting: env vars `ARRANGER_CORPUS_FINGERPRINT{,_MODE}` became
`ARRANGER_ENV_FINGERPRINT{,_MODE}`; § 5 is now "Dataset and case set"; R6 is now "test environment
fingerprint design". Considered and rejected: *snapshot* (collides with the Elasticsearch
snapshot/restore API), *baseline data* (collides with "baseline" meaning the stored previous run),
*golden dataset* ("gold" is already load-bearing for expected answers), *test set* (in ML that means
the labelled examples, which maps to the case set rather than the data).

Earlier entries in this log still use "corpus" as written at the time; not retroactively edited, since
this is a chronological record.

**Follow-up worth considering:** if these terms spread into the eval workspace's README and
`.env.schema`, add a line to `docs/concepts.md`'s vocabulary reference table, the same way
"settings" vs "configuration" was resolved there (`tech-debt.md:295`).

### Revision 9: `abstentionCorrectness` renamed and specified (2026-08-20)

Developer asked for a clearer name. The stronger argument turned out to be accuracy, not readability:
**"abstention" described only one of the four behaviours the metric scores.** Per the `prompts.ts`
taxonomy, Unanswerable means decline, but Ambiguous means ask a clarifying question, Improper means stay
conversational, and Answerable means proceed. The old name covered a quarter of the metric and implied it
was about refusing.

Renamed to **`responseTypeMatch`**, which parallels `outcomeMatch`: a comparison between the response
type the case called for and the response type observed. Answers column updated from "Declines, asks, or
chats when it should, per category" to "Answers, declines, asks, or chats, as the case requires" so all
four behaviours are visible. Considered and rejected: `questionTypeHandling` (closer to repo vocabulary
but "handling" is vaguer than "match"), `answerabilityMatch` (undersells the ask-vs-chat distinction),
`categoryMatch` ("category" alone says nothing about what is categorised).

**The follow-up question exposed a real gap:** § 3.1 named the taxonomy but never said how the metric is
computed, unlike every other metric in that section. Now specified, and the specification is better than
expected:

| Category | Deterministic expectation | Reads prose? |
| --- | --- | --- |
| Answerable | `execute_query` ran and `outcomeMatch` holds | No |
| Unanswerable | No `execute_query` at all | No |
| Ambiguous | No `execute_query`, and the final turn asks a question | One weak heuristic |
| Improper | No tool calls whatsoever, not even `list_catalogues` | No |

**Three of four categories are scored by what the model did _not_ call**, so this rides the same
trajectory instrumentation as the rest of § 3.1 and stays honestly in the deterministic column. Improper
is the strictest and cheapest row, since `prompts.ts` forbids loading catalogue metadata on an improper
turn, making any tool call a failure. Ambiguous is the only soft spot: "did not query" cannot separate a
good clarifying question from a flat refusal, so the cheap check is whether the final turn ends in a
question and the quality of the options presented is deferred to `answerQuality`.

Purpose recorded explicitly, since it was only implied before: it is the sole guard against the
degenerate optimum (a suite of only answerable cases rewards a server that makes the model always query,
and a query against a false premise looks like a pass everywhere else), and the sole test of behaviour
the server already ships instructions for (`instructions.ts` on asking rather than silently choosing;
`prompts.ts` output formats for all three negative cases).

**Still open:** whether to rename the § 5.3 case-format field `category` to `questionType` so the pair
reads as a matched set. Offered, not yet answered.

### Revision 14: Pass B dropped, consistency rebuilt on paraphrase variance (2026-08-22)

Developer challenged the premise behind Pass B: why would a researcher-facing deployment ever run at
temperature above 0? Query translation has one right answer, the server's whole design is variance
reduction, and § 3.3 already argued inconsistency is a correctness failure here. The plan asserted "the
sampling configuration the deployment will actually use" without ever establishing what that was.

Decision taken: **we control the client and greedy is fine.** So Pass B is gone, sampling is greedy
everywhere, and the consistency group is rebuilt on paraphrase variance.

**Why this is a better suite, not just a smaller one.** With greedy sampling, repeated identical sessions
are nearly redundant, so the old consistency metrics were measuring something the deployment would not
experience. Real researchers do not ask the identical string twice: one asks "kidney cancer patients over
60", the next asks "patients aged 60+ with renal carcinoma". Robustness to phrasing is the version of
consistency that matters, and it is cheaper: every phrasing is *also* a distinct test of the surface, so
the runs buy coverage and a consistency signal at once, where repeated sessions bought only the latter.

**Terminology added to § 0:** an **intent** is one thing a researcher wants to know; a **phrasing** is one
way of asking it. A case is an intent plus its phrasings, all sharing one set of expectations, which is
what makes disagreement between them meaningful.

**Metric change:** `pass^k` → **`paraphraseRobustness`** (share of intents where every phrasing
succeeded). `answerDispersion` survives with its definition shifted from across-sessions to
across-phrasings, and it becomes the sharper of the two, since it catches two wordings that both look
answered and return different counts. Star count still seven. The success predicate established in
revision 12 carries over unchanged, now applied per phrasing.

**Structural edits:**

- § 4.1 "The two passes" → "One pass, greedy", stating what the choice buys (no sampling variance, one
  run per phrasing, every run comparable) and what it costs (blind to sampling clients), with an explicit
  pointer that the trade should be revisited if the deployment ever includes clients we do not control.
- § 4.2 now establishes **two** numbers instead of one, and the first is new: how stable greedy actually
  is, run one phrasing 20 times. **This validates the premise the single-pass design rests on**, so R3
  leads with it. If repeated runs disagree materially, the repeat-count machinery has to come back.
- § 3.7 "Sample size for consistency" → "How many phrasings per intent": three to five, and a paragraph
  on the fact that they must be *chosen* rather than randomly reworded. Clinical versus colloquial
  vocabulary, range versus threshold, explicit field name versus description, terse versus full sentence.
  Synonym-swapping one sentence tests nothing.
- § 5.3 case format now keys on `intent` with a `phrasings` array replacing the single `prompt`.
- § 7: `EVAL_PASS` and `EVAL_SESSIONS` gone; `EVAL_REPEATS` (default 1, above 1 only for the stability
  check) and `EVAL_ROBUSTNESS_SUBSET` added; `LLM_SEED_BASE` → `LLM_SEED`; sampling vars annotated as
  recorded-to-detect-deviation rather than swept.
- § 4.3 gained a reading rule worth having: a change that moves the mean without moving
  `paraphraseRobustness` fixed one wording; the reverse made the server less wording-sensitive. Different
  results, easily conflated.
- Cadence in Phase 5 and § 9.1 reworked from nightly-greedy/weekly-sampled to nightly-single-phrasing /
  weekly-full-robustness-subset.
- § 10 risk rows for variance and run time updated to match.

Verified: zero occurrences of Pass A, Pass B, `pass^k`, EVAL_PASS, EVAL_SESSIONS, or LLM_SEED_BASE; all
`§ N.N` references resolve; seven stars intact.

**Open question deliberately left in § 4.1:** if the deployment story ever includes clients the team does
not control, sampling stops being ours to fix and Pass B has to come back. Recorded as a trade rather
than a settled fact.
