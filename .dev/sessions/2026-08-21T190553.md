Answered a set of SQON-to-Elasticsearch compilation questions for the Usher session, by execution rather than by reading, since a design decision on their side turned on the answers. No code changed.

- Established the semantics of `not-in` versus `some-not-in`, now a canonical `tech-debt.md` entry. On a flat field the two emit **byte-identical** Elasticsearch, so the distinction is a no-op there. On a nested field they diverge because one places `must_not` inside the `nested` wrapper and the other outside, with the result that **each operator behaves like the other's name**: `not-in` means "there exists a nested object whose value is not in the list", and `some-not-in` means "no nested object has a value in the list". A filter author choosing between them by name gets the opposite quantifier, and half the time in the permissive direction.
- Checked whether any of this was already documented, and it is, inverted. `docs/reference/03-building-sqon-queries.md:53-56` is the published "Choosing an operator" table, and its two rows for these operators describe each other's behaviour: `not-in` as "does not match any of these values" (true on a flat field, false on a nested one) and `some-not-in` as "at least one nested item is excluded" (the opposite of what it does, and on a flat field it has no per-item behaviour at all). A reader using that table to express "at least one item is excluded" picks the operator meaning "none are included", which for an authorization predicate is the permissive direction. Raises the entry's severity and changes its fix: correcting the table comes before documenting the idiom, because a wrong operator table is worse than a missing one.
- **Second confirmed instance of one pattern**, worth naming rather than filing twice: Arranger's reference documentation describes SQON by what an operator's name suggests rather than by what the compiler emits, and both known instances are on the access-control path and err permissive. The first was the `graphql-router` README documenting a server-side filter with `field` where SQON requires `fieldName`, compiling to a null clause that restricts nothing. Two of the four membership rows in that table are now known wrong, which is an argument for checking the remainder against emitted queries rather than trusting untested entries.
- The useful half of that finding: **subset containment is expressible in a single clause**, as `not` of `not-in`, which reads as "there is no value outside my list, therefore every value is inside it". That is the universal quantification an authorization filter needs, and it is linear in the number of grants rather than exponential, which settles the additive-versus-subtractive question the Usher session was blocked on. It works **only on a nested field**: on a flat field the same expression double-negates to plain `in`, which on a multi-valued field is existential rather than universal, silently the wrong quantifier and in the permissive direction.
- Second canonical entry from the same session: **a wrong or missing `nestedFieldNames` silently produces a flat filter against a nested mapping**, which matches nothing. That is fail-closed for a positive filter and fail-open for a negated one, and an exclusion-shaped access filter is the negated case. Whether a `nested` query is emitted depends entirely on that argument rather than on the field name's shape, which makes its correctness part of the enforcement surface rather than query-builder detail.
- Confirmed two assertions the Usher session had recorded from schema reading rather than from this compiler, both of which hold: an empty combination (`and`, `or`, or `not` with empty content) passes through as an empty bool clause and matches everything, and `in` with an empty value array emits a `terms` with an empty array and matches nothing. Noted that `in []` is consequently the only fail-closed encoding of "entitled to nothing" in the set, since negating it inverts to match-all.
- Corrected shapes previously given to that session for the empty-combination cases. Both versions are right in their own context: the earlier ones came through `compileFilter`, which wraps the client and server filters into an `and` before compiling, while these are what `buildQuery` emits on the bare SQON. Flagged which is which so anything already quoted can be scoped rather than discarded.
- The consumer worked out what the inverted table would have cost them, and it is now the entry's strongest evidence: `not(some-not-in(categories, held))` reduces to "at least one category is granted", so a record tagged `[general, indigenous]` against a principal holding only `[general]` returns the indigenous data. Precisely the scenario their requirement exists to prevent. That converts the finding from "the table is wrong" into "the table converted a correct intent into a silent over-disclosure for a real consumer", which is a different and better severity argument than anything available from reading the table.
- Verified `in` on request and recorded a caveat larger than the answer. Nested `in` is doubly existential (a `nested` query matches when at least one object satisfies it, `terms` matches when at least one value does), which is safe for a single-valued identifier. But **the emitted query is identical whether a field is single-valued or multi-valued**, because Elasticsearch has no separate array type and the mapping does not distinguish them. So an identifier that becomes multi-valued through an indexing or mapping change silently widens every filter referencing it, with no code change and no diff to review. Filed alongside the `nestedFieldNames` finding as one class: **the enforcement behaviour of a correct clause depends on index-side facts the query cannot express**, making them assertions a deployment must guarantee rather than properties the filter establishes.
- Recorded a cross-boundary variant of the same defect class, reported by the consumer from a different repo: "Lyric fails secure on empty SQON combinations" is a property of `sqon-builder` plus drizzle rather than of the SQON layer, so it inverts if Lyric migrates to `@overture-stack/sqon`. The operator table misattributes semantics to a name; that misattributes a guarantee to a package. Both are invisible until the thing they depend on moves, and neither errors when it does. Added to the conformance-corpus constraints in `arranger-auth/roadmap.md` as a third format-level requirement, since a corpus recording only outcomes would go green straight through the migration that breaks it.
- Recorded a confidence boundary rather than eliding it: everything above is emitted query structure, verified locally. That empty bool clauses match all documents is standard Elasticsearch semantics rather than something verified against a live cluster here, and the related open question of what a cluster does with a `null` inside `must` is still unresolved. Flagged as deserving one query against the integration cluster if a decision turns on it.
