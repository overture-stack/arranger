Reviewed two peer sessions' feedback on `.dev/docs/mcp-platform-testing.md` and applied the approved subset. Seven items: one closed with no change after verification, one accepted in substance with a different remedy than proposed, five accepted as written. Plan document only; no code changed.

- **The `execute_query` approval gate cannot be bypassed by the model, verified by reading the path rather than assumed.** `confirmExecution` runs unconditionally inside the tool handler and the handler returns before `client.executeQuery` on a decline, so no argument, phrasing, or retry reaches Arranger without an accepted elicitation. That closed the item, but the coverage is narrower than the slogan: a client that does not advertise `elicitation` gets no gate at all, every other tool and all three introspection resources reach Arranger ungated (including the two introspection calls inside `execute_query`, which precede confirmation), a decline is not remembered so the model can re-prompt indefinitely, and the confirmation message embeds `JSON.stringify(variables)` whose SQON values are unvalidated beyond type shape, so the prompt's content is partly model-controlled even though its control flow is not. None of that is eval material; it is tech-debt shaped and is not yet logged.
- **Declined the statistical methods proposed for §5.3.6 while accepting the critique that prompted them.** The invented "three-point move" figure is gone and the minimum detectable effect now defers to R3, which exists to measure the noise floor. But correlation, t-tests, and ANOVA would have been a worse replacement: the outcome metrics are per-case binary results paired on a fixed case set, so the fitting methods are the paired ones the plan already named. Replacing one unearned specific with three inapplicable ones is not an improvement, and the general lesson is that the defect was a threshold-shaped number about a quantity a spike exists to measure, not specificity as such.
- **Corrected the peer's fingerprint reasoning while accepting its conclusion.** They framed keeping the query-derived signals as a trade-off against R6's "not so sensitive that a restart trips them". A document count and an aggregation checksum over a frozen index do not move on a restart; the signal that does is the introspection hash, because `buildCatalogueIntrospectionBody` stamps a fresh `generatedAt` on every router construction and the payload carries catalogue `status`. So R6's deliverable is a canonicalization rule for the payload, not a sensitivity trade-off, and the apparent conflict disappears. Their four-signal split moved into §4.1 as a diagnosis table, which is where it earns its keep: a server-side filter and a reindex both abort the run, and the operator needs the abort message to say which.
- **`params` guard: each parameter voids exactly the sub-assertion it can move.** `aggregationsFilterThemselves` and `includeMissing` void buckets; `first` and `offset` void the primary-key set; `total` survives all four. The `first`/`offset` half was not in the feedback and is arguably the worse exposure, since `outcomeMatch` asserts an exact primary-key set and a "show me a few examples" phrasing invites the model to override a default of 20. Kept it out of `forbidden` deliberately: those are model behaviours mapped onto the "Never guess" rules, choosing a different `first` is not misbehaviour, and scoring it there would inflate a starred metric and raise `answerDispersion` with nothing misunderstood.
- **Tokenizer pinned separately from the served model, and a mismatch reports as a required re-baseline rather than a budget breach.** The part not in the feedback: Phase 5 runs the token gate with no model server and loads a tokenizer locally, while L2 reads `prompt_tokens` from the serving stack, so the two paths can be in different units with nothing requiring otherwise. A gate whose unit comes from outside the repository needs an identity assertion before the comparison, or it fails on an empty diff, which §1.3 already argues is how a gate gets disabled.
- **"Human as a judge" is now the explicit framing, not "hand labels".** R4 has a human grade the answers first, those grades are committed as a fixture, and any change to the rubric, judge prompt, or `JUDGE_MODEL` re-runs the agreement check against them. Agreement is Cohen's kappa rather than percent agreement, and the kappa is recorded in the manifest so a judge scoring against a stale human control is visible in the baseline. The gap this closes is that R4 validated one configuration and then silently covered every later one.
- **One rule now stated in §0 covering three items at once:** if a value can change a case's expected answer it is pinned in the manifest, recorded on the case, or guarded at scoring, and if it can be none of the three it is an open question rather than an assumption. The principal, the server-side filter, and the model-settable `execute_query` parameters are the same defect three times, differing only in who sets the value.
- **Recorded the single-anonymous-principal assumption**, which was the load-bearing item. The MCP server forwards no identity, so `getServerSideFilter` computes one filter for every session and every expectation in the suite is derived for a caller with no restrictions. Pinned as an operator declaration in §2 rather than a hash, since the callback is not readable over HTTP, with detection left to the query-derived signals. §4.2 records why there is no principal field yet and that the eventual shape is a run-matrix axis like `tiers` rather than a case-level scalar, and cross-references the shared conformance corpus, whose "principal P can or cannot see record R" form is what this suite would have to interoperate with. §5.4.1 now states that `MCP_API_KEY` authenticates the transport without creating a principal, and that a single service credential would make the MCP server a confused deputy.

Open threads, none logged in `tech-debt.md` yet and all surfaced by this review rather than by the plan:

- `meta.authFiltered` is hardcoded `false as const` in `buildCatalogueIntrospection.ts`, with a test pinning the literal, while `docs/reference/05-introspection.md` documents it as reporting whether a server-side filter was active. The introspection body is also computed once at router construction with the request ignored, so it cannot report per-caller state even in principle.
- The `execute_query` elicitation prompt shows the query the MCP server sends, not the one Arranger runs, since the server-side filter is composed afterwards. Harmless while no filter is configured; misleading the moment one is.
- `phase-0-audit.md`'s P0-16 still claims `execute_query` inherits the aggregation `global` escape. That half is stale: `resolveAggregations` now compiles `serverSideQuery` separately and `buildAggregations` re-applies it. The identity half of P0-16 stands.
