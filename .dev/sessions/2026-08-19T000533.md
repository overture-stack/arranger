- Corrected a claim made about this repo's own code earlier in the session, which is recorded in full at `arranger-auth/usher-plugin.md` § Consequences of the per-submission access model and `arranger-auth/design.md` § A positive case. Saved-set expansion was asserted to need a read-time access re-check on the reasoning that a persisted ID list can be replayed after those records become restricted. Verified against the code and it is wrong: `resolveAggregations.ts:91` expands `set_id:` into the *client* filter with `:99` composing the server-side filter over the result, and `buildQuery/index.js:217` turns `set_id:` into an ES terms-lookup clause on the same side, so stored IDs can only narrow a result and never widen it.
- Kept the correction as a design artifact rather than deleting it. Sets are the one in-repo case of the composition seam working rather than failing: a mechanism that looks like it should be able to smuggle IDs past the access filter cannot, without anyone having considered sets and access control together, which is the property a seam provides and a convention does not. Every other example in `design.md` is a call site that composed nothing.
- The developer corrected the read-authorization finding's premise: today's fully-open iMS data is a production snapshot, not the target model, with per-submission access levels planned at submission time or afterwards. Consequences for this repo are in `arranger-auth/usher-plugin.md` § Consequences of the per-submission access model: enforcement is required at both the submission-service and Arranger layers, and access levels being mutable creates a window during which this repo serves a stale access decision until Maestro reindexes.
- Proposed a shared conformance corpus as the mechanism that keeps two independently-implemented enforcement layers agreeing, since dual-layer enforcement is the same convention-rather-than-seam problem promoted to platform scale, and both services currently have zero tests of their enforcement paths so neither has a suite to retrofit. Taken to the developer by the submission service as a cross-repo commitment. If adopted, `arranger-auth/roadmap.md` P0-0 should adopt it rather than duplicate it.
