`query_arranger` now sends the SQON cheat sheet inline instead of the raw JSON Schema as an embedded resource.

- Cause: `prompts.ts` was sending `JSON.stringify(sqon)`, the validation artifact, while `SQON_CHEAT_SHEET` (the generation guide) sat in a tool the prompt's workflow never mentioned. Separately, `type: 'resource'` is a portability hazard: minimal clients handle only `type: 'text'` and silently drop it, leaving the model told a grammar exists that it cannot see.
- Considered pulling the grammar via a `get_sqon_schema` call instead and rejected it: grammar is needed on every Answerable turn, so pulling costs a round trip, is contingent on the model choosing to call the tool, and lands the text in `messages` after the cache breakpoint, where it is re-billed per goal rather than sitting in the cached prefix.
- New `apps/mcp-server/src/mcp/sqonCheatSheet.ts`: `SQON_CHEAT_SHEET` extracted from `tools.ts` byte-identical (3,775 chars, moved programmatically). One line inside the literal that read "in this tool's structuredContent" now names `get_sqon_schema`, since the text is no longer tool-only. `tools.ts` imports it; `get_sqon_schema` output is unchanged.
- `prompts.ts`: second message is now `type: 'text'` carrying the cheat sheet, kept as a distinct message so a host folding it into a `system` parameter keeps a clean seam. `## SQON grammar` rewritten to point at the next message. `Promise.all` collapsed to one `getServerIntrospection()` call, so `prompts/get` makes one Arranger call instead of two and no longer breaks if the SQON endpoint is down. `SQON_RESOURCE_URI` and `JSON_MIME` deleted as dead; `resources.ts` uses its own literal, so the `arranger://introspection/sqon` resource is still registered.
- Verified: `tsc --noEmit` clean, `apps/mcp-server` unit suite 71/71, eslint and prettier clean. `integration-tests/mcp-server` was run this session (local ES was up, unlike prior sessions): 45/45.
- Held deliberately: `execute_query`'s description still mandates calling `get_sqon_schema`. Redundant on the prompt path now, but it is what drives correct behaviour for tools-only clients that never reach the prompt.
- Worth knowing for future MCP work: most local-model clients never reach prompts at all. LM Studio's MCP support is tools-first with no prompts picker, Ollama has no MCP client of its own, and `mcpo` (Open WebUI) flattens MCP to tool endpoints, dropping prompts and resources. Goose, LibreChat, and Continue do implement prompts. For those tools-only clients the tool descriptions are the real prompt, and neither confirmation gate fires: `confirmExecution` returns `true` without the elicitation capability, and the prompt's "wait for confirmation" is a request to the model, not a constraint.
- Logged tech debt: `SQON_CHEAT_SHEET` now has two consumers, so retiring it once `build_sqon` ships is a two-site decision. Inlining it into the prompt is the same "schema in the prompt on every request" pattern `build_sqon` removes; it is a net reduction against what the prompt sent before, but not the destination. Entry also flags sequencing against the MCP surface unification follow-on under **Deprecate `sqon-builder`**: if `build_sqon` lands first, deriving the cheat sheet from `getSqonFieldOperatorDetails()` may be moot.
- `/docs` gap: `query_arranger` is undocumented. `docs/usage/06-ai-and-automation.md` lists tools and resources but has no prompts section, so the server's only prompt is invisible to integrators. Predates this change, but this session touched the prompt's content. Its resource list at line 39 is still accurate.

**Server-level `instructions` on the MCP server.**

- New `apps/mcp-server/src/mcp/instructions.ts`: `SERVER_INSTRUCTIONS`, wired as the second `McpServer` constructor argument in `server.ts`. Sections: what the server is, "Never guess" (catalogue names, field names, SQON syntax, each paired with the tool that supplies it), the four-step call order, and notes on validation, the elicitation gate, `query_arranger`, and the introspection resources.
- Why here rather than only in tool descriptions: `instructions` ships in the `initialize` result and hosts typically fold it into the system prompt, so it is the only guidance the model holds _before_ it picks a first tool. Tool descriptions are read once a tool is already a candidate, which is too late to establish discovery-before-query. The two surfaces overlap deliberately for clients that drop `instructions`.
- Kept static rather than rendering live catalogue names into it. `createMcpServer` is synchronous and runs once per session in `createHttpApp`, so a dynamic prefix would cost an Arranger round trip per session, and a cached catalogue list in the system prompt is exactly the stale source the "call `list_catalogues`" rule exists to displace.
- Resolved a wording tension rather than leaving it: step 3 mandates `get_sqon_schema`, but `query_arranger` already sends the cheat sheet inline. The notes section says so explicitly, so the prompt path is not told to make a redundant call. Same tension as the `execute_query` description held above, now stated instead of implied.
