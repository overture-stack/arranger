The Usher adapter's branch is rebased onto main's GraphQL error rule, download route rules, loopback route tests and whole-day date reading, each of its commits carrying only what main lacks.

- `modules/usher-adapter/src/conditionFields.ts`, `integration-tests/server/harness/categoryChecker.ts`: a date alone is accepted again as a single range bound in a category condition, covering its whole UTC day, since the GraphQL router now reads one that way on every date field; the checker models it so.
- `modules/graphql-router/src/indexProbe.ts`, `modules/usher-adapter/src/indexChecks.ts`: the index probe counts, in one search with no script, the records holding a field and the values they hold in it, and the adapter refuses a catalogue whose resource field holds more values than records, saying some records hold more than one value. The search engine role no longer needs inline scripts (`modules/usher-adapter/README.md`, `docs/reference/07-feature-flags.md`).
- `modules/graphql-router/README.md`, `CHANGELOG.md`: the `onIndexMapping` hook's second argument, the `IndexProbe`, and its three questions.
- `modules/graphql-router/src/accessControl/AccessControlError.ts`, `filterCallback.ts`, `graphqlRoutes.ts`, `download/index.js`, `network/resolvers/aggregations.ts`: a filter callback may throw `AccessControlDeniedError`, given the catalogue and a kind (`no-access`, `access-too-broad`, `misconfigured`), to deny a read its catalogue before any search. Every read path answers with the GraphQL router's fixed text for the kind, naming the catalogue: `ACCESS_ENFORCEMENT_DENIED` and `403` for `no-access`, `INTERNAL_SERVER_ERROR` and `500` otherwise, logged as `access_enforcement.denial_answered` at info or at error.
- `modules/usher-adapter/src/createUsherAccessControl.ts`: a deny throws that denial, `no-grants` as `no-access`, `filter-limit` as `access-too-broad`, and the configuration reasons, the bridge's own fault and a catalogue missing from the results as `misconfigured`; `access_enforcement.denied` keeps the reason.
- `apps/search-server/src/server.accessControl.test.ts`: every principal is given the same catalogue listing and introspection, without the bridge being asked who is asking, so naming a denied catalogue names only one already listed.
- `.dev/docs/arranger-auth/usher-adapter.md`, `modules/usher-adapter/README.md`, `modules/graphql-router/README.md`, `docs/reference/07-feature-flags.md`, `CHANGELOG.md`: a denial is ambiguous below the catalogue and named at the catalogue, with the reason, kind, code and status of each deny.
- `modules/graphql-router/src/sets/`, `schema/`, `mapping/resolveSets.js`, `mapping/resolveAggregations.ts`, `config/utils/index.ts`, `router.ts`: the router's `getRequester` states who made a request, a principal with its id, an anonymous request or a suspended principal, and any other answer refuses the request as a configuration failure. Each saved set records how it was saved as `attribution`: by a principal, anonymously, or unattributed where the router has no `getRequester`, the client's `userId` kept as data. `saveSet` refuses a suspended principal, writing nothing; the sets connection lists a principal their own sets, the unattributed ones and the sets a filter names by `setId`, which is the only way an anonymous set is reached, reading a set with no mark as unattributed, and its aggregations count the same sets; a set's `sqon` goes to the principal who saved it, or to every reader for a set no principal owns. In every deployment, no reader is given a set's `userId`, which the sets connection and `saveSet` answer as `null`; a field a reader may be given other than as stored, `userId` always, `ids` and `size` under a filter callback and `sqon` under `getRequester`, is no filter or sort key and aggregates to `null`, nor is `sqon`, which the sets index stores and never indexes (`usableSetFieldsOf`), and a filter or sort naming anything but a field the sets index indexes and every reader is given as stored is refused with `BAD_USER_INPUT`, wherever in the filter it appears, its message listing the fields it may use. Under a filter callback, a set's `ids` and `size` are checked against the reader's filter in chunks and narrowed where it holds records the reader may not see, 20 sets a page. At startup the router adds `attribution` as a keyword to an existing sets index, warning `sets.index_mapping_outdated` where it cannot, and each save reads the mapping again (`sets/setsIndexMapping.ts`): where it lacks `attribution` as a keyword, a set saved without `getRequester` is stored unmarked, and under `getRequester` the save is refused, storing nothing. Without `getRequester`, sets have no owners, as in 3.0.x, logged as `sets.unowned` at info beside a callback.
- `modules/usher-adapter/src/requester.ts`, `apps/search-server/src/usher.ts`, `arrangerRoutes.ts`, `configs/`: the adapter's `requesterOf`, the subject the bridge confirmed, a suspended principal or an anonymous request, reaches every catalogue's router as `getRequester`, and a host passing its own `filters` can pass one beside them.
- `integration-tests/server/test/accessParity.test.ts`, `savedSetAccess.test.ts`, `harness/parity.ts`: a set used as a filter answers only the reader's permitted records on every read path, network search's local node included; each refused filter, sort and withheld aggregation under each router configuration, and a filter on a path within `sqon` and a sort on it refused with and without `getRequester`; the sets connection's attribution, the anonymous and unmarked sets, a suspended save, listing, narrowing, paging and aggregations, with and without `getRequester`, and with no callback, on both engines. `integration-tests/server/test/manageSets.js` retrieves the set it saved by its id, under the host's filter callback with no `getRequester`. `setsIndexMapping.test.ts` finds `attribution` mapped as a keyword in a created index and added to an earlier one, a set saved without it where an index maps it otherwise, and, in an index recreated after startup with a strict mapping lacking it, a set saved unmarked without `getRequester` and refused under it.
- `modules/graphql-router/src/mapping/createConnectionResolvers.ts`, `resolveHits.js`, `searchClient/types.ts`: the worker pool parameter typed as the class, the hits resolver's arguments as optional, and the search client's index parameters given `id` and `refresh`.
- `docs/reference/08-Migration/v3.1.md`: an existing sets index gains `attribution`, by the router given the privilege or by hand; a sets index the deployment creates itself carries `attribution` and `sqon` in its own mapping, with saved sets enabled, or is left to the router; a saved set's `userId` is stored, never answered; and a filter or sort on saved sets may name only the fields given alike to every reader.
