Made `isArray` reach consumers, corrected several documents describing behaviour that no longer ships, fixed one unlogged defect in `buildQuery`, and then audited the result for test and documentation coverage. The audit found three shipped behaviours with no documentation at all, an introspection reference describing a field shape the response no longer matches, and a test command covering six of the ten workspaces that have tests.

- **`isArray` now survives to the introspection response, and it did not before, including through the first attempt at this.** `buildFields` never passed it through, so a consumer had no way to know whether a field can hold more than one value. Adding the passthrough was not enough: `extendFields` defaulted it to `false` for every field, configured or not, so "the operator declared single-valued" and "nobody declared anything" arrived identical. The passthrough was inert for its stated purpose until that default changed. **A guard written against a condition the pipeline cannot produce reads as correct and tests as correct**, since the unit test constructing its own inputs is exactly the test that bypasses the collapsing layer.
- **The undeclared state is `null` rather than an omitted key, and the reason is about consumers rather than consistency.** An omitted key cannot distinguish "no declaration" from "this server predates the field", because both are absence. `null` present means the server sends `isArray` and nobody declared this field. That matters for a package consumed at a pinned version. `unit` in the same object had already settled this shape, defaulting to `null` and always emitting; the first attempt introduced a second shape for the same situation two lines apart.
- **`isArray` then shipped with no documentation anywhere**, in either `docs/` or the changelog, despite being the only signal a consumer has for field cardinality. The introspection reference was also wrong about the field shape in three further ways, two of them predating this work: it omitted `isArray`, described `unit` as absent when unset rather than always present as `null`, and named a `description` key under each field when `description` is the catalogue's own and fields carry none.
- **The cautious reading of `isArray` inverts between operators, so it cannot be factored into one shared helper.** Combining two `in` clauses on one field is only safe when the field is declared single-valued, which makes `false` the permitting state and `null` a refusal. An `all` clause is only satisfiable when the field can hold several values at once, which makes `true` the permitting state and `null` a refusal there instead. Both refuse on `null` and they permit on opposite values, so a helper meaning "treat `null` like `false`" is correct for one caller and inverted for the other. Recorded because the two consumers will sit in the same file.
- Corrected `docs/reference/03-building-sqon-queries.md` and `modules/sqon/README.md`, both describing reduction behaviour that changed. The merge rules were written per operator with `not` buried inside each line, which is how the range operators came to imply nothing about it; the universal rule now leads. The README's `matchNothing` guarantee was accurate and its justification was not, resting on leaves never being pruned, which was equally true while a same-field merge was destroying the value. **What actually holds it is an empty `terms` clause matching nothing in the search engine**, so the guarantee rests on engine semantics rather than on a reduction rule.
- **Unlogged defect, found while differentially testing reduction against a live cluster, now fixed: `buildQuery` collapsed double negation.** `not[not[X]]` compiled identically to `not[X]`, losing a negation level, verified against Elasticsearch returning the complement of the correct document set. Flattening a combination into a same-operator parent is associativity, which `and` and `or` have and `not` does not. `and[not[X]]` nested correctly, so it was specific to `not` directly inside `not`. No security consequence found: access-control filters compose as siblings under `and` rather than nesting negations. Fixed by excluding `not` from flattening, with regression tests confirmed to fail without the change.
- Two facts about this repo's own verification, both of which produced misleading passes before being noticed. `tsconfig.release.json` sets `noCheck`, so "the release build passes" is not evidence of anything and the checking config reports 53 errors it hides. And `modules/graphql-router/dist` carries 27 compiled `.test.js` files that the runner discovers, so every test in that package runs twice and a stale `dist` reports failures in code already fixed. The second is tracked as trimming published contents, which understates it: it is a test-reliability problem, not only a packaging one.
- **`npm run test:dev` runs six of the ten workspaces that have test scripts, and neither of the two needing a live search engine is among them.** Absent: `integration-tests/server` (98 tests), `integration-tests/mcp-server` (68), `modules/charts` (12), `modules/components` (59). A green `test:dev` therefore says nothing about 237 of 906 tests. **The membership follows no rule**, which is what makes it unfixable by addition: `integration-tests/import` is included while the other two `integration-tests/*` workspaces are not, so neither "fast", nor "no external dependency", nor "by directory" describes the set. Logged with a fix that splits by precondition (`test:unit` for suites needing nothing running, `test:integration` for the two reading `ES_HOST`), leaving `integration-tests/import` as the one real decision, since it needs a built `dist/` but no service and is a packaging check rather than either kind.
- **A green exit code and a summary of test counts are not the same evidence, and the counts were the unreliable half.** The two Jest workspaces report `Tests: N passed` while the node:test workspaces report `# tests N`, so a count collected by matching one format silently omits the other, reporting a subset as though it were the whole. The exit code covered what the count missed. This compounds the `dist` staleness above: the suites most exposed to a stale `dist` are among those `test:dev` omits, so the weakest verification path and the thinnest coverage coincide.
- **Two fixture documents share an `_id`, so `integration-tests/server` indexes three documents where the file declares four.** The loader passes `id: datum._id` to `esClient.index()`, making the fixture's `_id` the Elasticsearch document id; lines 5 and 45 of `model_centric_1.data.json` carry the same value, so the second silently overwrites the first. `model_centric_2.data.json` has the same duplication. Nothing fails or warns: aggregation, sort, and pagination tests run against a smaller set than the fixture reads as, and one document's field values are never exercised. Expect assertions calibrated against the collapsed set to change when it is fixed, which is the useful part.
- **`compileFilter` has no tests at all**, and it is where the incoming client SQON and the configured server-side filter are combined into the single SQON that gets compiled, so every read path depends on it: record queries, aggregations, the export route, and federated queries. Several existing entries already name its contract as the seam worth changing, meaning each of those changes would be made with no regression coverage underneath. Logged, along with the `esClient` option naming a `SearchClient` with no documented path from a real engine client to one, and `router.ts`'s mount order being load-bearing and unmarked in two places.
- Roadmap entry added for consolidating code sorting onto one tool. Three mechanisms currently order code and none covers object literals, which is where the ordering mistakes happen, and the property-ordering convention describes that failure exhaustively including the conditional-spread variant. Detail and the two open questions are in `.dev/roadmap.md`.

Added `description` to `getSqonFieldOperatorDetails()`'s return type in `modules/sqon`: `in` and `all` (and `not-in`/`some-not-in`) carried the same `valueType`, so nothing distinguished "matches any" from "requires every" for a reader choosing between them, including `build_sqon`'s own schema text. Every field operator now carries a one-clause statement of its meaning, matching the operator-selection table already in `docs/reference/03-building-sqon-queries.md`. Purely additive.

Added `fast-check` as a devDependency of `modules/sqon` (matching the version already used by `modules/types`) and a property-based test for `reduceSqon`: idempotency and semantic preservation (reducing a SQON never changes which documents it matches, checked against an independent evaluator) over a generated tree of `in`/`not-in`/`gt`/`gte`/`lt`/`lte` and `and`/`or`/`not`. Hand-picked cases had missed real defects that fuzzing caught immediately; this keeps that coverage in the suite going forward instead of as one-off scratch scripts.
