Responded to PR review on the MCP SDK v2 migration, fixing a defect that made one documented `MCP_HOST` value unserviceable and tightening the transport's configuration, error codes and introspection traffic.

- `apps/mcp-server/src/http/server.ts`: the request path resolves against a fixed base rather than `config.mcp.host`, which answered every request `500` under `MCP_HOST=::1`, since a bare IPv6 literal is not a valid URL authority. A bind address is now rendered for a URL through `hostAsUrlAuthority`, so the startup line is dialable
- `apps/mcp-server/.env.schema`: the Host and Origin allowlists carry `[::1]`, without which an IPv6 loopback bind is refused by the Host guard even once the path parses
- `apps/mcp-server/src/utils/config.ts`: a routable `MCP_HOST` requires `MCP_REQUEST_STATE_SECRET` at startup, matching the rule `MCP_ALLOWED_HOSTS` already carried. A generated per-process key is correct for one instance and fails every query confirmation across several, and that failure reads as a bug rather than as a missing variable. A loopback bind requires neither variable, and both refusals are reported together
- `apps/mcp-server/src/utils/config.ts`: the localhost allowlists come from the SDK's `localhostAllowedHostnames()` and `localhostAllowedOrigins()`, so they cannot drift from what its guards compare against. The two are called separately although they return the same list today
- `apps/mcp-server/scripts/generateSecret.mjs`, `apps/mcp-server/package.json`, `package.json`: `setup-env` creates `.env` and its signing key in one command, with `generate-secret` and `generate-secret:print` for an existing file and for a secrets manager. Keys come from `node:crypto` because `openssl` is absent from the `node:24-alpine` deploy image and from a stock Windows shell. A flag passed to a root `mcp-server:*` alias does not survive the `npm run -w` hop, so an alias that forwards one needs a trailing `--`
- `apps/mcp-server/src/http/errorCodes.ts`: `TRANSPORT_REJECTION` is the JSON-RPC code for a refusal made before any MCP message is read, matching the `-32000` the SDK answers for a disallowed Host, a non-POST verb and a non-JSON body. The wrong-path `404` and the oversized-body `413` moved onto it, so the endpoint classifies its own refusals the way the SDK classifies the ones it makes alongside them
- `apps/mcp-server/src/http/requestBody.ts`: `PARSE_ERROR` comes from the SDK rather than a repeated literal. No Content-Type check belongs here: `createMcpHandler` answers `415` before it classifies a body
- `apps/mcp-server/src/mcp/executeQueryTool.ts`: the declared client capabilities are schema-parsed rather than asserted, so a shape mismatch refuses instead of reading as elicitation support
- `apps/mcp-server/src/mcp/executeQueryTool.ts`: both Arranger introspection calls are issued together, saving a round trip of latency on entry and again on every confirmation re-entry. `allSettled` keeps the catalogue-not-configured message ahead of the failure an unknown `catalogueId` produces, at the cost of one wasted request on that path
- `apps/mcp-server/src/server.ts`: building an `McpServer` per request costs 0.28ms, so the SDK's per-instance schema-conversion cache is rebuilt each time. No cross-instance cache was added: the only public seam, `fromJsonSchema`, takes a JSON Schema validator and would replace this tool's Zod messages, which are what let a model correct its own arguments
- `apps/mcp-server/src/http/server.ts`: `handler.close()` still runs before `httpServer.close()`. Reversing it would park shutdown behind keep-alive connections draining, which is a worse trade than the fault response a request landing in that window receives
