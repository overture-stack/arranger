Reviewed [OHCRN/platform#1964](https://github.com/OHCRN/platform/pull/1964) (researcher-ui's migration from `sqon-builder`/`SQONType` to `@overture-stack/sqon`), which surfaced a real bug and led to a new `@overture-stack/sqon` export.

- Root-caused a review comment from the PR author: `SqonBuilder`'s single-item combination collapse (`reduceSqon`, ported from `sqon-builder`) breaks `SQONViewer`'s assumption that a `SqonNode`'s top-level `content` is always an array. Confirmed the exact crash (`sqonContent.map is not a function`) traces to `modules/components/src/SQONViewer/index.jsx:39`, which has no `Array.isArray` guard.
- Added `asCombination(node, op = 'and')` to `modules/sqon/src/builder/asCombination.ts`: wraps a node in a combination if it isn't already one, without ever unwrapping a single-item result the way builder methods do. Exported from the package root, documented in `README.md` and `docs/sqon-builder-absorption.md`, tested (6 cases), and noted in `CHANGELOG.md`. Not yet in a released version; a future rc round is needed before consumers can use it.
- Reviewed the full PR diff and found a second instance of the same class of bug the PR author hadn't caught: `removeFilter` in `apps/researcher-ui/src/utils/sqonHelpers.ts` was migrated to `SqonBuilder.and(filteredContent).toValue()`, which collapses to a bare leaf when exactly one filter remains after removal, directly contradicting its own adjacent code comment ("SQONViewer expects top-level to always have op: 'and' with content as array"). Drafted and the developer posted review comments identifying this, plus a correction to the developer's own earlier comment that had called the wrapping "unnecessary noise" before this was traced.
- Logged the underlying SQONViewer gap in `.dev/tech-debt.md` ("SQONViewer requires the top-level SqonNode to always be a combination; crashes on a bare leaf"): `index.jsx`'s render loop and several more call sites in `SQONViewer/utils.js` assume `.content` is always an array with no guard, while `removeSQON` in the same file already demonstrates the correct defensive pattern (checks `Array.isArray` before assuming array shape). Cross-referenced the existing "no rendering-level test coverage" entry, since fixing this needs the same test-first treatment as the sibling SQON-viewer bubble regression already logged there.

Documented, rather than hardcoded, why a restrictive `ALLOWED_CORS_ORIGINS` blocks GraphQL Playground/Sandbox when opened directly in a browser: appending Apollo's own Sandbox origin to the allowlist by default (in the chart or in code) would couple a security-relevant setting to an unrelated feature flag and hardcode a third-party origin that isn't guaranteed stable.

- `apps/search-server/.env.schema`, `apps/search-server/src/server.ts`: one-line pointers added at the CORS origin setting, matching each file's existing comment density.
- `docs/usage/08-feature-flags.md`: added the full explanation as prose after the "Optional functionality" table, the canonical place for it; the other two files just point here instead of repeating it.
