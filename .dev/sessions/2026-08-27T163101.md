Same field, same states, opposite safe value, because the two operators are unsatisfiable in opposite cardinality directions. A second vector shared the same root cause: the function took no `existingSqon` parameter, so an existing `all` leaf plus one new single-value clause on the same field bypassed it too.** Fixed by making the check collision-aware like `findInClauseCardinalityConflicts` already was: it now accumulates the deduplicated value set per field across every non-negated `all` clause and any existing unpivoted `all` leaf, and flags the field when that combined set exceeds one value. **A second review round confirmed the fix and flagged one deliberate boundary, not a defect.** The gate catches same-operator collisions (`all`/`all`, `in`/`in`) but not cross-operator ones: `all:a['X']` alongside `in:a['Y']` on a single-valued field is equally unsatisfiable, and neither function accumulates the other's operator. Confirmed directly (`addFilterClause` folding those two produces two sibling leaves, no merge, so nothing catches the collision). Agreed this should stay unfixed rather than chased: the general form covers every pair of clauses requiring different exact values of a single-valued field (`in`+`between`, `all`+`between`, and further), and catching all of them is a satisfiability checker, not a clause validator. Documented as a stated boundary in `.dev/docs/build-sqon-tool.md`'s design section instead, so a future reader who hits the `all`+`in` case reads a decision on record rather than concluding the gate is broken.

**A third finding, from SQON reviewing the same changeset independently, was a real gap in how both gates read `existingSqon`.** Both functions scanned it via `normalizeSqonNode` (alias canonicalization only), while `addFilterClause` reduces it fully via `SqonBuilder.from()` before folding. A same-field collision hiding inside a nested single-item group, `{op:'and', content:[{op:'and', content:[in:a['X']]}]}`, is invisible to the raw scan (its top-level child is a group, not a leaf) but becomes a genuine top-level sibling once reduced, exactly what the merge targets. Confirmed directly: `normalizeSqonNode` left that structure untouched; `SqonBuilder.from(...).toValue()` collapsed it to the bare leaf. Fixed by having `resolveExistingSqon` reduce via `SqonBuilder.from(parsed.data).toValue()` instead, so the gate and the fold see the same shape. Added a fifth end-to-end test reproducing the exact nested-group scenario through `build_sqon` itself, not just against the `SqonBuilder` primitive.

A companion fix in the same message: `types.ts`'s `isArray` widened from `.nullable()` to `.nullable().optional()`, so introspection from a server predating the field doesn't hard-fail catalogue resolution. Safe because both gates already treat `undefined` and `null` identically (only `=== true`/`=== false` branch explicitly).

**A fourth, unrelated defect surfaced while SQON was verifying the reduction fix was safe to make.** They correctly gated it on first extending `reduce.property.test.ts`'s meaning-preservation property to cover `all`, `some-not-in`, `between`, and `pivot` (previously asserted only for `in`/`not-in`/the range ops), and the extension failed on its first run: `deduplicateValues` ran on `between`'s fixed `[min, max]` pair as if it were a set of interchangeable options, so `between('age', [30, 30])` collapsed to one element and then failed the schema's own two-element requirement. **Confirmed live in the published package, not just this branch**: installed `@overture-stack/sqon@1.0.0-rc.5` fresh from npm in an isolated directory and reproduced both the collapse and the resulting `SqonSchema.safeParse` failure directly. Fixed in `modules/sqon/src/builder/reduce.ts` by excluding `between` from `deduplicateValues`. This is SQON's fix, not this branch's own work, but it is a real dependency of the reduction-order fix above, since that fix's safety rests on reduction being meaning-preserving for every operator the gate's `existingSqon` might carry.
