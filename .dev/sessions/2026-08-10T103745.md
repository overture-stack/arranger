Reviewed the test plan for the now-implemented `build_sqon` tool, then wrote the tests. The plan's four test items were all worth keeping; the review added three things it did not cover, one of which turned up a live bug.

Tests are written against the tool's registered surface rather than by widening exports: a fake `McpServer` captures the `(name, config, handler)` triple, inputs are parsed through the captured `inputSchema` exactly as the SDK parses them, and only then does the handler run against a stubbed `ArrangerClient`. That covers `resolveCatalogue`, `foldClauses`, and `normalizeRoot` end-to-end without exporting any of them, so the fold/normalize split stays an implementation detail. The plan's "fold-level tests assert a bare leaf root" line is therefore satisfied indirectly: the single-clause and empty-`existingSqon` cases both prove the fold produced a bare leaf, because the wrap is visible in the output.

- `apps/mcp-server/src/mcp/buildSqonTool.test.ts` (new, 56 tests): `BUILD_SQON_OPERATORS` (v1 set, withheld operators, and that every named operator actually exists in `getSqonFieldOperatorDetails`, since a typo there would silently drop a description line); `describeOperators`; input-schema accept/reject including operator aliases, text operators, `between` arity, and per-item error reporting across a batch; `resolveCatalogue` across all four cases plus a non-404 transport failure and an unparseable payload; fold shapes for `and`/`or`/negation/`between`/date bounds; `existingSqon` extension, alias normalization, empty-root, and the cross-catalogue rejection; and the response contract (output-schema conformance, text mirror, `isError`, summary wording, `clauseCount`/`filterCount`, and the merge note).
- `apps/mcp-server/src/arranger/clauseValidation.test.ts` (new, 23 tests): every branch of `validateClause`, both orderings that prove it stops at the first problem per clause, and multi-error batches with their `clauses[i]` indices.
- `apps/mcp-server/src/arranger/sqonSummary.test.ts` (new, 25 tests): every operator including the unreachable default branch, value quoting, display-name fallback, root vs nested bracketing, `not`, empty SQON, and `countFilterClauses`.
- `apps/mcp-server/src/mcp/tools.test.ts` (new, 13 tests): the coverage gap the plan missed. Tool names are literal strings in prose across four text surfaces with nothing linking them to the registration, so the test asserts that every `<verb>_<subject>` identifier appearing in `SERVER_INSTRUCTIONS`, `SQON_CHEAT_SHEET`, any tool description, any input-schema description, or the rendered `query_arranger` prompt resolves to a registered tool. Matching the shape rather than an allowlist is the point: an allowlist only ever confirms the names already written down.
- `apps/mcp-server/src/mcp/prompts.ts`: fixed `build_soqn` to `build_sqon` in the `query_arranger` confirmation step. Introduced with the `build_sqon` text-surface changes; the tool call would simply have failed for anyone following the prompt. Verified the new test fails on the typo before fixing it.
- `apps/mcp-server/src/arranger/validation.test.ts`: its introspection fixtures no longer typechecked against the current `IntrospectionResponse` (per-catalogue `status`/`error` and the server-wide aggregate `status`) or `SqonIntrospectionResponse` (`schema` is now `VersionedSqonJsonSchema`, not `Record<string, unknown>`). One measured correction to the plan's verified-behaviour table. It records "Input schema violation throws `McpError(InvalidParams)`, not a tool result". That is true inside the request handler, but the SDK converts it before it reaches the wire: the caller gets an ordinary `isError` result whose text is `Input validation error: Invalid arguments for tool build_sqon: ...` followed by the Zod issues, including the list of accepted operators. That is the better outcome, since a model can self-correct from it, but the table said the opposite and the first draft of the test asserted a rejection that never comes. Table corrected.
