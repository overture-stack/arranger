The Usher adapter's work for the category model begins, against a local draft of Usher's coming record registration, whose categories are named SQON conditions.

- `modules/usher-adapter/src/conditionFields.ts`: a startup check of every category condition against the catalogue's index mapping. Each field it names resolves through the mapping, multi-fields included, outside any nested mapping, as a keyword, date or numeric field, with ranges only on dates and numbers; SQON's operator aliases count as the operators they stand for. A date field names no format, or one built only from `strict_date_optional_time`, `date_optional_time` and `epoch_millis`. Each value a condition holds is one its field's type holds: a non-empty string on a keyword, a finite number on a numeric field, and on a date a full date or a full date-time to the millisecond on a real calendar day, and a date `between` lists the bound starting earlier first, so a condition holds only what the independent checker models. Not yet wired into startup, which waits for Usher's released type.
- `modules/usher-adapter/src/draftRegistration.ts`: the local draft of that registration type.
- `modules/graphql-router/src/download/index.test.js`: under a restricting filter, a client sqon of any shape exports no document outside it and is refused only in fixed text; a filter callback refusing an export for now is answered 503 in plain text with `Retry-After` before any search; a client leaving before the first row, or while a later page fails, ends only its own export.
- `integration-tests/server/test/usherAdapter.test.ts`: through the Usher adapter, a client filter under a principal's access returns exactly the records both permit, on every endpoint, and each refused export is plain text with `nosniff`.
- `.dev/tech-debt.md`: the export-formatter entry names the two column options still without tests.
- `modules/graphql-router/src/indexProbe.ts`, `router.ts`: the `onIndexMapping` hook also receives a probe of the catalogue's index, which compiles a condition as the router compiles its filters and asks the engine whether it accepts it on every shard, how many records it matches, and how many records hold several values in a field. Every count rejects when a shard fails, the search times out or the total is inexact, and a field inside a nested mapping is refused before the engine is asked.
- `integration-tests/server/harness/categoryChecker.ts`, `categoryFixture.ts`: an independent checker of which records a principal may see under the category model, written from its rules rather than from Arranger's compiler, with a fixture for parity tests: records in several categories, records missing a condition's field in each way, unmarked records, global and resource categories, dates timed inside a bound's day, and records of several resources.
- `modules/graphql-router/src/graphqlRoutes.ts`, `download/index.js`, `network/resolvers/aggregations.ts`: a filter callback's refusal to serve a request yet is answered with the router's fixed text, `ACCESS_CONTROL_UNAVAILABLE_MESSAGE`, on the GraphQL endpoint, the export route and each network node, keeping its code and `Retry-After`; the thrower's message is logged as `access_control.unavailable_answered`. `modules/usher-adapter/README.md` and `unavailableAnswer.ts` say the bridge's text reaches the log, not the client.
- `modules/usher-adapter/src/createUsherAccessControl.ts`, `indexChecks.ts`, `events.ts`, `verifyFields.ts`, `conditionFields.ts`: the adapter takes Usher's released category registration. `verify` is async and checks each catalogue in three steps, each only once the one before passed: Usher's registration format, the index mapping, and the index through the router's probe. The probe step refuses a resource field some record holds several values in, and a condition the engine refuses, logging the engine's explanation as `access_control.condition_refused` at error; it warns of a category matching no record as `access_control.category_matches_no_record`, counting a resource's own category within that resource; a check the engine fails to answer refuses the catalogue. Every deny reason matches nothing, and a new result kind fails to compile.
- `apps/search-server/src/server.ts`, `usher.ts`, `arrangerRoutes.ts`: each catalogue's probe reaches the adapter beside its mapping, verification is awaited before the bridge starts, and every stop of the bridge is awaited, a failed start rejecting with its own error once the stop settles.
- `modules/graphql-router/src/download/index.js`: a refused export request is logged at info, a client's ordinary mistake.
- `modules/usher-adapter/README.md`, `docs/reference/07-feature-flags.md`: what startup checks and refuses, its two events, and the search engine role's needs on each catalogue's index.
- `.dev/tech-debt.md`: the graceful-shutdown entry names the bridge's stop the server cannot yet wait for.
- `modules/usher-adapter/src/indexChecks.ts`, `apps/search-server/src/configs/fromEnv/usherBridgeEnv.ts`: a startup check the engine fails to answer logs its cause chain, the engine's report included, as `access_control.startup_check_failed` at error, beside the refusal. `ACCESS_CONTROL_FILTER_CLAUSE_LIMIT`, an optional positive integer, sets the bridge's `filterClauseLimit`, anything else refusing startup; the docs pair it with the engine's `indices.query.bool.max_clause_count`.
- Needed before this branch's local commits are pushed: `modules/usher-adapter` and `apps/search-server` import `@overture-stack/usher-types` and `@overture-stack/usher-express-bridge`, which neither declares and the lockfile does not hold, so a clean `npm ci` fails at import. Both are installed from tarballs with `--no-save` until they publish. The order: Usher's packages publish as a release candidate; then both workspaces declare them with caret ranges and the lockfile is regenerated.
- `integration-tests/server/test/categoryParity.test.ts`: each fixture principal's narrowing, rendered by Usher's `canonicalRecordNarrowing` and served as the GraphQL router's server-side filter, returns on both engines exactly the records, the total and the per-study counts the independent checker shows it, records holding several studies included, with each multi-study rule named; through the Usher adapter, the fixture's records of one study each pass startup verification and match the checker.
