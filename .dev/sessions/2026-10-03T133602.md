Filtering by a saved set selects the set's records on every read path, looked up in the catalogue's own sets index on Elasticsearch and OpenSearch alike.

- `modules/graphql-router/src/middleware/buildQuery/index.js` (`getSetFilter`), `graphqlRoutes.ts` and each read path: a `set_id:` value is looked up in the sets index the catalogue's type carries, naming no document type, and a set filter compiled without a sets index is refused; an export context built without the router gets the default sets index a catalogue with no sets configuration uses.
- `modules/graphql-router/src/mapping/`: the aggregation path's separate set resolution is deleted, so facets use the same compiled set filter as hits.
- `integration-tests/server/test/accessParity.test.ts`, `buildQuerySetId.test.js`, `buildAggregations/setFilters.test.js`, `getAllData.test.js`: the saved-set cells run against a catalogue's own sets index on both engines, under `in`, `not-in` and `some-not-in`; every facet-level filter looks a set up in that index; and the facet suite removes the sets index it creates.
- `.dev/tech-debt.md`: the entries this resolves are deleted, and the remaining saved-set entry narrows to owner binding and shared sets indices; `.dev/docs/search-engine-integration.md` describes the lookup and the `indices:data/read/get` it needs on the sets index.
- `.dev/docs/atlas/roadmap/sets-feature.md`: where a set lives once a query spans catalogues or network nodes, as an open question.
- `modules/graphql-router/src/middleware/buildAggregations/index.js`, `nestedFacetTermFilters.test.js`, `integration-tests/server/test/nestedFacets.test.ts`: a facet on a nested field applies a clause on a field nested deeper inside it through that level's own nested query, so it counts the items holding a matching deeper item, under `in` and `not-in` alike, on both layouts and both engines.
- `apps/search-server/src/configs/fromEnv/renamedEnvs.ts`, `localEnvs.ts` and their tests: the seven 3.0 names of renamed environment variables keep working as deprecated aliases, each warned about once at startup with a link to the migration guide pinned to the release tag; a 3.0 value means what 3.0 read it as, the 3.1 name wins when both are set to different values, and `DEBUG` counts only when it holds `true`; the five variables no longer read, `MAX_DOWNLOAD_ROWS` among them since 3.0 never applied it, warn that they have no effect; the CHANGELOG lists every rename, and the guide documents the aliases under stable anchors.
