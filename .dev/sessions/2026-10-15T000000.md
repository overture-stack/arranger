Decided the MCP host ships as a standalone desktop app rather than a web-hosted service, and designed its connection-authentication model for that shape.

- `.dev/docs/mcp-host-plan.md`: decided the UI ships as a standalone desktop app, not a web-hosted service, to avoid the DevOps and infrastructure burden a deployed website would add for operators. A future browser-served version, if ever built, is scoped to serve one session per user (a second tab cancels or blocks the first); design deferred until that work starts. Updated the architecture table, diagram, and component descriptions to match (an app renderer and main process over the framework's own IPC, not a browser and a server over a network transport). Added open questions on whether the renderer process is sandboxed against independent network access, on a second app launch being a second process rather than a second window, and on crash reporting having no mechanism yet despite a rule already requiring one.
- `.dev/docs/arranger-auth/mcp-host-connections.md`: scoped the whole document to targets with Usher enabled. Against a no-auth target, `apps/mcp-server` needs no identity from the host at all, matching the evaluation harness's existing pattern of running it locally with no credential. Documented the host's own sign-in as native-app OAuth: the system browser only, never the app's embedded webview; a public client with PKCE and no client secret; a loopback or private-use URI redirect; mandatory consent on the client, since a public client's ID can be presented by any app; sign-out revoking the refresh token at the identity provider, since deleting it locally alone leaves it valid there; and no back-channel logout for a desktop app, so a revoked session is only discovered at the next refresh, bounded by the realm's access-token lifetime. Decided per-person token storage is the OS keychain (Keychain, Credential Manager or DPAPI, Secret Service or the Freedesktop Portal Secret interface for a sandboxed Linux package), holding the person's own Overture refresh token alongside third-party ones. Documented the residual threat a keychain does not cover (another process running as the same user) and the Linux degraded-backend risk: when no keyring provider is running, storage must refuse to persist anything, keep the token in memory for that session only, tell the person why, and accept re-authentication at each launch as the cost of failing secure.
