# Session 2026-08-12

## search-server documentType route fallback

Investigated failing `apps/search-server/src/arrangerRoutes.test.ts` cases where `response.json()` threw on an HTML `<!DOCTYPE` response. Cause: `arrangerRoutes.ts` mounted literal catalogue IDs only, while tests expected the same documentType-to-catalogueId resolution already implemented for `/introspection/:catalogueId`. Requests like `/records/graphql` fell through to Express' default HTML 404 page when `records` was only a `documentType`, not a real catalogue ID.

Fix:

- `apps/search-server/src/arrangerRoutes.ts` now imports `findCatalogueByIdentifier`.
- In multiple-catalogue mode, after literal `/${catalogueId}` routers are mounted, a `/:catalogueIdentifier` fallback resolves unique `documentType` values to the real catalogue router.
- Literal catalogue IDs still win because they are mounted before the fallback.
- Ambiguous shared `documentType` values now return JSON `409` with `ambiguous_document_type` and the matching catalogue IDs.
- Unknown identifiers still fall through to 404.

Verification:

- Rebuilt `modules/graphql-router` and refreshed the package boundary after the known stale-`dist` issue surfaced.

- `npm run test -w apps/search-server`: 50 passing.
