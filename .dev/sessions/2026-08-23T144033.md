Settled the deny encoding for the Usher plugin by execution, at that session's request. The answer is recorded in `arranger-auth/usher-plugin.md`; the reusable finding is below. No code changed.

- **A deny filter expressed as a negated empty combination inverts to allow-everything under `reduceSqon`.** `{op:'not', content:[{op:'and', content:[]}]}` emits match-none raw, but the reducer strips the empty inner combination and leaves `not` with nothing to negate, emitting `{"bool":{"must_not":[]}}`, which is match-all. Composed against a client filter that is worse than it first appears: `AND(client, match-all)` reduces to the client's own unrestricted query, so the caller receives exactly what they asked for with no restriction applied.
- **The trap is that it is correct until someone normalizes it.** `reduceSqon` does not run anywhere in `graphql-router`'s compile path, confirmed by grep across the middleware and mapping trees, so the negation form works right up until the value passes through `SqonBuilder.from(x).toValue()` once. That is an ordinary thing to add later for normalization, and it would silently invert a security property. A correctness that depends on nobody normalizing a value is not a correctness worth relying on, which is the general form worth keeping.
- The leaf encoding `{op:'in', content:{fieldName, value:[]}}` survives raw, reduced, and composed, because combination-pruning does not reach a leaf. It is not a compromise chosen for lack of alternatives: **no field-free encoding exists, and that is structural.** Every leaf operator requires a `fieldName`, so any field-free form must be a combination, and combinations are exactly the category the reducer collapses.
- One case remains genuinely unresolved and was reported as such rather than guessed: `{op:'or', content:[]}` emits `{"bool":{"should":[]}}`, whose match semantics depend on whether Elasticsearch applies a default `minimum_should_match` of 1 to an empty `should` array. That decides match-none versus match-all and needs a live cluster, alongside the still-open question of what a cluster does with a `null` inside `must`.
- Corrected a generalization given to that session earlier: empty combinations were described as passing through as empty bool clauses that match all documents. That holds for `and` and is unverified for `or`, for the reason above. Narrowed rather than left standing, since a Usher decision could have rested on it.
- Declined a request that was not this session's to grant. A `matchNothing()` constructor belongs in `modules/sqon`, which now has its own registered owner, so it was routed there rather than actioned. Endorsed with one addition: the pinning test should assert the emitted Elasticsearch and that the value survives a builder round-trip unchanged, because a test on the SQON node shape alone would not have caught the failure above.
