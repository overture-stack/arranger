# Changelog

All notable changes to this project are documented here.

This file covers high-level release notes for the Arranger project as a whole. When Changesets is adopted (see roadmap Phase 3.1), individual packages will also gain their own `CHANGELOG.md` files generated automatically at publish time. This root file is maintained by hand and covers operator- and integrator-facing changes.

## [3.1.0] - Unreleased

### Breaking changes

- **`ENABLE_NETWORK_AGGREGATION` and `NETWORK_AGGREGATIONS` are no longer read**: configure network search per catalogue, in a `network.json` file beside its other configuration files. Setting either, or `ES_LOG`, `MAX_DOWNLOAD_ROWS` or `MAX_LIVE_VERSIONS`, which 3.0 never acted on, prints a `DeprecationWarning`, code `ARRANGER_ENV_UNREAD`, saying it has no effect and linking the [migration guide](docs/reference/08-Migration/v3.1.md#environment-variables-no-longer-read).
- **Boolean environment flags accept `true`/`1` and `false`/`0` only, trimmed and case-insensitive**: `1` and `0` are accepted as before, and a value padded with whitespace, as a templated Helm value or a `.env` line easily is, reads as written. A blank value means unset and takes the flag's default, so a blank `DISABLE_GRAPHQL_INTROSPECTION` under `NODE_ENV=production` now disables introspection; set it to `false` explicitly wherever introspection must stay on, such as on a network search remote. Any other value, `yes`, `no`, `on` and `off` included, is ignored: it logs a warning naming it, under the event `config.boolean_value_ignored`, and the flag's default applies. Every flag defaults to `false` except `DISABLE_GRAPHQL_INTROSPECTION` under `NODE_ENV=production`, so that is the one flag an ignored value can now turn on. Word pairs are left out on purpose, since `no` and `on` are one transposition apart and mean opposites. `stringToBool` from `@overture-stack/arranger-types/tools` applies the same rule, and also accepts the booleans `true` and `false` and the numbers `1` and `0`. `ENABLE_ACCESS_CONTROL` follows a stricter rule of its own, recorded under [Server](#server).
- **Numeric environment values keep an explicit `0`, and a blank one takes the default**: a blank or whitespace-only value counts as unset, and a value that is not a finite number logs a warning naming it and takes the default. `SERVER_PORT=0` now binds a free port the OS assigns, and the startup line reports that port, where it previously fell back to `5050`; `PING_MS=0` is likewise kept rather than replaced by `2200`. `GRAPHQL_MAX_ALIASES` or `GRAPHQL_MAX_DEPTH` set to whitespace only takes the router's default of 15 aliases or a depth of 7. Leave a variable unset for its default, or set the value meant.
- **Docker image `arranger-server` renamed to `arranger-search-server`**: Update `docker-compose.yml`, Helm values, and any deployment manifests.
- **`getServerSideFilter` must be a synchronous function that returns a filter for every request; `null` and `undefined` are no longer accepted as its result**: the callback's contract is now total. A callback returning nothing, or returning a filter that holds an empty combination anywhere, beside clauses or alone, or that holds an `all` with no values, which compiles to one, a range with no bound, a `not-in` or `some-not-in` that lost its value list, a clause naming no field (such as one keyed by `field` rather than `fieldName`), or an entry that is not a SQON node, is refused with an error instead of being treated as "no restriction", since an empty combination matches every document; so is one that throws or returns a promise. The refusal, logged on the server, names the empty combination by its operator and position. `arrangerRouter` rejects at construction a `getServerSideFilter` that is neither left out nor a non-async function, `null` included, naming what it received; `getGraphQLRoutes` and `createSchemasFromConfigs` require one and throw at build, even with `rethrowOnError: false`. A deployment that applies no access control leaves `getServerSideFilter` out and needs no change: the published router `1.0.0-rc.6` refused its exports, and this release serves them again. To allow one request without restricting it, return `includeEverything(context)`; the context argument is required, so a call to `getDefaultServerSideFilter()` with no argument, as earlier examples showed, no longer typechecks. To deny one, return a leaf that matches nothing, such as `SqonBuilder.matchNothing(fieldName).toValue()`.
- **`DISABLE_FILTERS` (`disableFilters`) leaves a filter written into the query itself out of the search query**: a request whose GraphQL variables carry `filters` or `sqon` is refused with `400`. A filter written as a literal argument in the query document is left out of the search query and of every facet, a bucket's `filter_by_term` included, and the request answers `200`. An export's `sqon` is left out the same way, and a saved set records no client filter. Clients that send inline filters to such a server should stop, or the operator should unset the flag; the server-side filter applies either way.
- **With `DISABLE_DOWNLOADS` (`disableDownloads`) set, the router's `/download` answers `404`**: it does so with a JSON error for every method and path beneath it. Remove the flag wherever downloads should stay available. It gates the router's own route only, so an integration serving its own export route through `getAllData` or `dataStream` should apply it there too.
- **Download requests are validated before any output, one file per request**: `/download` takes `params` as one form field holding JSON, and `dataStream` validates the same object itself, so an integration can pass the client's object whole. `files` must hold exactly one file object: this version exports one file per request, so a client wanting several sends one request for each. The file's fields are read by name, `sqon`, `columns`, `sort`, `fileName`, `fileType`, `maxRows`, `chunkSize`, `uniqueBy` and `valueWhenEmpty`, and anything else it carries is ignored. `chunkSize` must be a positive integer and `maxRows` a non-negative integer, both as JSON numbers; `fileType` is `tsv` or `json`, where absent, `null` or empty names none, and `tsv` applies when nothing names one; `columns` is a non-empty array of column objects; `sort` is an array of entries, each naming a `fieldName` and an `order` of `asc` or `desc`; `fileName` is a well-formed string, and `uniqueBy` and `valueWhenEmpty` are strings. The top-level `chunkSize`, `fileName` and `fileType` follow the same rules. A request breaking a rule is refused before any search runs. `getAllData` holds its `chunkSize` and `sort` to the same rules, and rejects with `InvalidExportRequestError` before any search when either breaks them or its `sqon` cannot be compiled. `/download` answers every failure from reading `params` onward as plain text. An invalid request gets `400` and the rule it broke, a fixed text naming the field at fault and never a value the request carried, and, when its filter cannot be compiled, the SQON rule it broke where the compiler names one. An access-control failure gets `500` and the text below under [Access control](#access-control), and any other server fault `500` and "The download failed because of a problem on the server, not in the request." The detail is logged on the server only, under `download.invalid_request` or `download.failed`, or `download.stream_failed` for a failure after output has started. Response headers wait for the first formatted row, so a failure before any output answers with its status, and a failure partway through aborts the response. With no name given, a file is named `file.<fileType>`.

- **`execute_query`'s `sqon` argument is now enforced as required**: omitting it fails schema validation instead of reaching the handler, since Zod 4 treats an `unknown()` key as required. The tool already documented it as required, so this closes a gap rather than changing intent. The error still names the fix and the empty-root-SQON form, behind the validator's own opening text.

- **The MCP server serves protocol revision `2026-07-28` only, and refuses 2025-era clients**: it now runs on v2 of the MCP TypeScript SDK. Every SDK client negotiates the 2025 era by default, so a consumer must opt into modern negotiation explicitly or the endpoint refuses the connection with an unsupported-protocol-version error. The MCP Inspector needs `"protocolEra": "modern"` in its server entry. Serving both eras was not an option: the 2025 path cannot carry `execute_query`'s confirmation step.
- **`MCP_ALLOWED_HOSTS` is required whenever `MCP_HOST` is not loopback, and the default `MCP_HOST` is not**: the server exits at startup rather than bind a routable interface without DNS rebinding protection. Unset, `MCP_HOST` is `0.0.0.0`, so a server started with default settings, the image included, exits until `MCP_ALLOWED_HOSTS` and `MCP_REQUEST_STATE_SECRET` are both set. Set `MCP_ALLOWED_HOSTS` to the hostnames clients use, or to `*` if an upstream gateway validates `Host`. A request whose `Host` is not on the list is refused with `403`. A loopback bind with it unset accepts the localhost hostnames, which is the only set the published `0.1.0-rc.5` accepted on any bind.
- **`MCP_HOST` sets the address the server binds**: in a container, keep it unset or at `0.0.0.0`, since a loopback value accepts no connection from outside the container. The default bind is IPv4 only; set `MCP_HOST=::` where IPv6 is available and clients connect over it, such as a client whose resolver prefers `::1` for `localhost`.
- **The MCP endpoint answers at `MCP_PATH` exactly**: the match is case-sensitive and takes no trailing slash, so `/mcp/` and `/MCP` answer `404` naming the endpoint. Point reverse proxies and client URLs at the path exactly.
- **`execute_query` refuses a client that does not declare the `elicitation` capability**: the generated query must be confirmed before it runs, and a client that cannot present that request is now refused rather than served unconfirmed.

- **MCP tool input schemas no longer advertise `additionalProperties: false`**: Zod 4 omits it where Zod 3 emitted it. Unrecognized properties are still stripped at runtime, so this loosens what `tools/list` advertises, not what the server accepts. Clients doing strict-mode function calling against the advertised schema should re-check.

- **SQON nesting is now capped**: `SqonSchema` rejects anything deeper than `SQON_MAX_DEPTH` (128 in raw JSON nesting, 62 nested combinations) instead of throwing an uncaught `RangeError` out of `safeParse`. Real queries nest 2 to 4 levels, so no realistic query comes close. `SQON_MAX_DEPTH` and `checkSqonDepth()` are exported so callers can apply a stricter limit of their own. Network search validates each query's `filters` against `SqonSchema` too, so a filter past the cap is refused there with an error.

- **The published SQON JSON Schema at `GET /introspection/sqon` changed shape**: it is now generated by Zod 4's `zod.toJSONSchema` rather than `zod-to-json-schema`. It accepts exactly the same SQONs; only how it is written changed. `additionalProperties: true` became the equivalent `{}`, shared value subschemas are inlined instead of referenced through another definition's path, while a group's children now reference the SQON union by name rather than inlining it (so every `$ref` targets a `$defs` entry root), and operators pairing a canonical name with aliases (`in`/`=`, `gt`/`>`, `wildcard`/`filter`) emit as a two-branch `oneOf` instead of one flat `enum`. Strict `$ref` resolvers benefit; anything pattern-matching the exact JSON should re-check.

- **The SQON JSON Schema's `$id` changed**: it is now `https://overture.bio/schemas/sqon/v{version}.schema.json`, on Overture's own domain and without the `arranger` path segment, since SQON is an Overture-wide schema rather than an Arranger one. The published `@overture-stack/sqon` 1.0.0-rc.5 carries `https://overture-stack.org/schemas/arranger/sqon/v{version}.schema.json`. Every `$ref` in the schema targets an internal `$defs` entry, so validation is unaffected; anything keying on the schema's `$id`, such as a cache or a registry lookup, will see it change.

- **`@overture-stack/sqon` now uses Zod 4, which it installs itself**: `zod` `^4.2.0` is a regular dependency, and `@overture-stack/arranger-types` reaches Zod only through it. A tree that already holds Zod 3, for example through the deprecated `sqon-builder` packages, gets a separate Zod 4 copy for `@overture-stack/sqon`, and a tree already on Zod 4.2 or later shares one copy. What changes for consumers coming from rc.5:
  - Composing the exported schemas into your own Zod schemas needs Zod 4 in your own dependencies, since schemas from two Zod majors do not combine.
  - Validation errors are Zod 4's: read `.issues`, since `.errors` no longer exists.
  - `Infinity` and `-Infinity` are rejected as values.
  - Zod 4 compiles schemas at runtime, which a Content Security Policy without `unsafe-eval` blocks. Call Zod's `config({ jitless: true })` before any SQON is parsed.
  - A browser bundle holding both Zod majors stays larger until the host stops depending on `sqon-builder`.

- **Compiling against SQON types needs TypeScript 5**: `@overture-stack/sqon`'s declarations reference Zod 4's, which TypeScript 4 cannot parse, `skipLibCheck` included. That reaches every TypeScript consumer whose types import a SQON type, directly or through `@overture-stack/arranger-types`, the router or `@overture-stack/arranger-components`. Use TypeScript 5.4 or later, or 5.0 or later with `skipLibCheck`.

- **A fresh install of an earlier 3.1 prerelease picks up this release's `@overture-stack/sqon` and `@overture-stack/arranger-types`**: the published `@overture-stack/arranger-graphql-router` 1.0.0-rc.6 and `@overture-stack/arranger-components` 3.1.0-rc.3 depend on both at `^1.0.0-rc.5`, which admits later prereleases. An install with no lockfile, or with one regenerated, therefore brings in the SQON and Zod changes recorded here without the router or components being upgraded. Commit the lockfile, or pin exact versions, to take them with the upgrade instead.

- **The `/mock/graphql` endpoint and the `mock` option on `/download` are removed**: vestigial, and not doing what their names said. `addMocksToSchema` returns a new schema rather than mutating its argument, and its return value was discarded, so the "mock" schema was the ordinary resolver-backed schema with the mocks thrown away. It was built and mounted unconditionally, given no middleware and no request context, and referenced by nothing in this repository: no test, no documentation, no component. What it produced was a second live GraphQL endpoint running production resolvers with access control absent rather than mocked, returning nothing today only because a resolver throws on the missing search client. `/download` selected the same schema through a client-supplied `mock` flag that no documentation described. Nothing replaces either; a deployment that never called them sees no change. The programmatic surface went with them: `createSchemasFromConfigs()` no longer returns a `mockSchema`, the request context carries none, and `getAllData` and `dataStream` ignore a `mock` argument.

- **`MAX_RESULTS_WINDOW` is now enforced**: Previously present in the env schema but not applied; now caps query results at `10000` by default. Deployments that return more than 10,000 documents must set this explicitly (via env var or per-catalogue `table.json`).

See [docs/reference/08-Migration/v3.1.md](docs/reference/08-Migration/v3.1.md) for upgrade instructions.

### Architecture

- **Server abstracted into its own application** (`apps/search-server`): The Arranger search server is now a separate app rather than part of the main module, making the core routing logic in `modules/graphql-router` easier to compose in custom deployments.
- **New `modules/sqon` package** (`@overture-stack/sqon`): Centralizes SQON schema definitions, operator metadata, and validation. Shared by server and client code.

### Types (`@overture-stack/arranger-types`)

- **A field's `isArray` is now `boolean | null`**: `null` means nothing declared the field's cardinality, which is distinct from `false`, meaning a configuration declared it single-valued. Consumers that treated the value as a plain boolean will read `null` as falsy and so as "single-valued", which is the one conflation the third state exists to prevent; check for `null` explicitly.
- **`table.columns`, `facets.aggs`, `sets.index`/`type`, and `charts.query` are now optional**: none of these are validated by `arrangerRouter`'s own config validation, and all are given complete defaults when omitted, so requiring them from callers didn't match how they're actually used (matching how `downloads`'s fields were already optional). Non-breaking: any config that already provided these continues to work unchanged.

### Server

- **Seven environment variables are renamed, and their 3.0 names keep working as deprecated aliases**: `ALLOW_CUSTOM_MAX_DOWNLOAD_ROWS` is now `ALLOW_CUSTOM_DOWNLOAD_MAX_ROWS`, `CONFIG_PATH` is `CONFIGS_PATH`, `DEBUG` is `ENABLE_DEBUG`, `ES_ARRANGER_SET_INDEX` and `ES_ARRANGER_SET_TYPE` are `ES_ARRANGER_SETS_INDEX` and `ES_ARRANGER_SETS_TYPE`, `PORT` is `SERVER_PORT`, and `SEARCH_CLIENT_TYPE` is `SEARCH_ENGINE`, which accepts `opensearch` or `elasticsearch` and detects the engine when unset. A 3.0 name still sets its 3.1 variable, and the server prints one `DeprecationWarning` at startup, code `ARRANGER_ENV_RENAMED`, naming the new name and linking the [migration guide](docs/reference/08-Migration/v3.1.md#environment-variable-renames). A 3.0 value means what 3.0 read it as, so a flag is on only for `true` and a number of `0` takes the default. Where both names are set, the 3.1 name wins, and the warning says the 3.0 one was ignored unless both hold the same value. `DEBUG` counts only when it holds `true`, since other tools read it for settings of their own. Update `.env` files, container configs and Helm values.
- **A configuration directory laid out for 3.0 is still found, as a deprecated fallback**: where `CONFIGS_PATH`, or its default `./configs`, is a relative path naming no directory from where the server starts but naming one from `modules/server` beneath it, where 3.0 resolved it, the server reads that one and prints one `DeprecationWarning`, code `ARRANGER_CONFIGS_LOCATION`, naming both paths and linking the [migration guide](docs/reference/08-Migration/v3.1.md#configs-directory). An absolute path never falls back.
- **Multicatalogue support**: A single Arranger server can now serve multiple catalogues simultaneously. Organize configs in subdirectories under `CONFIGS_PATH` (one subdirectory per catalogue). Existing flat layouts continue to work as single-catalogue deployments: no migration required.
- **Catalogue-scoped paths accept a `documentType`, not just a `catalogueId`**: `/{catalogueId}/graphql` and `GET /introspection/:catalogueId` now also resolve a `documentType`, provided it names exactly one catalogue on the server. A real `catalogueId` is always checked first and always wins, so this can't be shadowed by a same-named `documentType`. A `documentType` shared by more than one catalogue returns `409` (`ambiguous_document_type`) listing every matching `catalogueId`, rather than silently picking one. See [docs/reference/05-introspection.md](docs/reference/05-introspection.md#catalogueid-also-accepts-a-documenttype).
- **Partial catalogue availability**: A catalogue whose search index is missing or unreachable no longer crashes the whole server. It's reported as `failed` (with an `error` object: a machine-readable `code` and a human-readable `message`) in `GET /introspection` and its own `GET /introspection/:catalogueId`, alongside a server-wide `status` (`healthy`/`degraded`/`unhealthy`). Its GraphQL endpoint returns `404` instead of taking the process down. New `GET /ready` readiness endpoint reflects this aggregate for orchestration probes. `GET /ping` (liveness) is unaffected and stays blind to catalogue state on purpose, so a search-engine outage doesn't trigger a restart loop. New `READY_PATH` env var (default `/ready`), mirrors `PING_PATH`. A failing catalogue's full stack trace and cause chain is only printed to the console when `enableDebug` is set: by default, only the curated `code`/`message` summary is logged, keeping routine startup output readable when several catalogues load concurrently. New `permission_denied` error code, for a search engine user lacking the permissions needed to read its index or mapping. A catalogue whose GraphQL schema or endpoint fails to build is now correctly reported as `failed` with the new `schema_build_error` code, instead of being silently mounted as `available` while every request under it returned a generic `500`.
- **New `nestingPrefix` catalogue config**: for a catalogue whose real index documents wrap all their content under one top-level envelope property (for example a Lyric-sourced catalogue, which nests everything under `data`), setting `nestingPrefix` (a dotted path, e.g. `"data"` or `"envelope.payload"` for deeper envelopes) unwraps the mapping at that path during schema generation, so `extended.json`/`facets.json`/`table.json` can keep referencing clean, unprefixed field names (mapping ingestion), and every filter, aggregation, sort, and response read re-applies the prefix against the real ES paths transparently (per-request query/response translation), so a catalogue with `nestingPrefix` set behaves identically, end to end, to one whose documents were never wrapped in the first place. A configured value that doesn't match the real mapping fails the catalogue at startup (new `nesting_prefix_not_found` error code, reported via `GET /introspection` like any other catalogue failure) rather than silently falling back and reproducing the exact "everything is null" symptom this feature exists to fix. See [docs/reference/01-arranger-configs.md](docs/reference/01-arranger-configs.md#nestingprefix-optional) for full detail, including a documented bandwidth tradeoff and a field-level-access-control caveat for future work.
- **Field names with characters GraphQL can't use as identifiers now work** (e.g. a hyphen or leading digit, common in some biomarker/clinical naming conventions): previously any such field crashed schema generation outright. These are now sanitized into valid GraphQL identifiers automatically; `extended.json`/`table.json`/`facets.json` continue to reference fields by their natural raw path, no config changes required. `facets.json` specifically can now reference nested fields by their raw dotted path too (e.g. `"donor.age"`); the previous `__`-escaped form (`"donor__age"`) still works but is deprecated, see [migration guide](docs/reference/08-Migration/v3.1.md). The one case sanitization can't resolve automatically, two distinct raw field names colliding on the same sanitized identifier, still fails with `schema_build_error`, naming the specific colliding fields.
- **Introspection API**: New REST endpoints for tooling and LLM integration:
    - `GET /introspection`: Lists all registered catalogues with their document types, GraphQL paths, introspection paths, and availability `status`.
    - `GET /introspection/:catalogueId`: Returns all fields for a catalogue, their ES types, and valid SQON operators grouped by field type.
    - `GET /introspection/sqon`: Returns the SQON JSON Schema.
    - See [docs/reference/05-introspection.md](docs/reference/05-introspection.md) for full API reference.
- **Introspection now reports `isArray` for every field**: whether one document can hold more than one value for that field, which no part of the response previously carried. A consumer cannot infer this from `type`, because Elasticsearch never enforces cardinality against its mapping: any field can hold an array unless a configuration says otherwise. Three states are distinguishable. `true` means a configuration declared it multi-valued, `false` means one declared it single-valued, and `null` means nothing declared it either way. `null` rather than an omitted key, so a consumer pinned to a published version can tell "nothing declared this field" apart from "this server predates the field", which two absences could not express. Previously `extendFields` defaulted the value to `false` for every field whether configured or not, collapsing the last two states into one before the value ever left the server. Which state is the cautious one depends on the operator: an `all` clause needs `true` to be satisfiable at all, whereas combining two `in` clauses on one field is only safe when it is `false`. See [docs/reference/05-introspection.md](docs/reference/05-introspection.md#get-introspectioncatalogueid).
- **Network search federation**: A catalogue can federate queries across multiple remote Arranger nodes via `network.json` config. Supports passthrough headers for forwarding auth tokens to remote nodes.
- **GraphQL query complexity limits**: Configurable alias count and query depth limits protect against abusive queries. Set via `GRAPHQL_MAX_ALIASES` and `GRAPHQL_MAX_DEPTH` env vars or per-catalogue config. The defaults are 15 aliases and a depth of 7.
- **CORS configuration**: `ALLOWED_CORS_ORIGINS` env var controls which origins are permitted. Omit to allow all.
- **Catalogue descriptions**: Add an optional `"description"` field to `base.json` to surface a human-readable label in introspection responses.
- **`ROW_ID_FIELD_NAME` configurable**: The ES field used as the row identifier (default `id`). Previously hardcoded.
- **`DOWNLOAD_STREAM_BUFFER_SIZE` default corrected**: Fixed incorrect default of `100`; now `2000` as documented.
- **Fixed: `downloads.maxRows`/`downloads.allowCustomMaxRows` were never enforced**: `getAllData` referenced config property names that didn't exist, so every download ran completely uncapped regardless of configuration. Downloads are now correctly capped at the configured `maxRows` (default `100`), or a caller-supplied value when `allowCustomMaxRows` is set.
- **Fixed: a `not` nested directly inside another `not` lost a level of negation**: query building flattens a combination into a same-operator parent, which is sound for `and` and `or` because both are associative, and unsound for `not`, which is not. `not[not[X]]` therefore compiled to the same query as `not[X]`, so a doubly negated filter matched the complement of the document set it named. Confirmed against a live cluster rather than by inspection. `and[not[X]]` nested correctly, so the defect was specific to `not` appearing directly inside `not`. Access-control filters compose as siblings under `and` rather than as nested negations, so no access-control path could reach it. Flattening now excludes `not` for every operator, and the regression is covered by tests that fail without the fix.
- **An empty combination inside a client filter means every document, wherever it sits**: query building flattens a combination into a same-operator parent only where that keeps its meaning, so an empty combination is removed only directly under `and`, and `or[ X, or[] ]` matches every document. An empty combination directly under `and` still changes nothing, and a root `and[]` still means no filter. A saved or bookmarked query that already carries `or[ X, or[] ]` now matches everything its reader may see, where the empty group was ignored before; the server-side filter still bounds it. Facets read an empty combination the same way, nested ones included: with `aggregations_filter_themselves` false, an aggregation dropped one that arrived empty, so its counts disagreed with hits wherever one sat under `or` or `not`. A facet on a nested field still applies the conditions on its own level as a filter of its own, which can differ from hits (tracked in `.dev/tech-debt.md`). Among Arranger's own interfaces, only the AdvancedSqonBuilder produced the changed shape, by emptying a group or a query a union refers to, and it now removes both (see Components). Around the changed shape, a `not` now matches nothing.
- **The query compiler names the SQON rule a filter breaks**: a `pivot` naming no nested field is refused with "A filter's pivot must name a nested field of this catalogue; it requires the filter's conditions to hold for the same nested object.", which reaches GraphQL clients and, through `400`, export clients.
- **Fixed: exports compile filters on nested fields as nested queries**: `getAllData`, which backs `/download`, now takes its list of nested fields from the index mapping, as `resolveHits`, `resolveAggregations` and `resolveSets` already do, instead of from the catalogue's `extended` configuration. Whether the compiler wraps a clause in a `nested` query is decided entirely by that list. The two sources agree wherever the mapping extends cleanly, because `extendFields` takes each field's `type` from the mapping and never from the configuration file. `getAllData` refuses to build a query when the mapping-derived list is absent, since `buildQuery` defaults the argument to an empty list. Exports that filter on a nested field now return the same documents as the same filter does in search, whether or not access control is configured, so their row counts can change for some catalogues and integrations.
- **A facet on a nested field honours a filter on a field nested deeper inside it**: under `in(donors.specimens.tissue, ['Solid'])`, a facet on `donors.donor_id` counts the donors holding a Solid specimen, where it came back empty; under the matching `not-in` it counts only the donors holding a specimen outside the list, where the clause was ignored. A clause on the facet's own level or outside its nested objects, and a facet on the deeper level itself, count as before.
- **A `type` declared for a field in `extended.json` is now reported as ignored**: a field's type belongs to the index mapping, which the search engine uses to decide storage, and `extendFields` has always taken it from there and never from the configuration file. A declaration in the file had no effect and nothing said so. Startup now warns once per catalogue, naming every field whose entry declares one. No behaviour changes: the declaration was already being ignored.
- **A catalogue with no `extended.json` reports nothing, and a real failure to extend the mapping reports at error level**: through `arrangerRouter`, and so in the search server, a catalogue with no `extended.json` is given an empty list and was already silent. An integration calling `getGraphQLRoutes` or `createSchemasFromConfigs` directly, with configs carrying no `extended` list at all, reached the same handler as a genuine failure through the same thrown error and printed the same line ("Something happened while extending the ES mappings"), so it could not tell a supported configuration from a fault. Absence is now silent there too. A real extension failure, wherever it happens, now logs at error level naming the catalogue, what degrades (facet, table and field display configuration, and the published GraphQL field types, since `isArray` decides whether a field is served as `[String]` or `String`), and what does not (filtering, which reads nesting from the mapping). Both still fall back rather than stopping the catalogue. Update any log matcher keyed on the old line.
- **New `ENABLE_ACCESS_CONTROL` env var, read strictly**: unset means no access control, and the server logs `access control source: defaulted (unset)`, unless a host application passes its own `filters` option, which then applies and is logged as `access control source: configured by host`. `false` or `0`, trimmed and in any case, states that explicitly: every catalogue's router is given `includeEverything`, and the server logs `access control source: explicit (set to false)`. `true` or `1` requires the Usher adapter and its configuration, which this build does not include, so the server refuses to start rather than run without the access control it was asked for. Any other value, an empty one included, also refuses startup, quoting the value, since a mistyped value falling back to a default could leave access control off unnoticed; that is why this variable does not follow the boolean flag rule. A host application passing its own `filters` option alongside `ENABLE_ACCESS_CONTROL=false` is refused at startup as a contradiction. Each refusal is logged under `access_control.startup_refused`. See [docs/reference/07-feature-flags.md](docs/reference/07-feature-flags.md#access-control).
- **Exports page without a separate count query**: `getAllData`, which backs `/download` and `dataStream`, pages with `search_after` on the export's sort plus an `_id` tiebreaker, takes `total` from the first page, and stops when a page comes back short or the row limit is reached. A failed search, or a page reporting a failed shard, fails the export. Paging honours backpressure, and stops once the reader or the response ends. The chunks keep their `{ hits, total }` shape, and `dataStream`'s TSV and JSON output is unchanged.
- **`GET /ready` also reports `engineReachable`**: a server given a search client through its `esClient` option probes the engine every `PING_MS`, and readiness answers `503` while the engine is unreachable. The search server image is given none, so there `engineReachable` is always `true` and readiness follows catalogue status alone; do not alert on it from the image.
- **Filtering by a saved set selects the set's records on hits, aggregations and exports**: a `set_id:` value is looked up in the catalogue's own sets index, on Elasticsearch and OpenSearch alike. The search engine fetches the set by id, so a deployment whose search-engine role is written by hand needs `indices:data/read/get` on the sets index, which the `read` action group covers.

### Access control

- **The server-side filter is now applied on every read path**: record queries, aggregations, the export route, and federated queries. It was previously composed per call site, which meant a read path could be added without it. `buildAggregations` re-applies the filter after the field-removal step that facets require, the export route composes it through the same `compileFilter` as GraphQL reads, and federated queries forward it to remote nodes in the outgoing query variables.

- **Federation forwards the filter rather than enforcing it.** A remote node applies the SQON it receives; a node that ignores it applies nothing, and the querying node cannot detect that. Treat federated results as trusted only to the extent the remote nodes are.

- **New `includeEverything` export** from `@overture-stack/arranger-graphql-router`: the filter callback that keeps every document. A callback returns `includeEverything(context)` to allow one request without restricting it, and passing `includeEverything` itself to the router states, optionally, that a deployment applies no access control. `getDefaultServerSideFilter` is now a deprecated alias for it, the same function object. Both are typed as filter callbacks taking the request context, so a call with no argument does not typecheck: call it with the context, or pass the function itself.

- **The router records its access-control decision in the state of every request it serves, and exports resolve their filter from it**: `getAllData`, `dataStream` and the router's `/download` apply the filter the router was constructed with, evaluated once per export. A `getServerSideFilter` passed to `getAllData` or `dataStream` is composed with it under `and`, so a caller can only narrow it. A deployment with no access control writes nothing for any of this: the router records `includeEverything` as defaulted, and exports apply it. On a context no router built, `getAllData` and `dataStream` need the filter function passed explicitly, either the one the deployment's router was configured with or `includeEverything` where the deployment applies no access control; passing nothing is refused before any output. The record survives a spread copy of the request's state and cannot be expressed in JSON, so a request body can never supply one. The startup log names each catalogue's decision: `access control: filter configured`, `access control: none (explicit)` when the function given is `includeEverything` itself, or `access control: none (defaulted)` when none was given.

- **Access-control failures reach GraphQL clients as fixed text**: when access control cannot be evaluated for a request, because the callback threw or returned a promise, or its filter was absent or held an empty combination, the client receives "The server could not apply its access control because of a problem in its configuration, not in this request." with no exception detail or stack, debug mode included. The full message and its cause are logged on the server under `access_control.evaluation_failed`. Network search reports the same text in a failing node's `errors`. Every other GraphQL error is formatted as before.

- **`AccessControlError` and `InvalidExportRequestError` are exported**, the first from the package root and the second from `@overture-stack/arranger-graphql-router/download`, so an integration with its own export route can answer the way `/download` does: `InvalidExportRequestError` is a bad request, answered with `400`, while `AccessControlError` is a refusal and any other error a server fault, both answered with `500`. Answer each as plain text: an `InvalidExportRequestError` with its message, which names the rule broken where there is one and never a value the request carried, and an `AccessControlError` or any other error with fixed text, such as the exported `ACCESS_CONTROL_FAILURE_MESSAGE`. Log the error and its cause on the server, an `AccessControlError` both as the export's own failure and under `access_control.evaluation_failed`, as `/download` does: it logs `download.failed` with `reason: 'access_control'`, and the same event GraphQL and network search log. See [the router's README](modules/graphql-router/README.md#export-routes).

- **Per-request state lives in `res.locals`, and the filter callback reads it on every read path**: the GraphQL router keeps its own keys, its catalogue configuration, search client, schema, debug flag and access-control decision, under `res.locals.arranger`, and `getServerSideFilter` receives an application's own `res.locals` keys beneath them on hits, aggregations, saved sets and exports. The GraphQL router's keys, and those `graphqlOptions.context` returns on GraphQL reads, take precedence. `getAllData` and `dataStream` accept `ctx: res.locals`, and the package declares `res.locals.arranger` on Express's `Locals` for TypeScript.

- **`req.context` is deprecated**: it remains a view of `res.locals.arranger`, so an application reading or writing it, setting it before the GraphQL router, or passing `ctx: req.context` to `getAllData` or `dataStream` keeps working, and Node prints one `DeprecationWarning`, code `ARRANGER_REQ_CONTEXT`, naming `res.locals` and linking the [migration guide](docs/reference/08-Migration/v3.1.md#per-request-state-res-locals). `addContext` is deprecated with it. With access control, `ctx: req.context` hands the filter callback the GraphQL router's keys alone, without those recorded at the root of `res.locals`, so the callback treats the export as a request carrying no identity, by its own rule. Pass `res.locals`.

### MCP server

- **New `apps/mcp-server`**: A Model Context Protocol server that exposes Arranger catalogues as LLM-queryable resources and tools. Separate Docker image: `ghcr.io/overture-stack/arranger-mcp-server`. Implements the MCP Streamable HTTP transport.
    - Resources: server introspection, SQON schema, per-catalogue fields.
    - Tools: `list_catalogues`, `get_sqon_schema`, `get_catalogue_fields`, `build_sqon`, `execute_query`.
- **`build_sqon` tool**: builds a validated SQON from plain `fieldName`/`operator`/`value` clauses, so a model selects conditions instead of writing query JSON. Every clause is checked against the catalogue's own field types and valid operators before anything is built, and one error is reported per invalid clause rather than stopping at the first, so a whole batch can be corrected in one resubmission. Returns the SQON alongside a plain-English `summary` built from the catalogue's display names (for reading back to the user before the query runs), and reports when equivalent clauses merged, either during the build or because a supplied `existingSqon` was already redundant on arrival, so a lower filter count than was submitted is explained rather than silent. Optionally extends the SQON from an earlier call via `existingSqon`, for narrowing a query that already ran. Covers every operator `modules/sqon` implements: the single-field operators (`in`, `not-in`, `some-not-in`, `all`, `gt`, `gte`, `lt`, `lte`, `between`) via `fieldName`, and `wildcard` text search across several fields at once via `fieldNames`. One `and`/`or` applies per call; mixed AND/OR nesting still requires a hand-written `sqon` passed to `execute_query`, as does the planned `fuzzy` operator. An asterisk inside an `in`-like value is rejected and redirected to `wildcard`, since Arranger would otherwise run it as a regular expression rather than matching it literally. The server instructions, `execute_query`'s description, and the `query_arranger` prompt now all route SQON construction through this tool. See [docs/mcp-server.md](docs/mcp-server.md) for the full tool surface.
- **`build_sqon`'s same-field `in` merge is now conditional on the field's declared cardinality (`isArray`), and `all` is gated the same way in the other direction**: an ambiguous same-field collision is refused rather than silently resolved, reported as an error naming both readings; a successful merge still reports itself via `notes` so a lower filter count than submitted is explained rather than silent. A field whose cardinality nothing declares counts as ambiguous, so two `in` clauses on it under `and` are refused: where either value should match, send one `in` clause carrying every value, and where the field is single-valued, declare it `isArray: false` in `extended.json` to restore the merge. See [docs/mcp-server.md](docs/mcp-server.md) for the full behaviour.

- **`execute_query` addresses fields whose raw names GraphQL can't use as identifiers**, matching the server-side support noted under [Server](#server) above. `fields`, `sort`, and `aggregationFields` take names exactly as `get_catalogue_fields` reports them, including hyphens and leading digits. Results are keyed by the names the generated GraphQL schema uses, which are not always the same string: `donor-info.age-at-diagnosis` comes back as `donor_info { age_at_diagnosis }` under `hits` and as `donor_info__age_at_diagnosis` under `aggregations`. Field names inside a `sqon` are never rewritten in either direction, since a SQON travels as a query variable rather than as part of the query document. See [docs/mcp-server.md](docs/mcp-server.md).

- **Express is no longer a dependency**: the MCP handler is served on plain `node:http`, removing Express and its transitive packages from the image and its audit surface. The request body size cap is unchanged in behaviour. Host validation now follows `MCP_ALLOWED_HOSTS`, and browser `Origin` is now validated too, against `MCP_ALLOWED_ORIGINS`.
- **Confirming a query is now two requests rather than one**: revision `2026-07-28` removes the server-to-client request channel, so `execute_query` returns an `input_required` result and the client re-invokes the tool with the answer attached. Hosts using an SDK client need no change; a hand-rolled client must echo `requestState` verbatim on the retry.
- **The confirmed query is bound to the query that runs**: the approval carries a signed digest of the built GraphQL document, its variables and its endpoint, so a call that rebuilds a different query under the same approval is refused. New `MCP_REQUEST_STATE_SECRET`, required whenever `MCP_HOST` is not loopback and enforced at startup like `MCP_ALLOWED_HOSTS`: without it each process signs with a key it generated for itself, so a second replica cannot verify a confirmation the first one issued. Generate one with the new `npm run mcp-server:generate-secret`. A loopback bind still needs no configuration. An approval stays valid for ten minutes. See [apps/mcp-server/README.md](apps/mcp-server/README.md#environment-variables).
- **New `MCP_ALLOWED_ORIGINS` and `MCP_MAX_BODY_BYTES`**: the hostnames of browser origins allowed to call the server, given as `app.example.org` rather than `https://app.example.org`, and the largest request body accepted (default `102_400`, preserving the limit Express applied before the transport moved to plain `node:http`). A request carrying no `Origin`, as every non-browser client sends, always passes the Origin check. On a routable bind with `MCP_ALLOWED_ORIGINS` unset, every browser origin is refused with `403`; a loopback bind with it unset accepts the localhost origins.
- **Cacheable results now publish freshness hints**: `tools/list`, `prompts/list`, `resources/list`, `resources/templates/list`, `resources/read` and `server/discover` carry `ttlMs` and `cacheScope`, so a client caches them instead of re-fetching. Results that track Arranger's catalogue configuration are scoped `private` and expire in a minute; the rest are `public` for an hour. `serverInfo.version`, which this revision stamps on every result, now comes from the package manifest.

### SQON operators

- **A `not-in` or `some-not-in` holding a special value excludes every value it lists**: a value list that mixes ordinary values with `__missing__`, a `*` pattern or a `set_id:` reference is split into one clause per kind of value, and for `not-in` and `some-not-in` those clauses are joined so that a document matches only when it avoids all of them; an `in` still matches a document that matches any of them. A `some-not-in` given a `set_id:` reference excludes the set's ids, as `not-in` does. On a nested field, each part of such a `not-in` can still be met by a different nested item (tracked in `.dev/tech-debt.md`).

- **A pivot holds a group's conditions on its path to one nested item, in whatever order the children come**: a pivoted `and` needs one nested item meeting all its conditions on the pivot path, and a pivoted `not` excludes the records where one item meets them all, while each of its other children is negated on its own. `some-not-in` with `__missing__` on a nested field keeps the records where no nested item lacks the field.

- **A range given several bounds applies every one of them, so the strictest decides**: `gt`, `gte`, `lt` and `lte` match only what each bound in their list admits, the largest bound deciding for `gt` and `gte` and the smallest for `lt` and `lte`.

- **`wildcard` is now the canonical op for text-pattern search**: The operator that performs case-insensitive substring matching across multiple fields was previously named `filter`. That name was misleading in two ways: it collides with the generic meaning of "filter" (every SQON op is a filter), and it falsely implies fuzzy/approximate matching, which is a distinct ES/OS feature (Levenshtein edit-distance) that does not exist yet. The operation is implemented with an ES/OS `wildcard` query, so `wildcard` is the name it carries going forward.

    `filter` is accepted as an alias and normalizes to `wildcard` at query-build time; existing serialized SQONs continue to work without any migration. New SQONs should use `op: "wildcard"`.

- **`VersionedSqonJsonSchema`, `SqonJsonSchema`, and `JsonSchemaObject` now exported from the package root**: previously only reachable through an internal path. Needed by any consumer that wants to reference the real shape of `getVersionedSqonJsonSchema()`'s return value instead of a hand-duplicated, looser type.

- **All operator aliases now normalize on parse, not just `filter`/`wildcard`**: `SqonBuilder.from()` rewrites every leaf's `op` to its canonical form (`=` -> `in`, `>=` -> `gte`, `filter` -> `wildcard`, etc.) before returning, recursively through nested combinations. Previously the schema validated aliases but never normalized them, so code that switched on `.op` after parsing (rather than going through the builder's own methods) could accept a query using an alias and then fail to match any canonical branch. Calling `SqonSchema.parse()` directly still returns the alias unchanged; use the newly-exported `normalizeSqonNode()` if you have a reason to validate without the builder. Also newly exported: `isGroupNode`/`isFieldFilter` type guards for discriminating a `SqonNode` by shape.

- **New `asCombination()` export, for consumers that need a stable, always-a-combination shape**: `SqonBuilder` always collapses a single-item `and`/`or` down to its sole child (`SqonBuilder.and([oneFilter]).toValue()` returns `oneFilter`, not `{ op: 'and', content: [oneFilter] }`), the same behaviour `sqon-builder` had. That's the right default for the common case, but it surprised a consumer whose SQON-rendering code assumed the top level was always a combination with `content` as an array, and crashed the moment a lone filter collapsed to a bare leaf. `asCombination(node, op = 'and')` wraps a node in a combination if it isn't already one, and never unwraps a single-item result the way builder methods do, use it instead of a hand-written `{ op: 'and', content: [node] }` literal wherever that stability matters more than the minimal form.

- **New `SqonBuilder.matchNothing(fieldName)` export, for a filter guaranteed to match nothing**: a builder holding an `in` filter with an empty value list, which `.toValue()` returns. It's a leaf, not a combination, so it stays stable under the builder's reduction, which never drops a leaf, and under later composition. `fieldName` has no effect on the result, an empty `in` matches nothing regardless of which field it names; a field name is still required since every leaf operator needs one. Use this to express "match nothing" (for example, a denied principal in an access-control filter) rather than constructing it by hand.

- **Fixed: `matchNothing()` (or any empty-value `in` filter) could be erased by a same-field filter under `and`**: same-field `in` filters were always merged by unioning their value lists, so `AND(matchNothing('study'), in('study', ['x']))` reduced to `in('study', ['x'])`, silently turning a deny into an allow. An empty `in` now wins outright when merged under `and` instead of being unioned away; `or` is unchanged, where union was already the correct result.

- **Fixed: `reduceSqon` was not idempotent for a same-field filter nested inside a combination**: two defects, found in sequence. First, a child combination was folded into its parent before being fully reduced itself, so a same-field filter it only produced through its own internal merging never got offered to the parent's merge check. Second, a merged value array was never deduplicated unless the merge result happened to also get promoted to a bare leaf; a merge that stayed part of a combination (for example, kept alive by a sibling clause on another field) could carry a duplicate value indefinitely. Every child is now fully reduced before being folded into its parent, and every merge result is deduplicated at the point it's produced, so a second `reduceSqon` pass never finds more to do than the first.

- **Fixed: merging two same-field filters under `not` could invert the query's meaning**: `not`'s children are each individually negated (`not[A, B]` means `¬A ∧ ¬B`), so combining two same-field clauses correctly under `not` requires flipping the operator itself; none of `reduceSqon`'s merge rules did that; they merged as if `not` behaved like `and`. Concretely, `not[not-in a:['2','3'], not-in a:['1']]` (matches nothing: the two clauses require `a` to be both in `{2,3}` and equal to `1`, which cannot hold) reduced to `not[not-in a:['1','2','3']]`, which matches `a` being `1`, `2`, or `3`. Found by differential testing against real query results, not by inspection. `reduceSqon` no longer merges same-field filters under `not` at all, for any operator; two clauses on the same field under `not` are now always kept separate, which costs a missed normalization but never an incorrect one.

- **Fixed: merging two same-field `in` filters under `and` widened the match set instead of narrowing it**: `AND(in a:['1','2'], in a:['1'])` requires a document to satisfy both clauses, their _intersection_, but was merged by unioning the value lists to `in a:['1','2']`, matching more documents than either clause alone. `reduceSqon` does not compute intersections, so `in` clauses under `and` are no longer merged at all; two separate `in` clauses under `and` already compile to two `terms` clauses under Elasticsearch's `bool.must`, which correctly evaluates as their intersection without any pre-computation needed. `or` is unaffected, union is the correct merge there. Confirmed this doesn't affect `arranger-components`' facet selection UI, which has its own independent same-field merge logic and never calls `reduceSqon` for it.

- **Fixed: same-field filter matching ignored `pivot` in three places**: a `pivot` scopes a nested-field condition to one matched sub-document, so treating two differently-scoped leaves (or one pivoted and one not) as the same filter silently reassigns a condition to the wrong nested scope, or drops its scoping entirely.
    - `reduceSqon`'s merge check now also compares `pivot`; two same-field leaves with different pivots are left as separate clauses instead of merged.
    - The exported `checkMatchingFilter`, used by `removeExactFilter`, now also compares `pivot`.
    - `SqonBuilderHandle.setFilter` always constructs an unpivoted leaf (it has no `pivot` parameter), but its "replace an existing same-field filter" check didn't require the existing filter to also be unpivoted, so it could silently replace a pivoted filter, discarding its nested scope. It now only replaces an existing unpivoted match, adding the new filter as a separate clause otherwise. `removeFilter` is unaffected by design: it's a bulk, field-scoped removal regardless of pivot, documented as such; use `removeExactFilter` to target one pivot specifically.

- **Fixed: `isFieldFilter` threw on a node with no `content` object** instead of returning `false`. Guarded against `content` being `undefined`, `null`, or non-object.

- **Fixed: `setFilter` silently inverted the requested condition when the current SQON's top level was a `not` combination**: a `not`'s children are each independently negated (`not[A, B]` means `¬A ∧ ¬B`), so replacing or adding a child there asserts the opposite of what was requested; `setFilter('a', 'in', ['z'])` against `not[in a:['x'], in b:['y']]` (`a≠x ∧ b≠y`) produced `not[in a:['z'], in b:['y']]` (`a≠z ∧ b≠y`), the caller having asked to assert `a is in ['z']` and silently gotten `a is not in ['z']` instead. This affected both the replace path and the append path (no existing match on the target field also landed inside the `not`, negated the same way). No silently-correct rewrite exists for every operator: only `in`/`not-in` and `gt`/`lte`/`gte`/`lt` have a clean single-leaf inverse, and treating the `not` as opaque and composing alongside it under `and` can produce an always-false query when the new value collides with one the `not` already excludes. `setFilter` now throws when the current SQON's top level is a `not`, rather than silently producing an incorrect result; reconstruct the SQON without a top-level `not` first. `removeFilter` needed no equivalent fix: dropping a child (or a value) from `not`'s content only ever widens the match, which is already correct.

- **`getSqonFieldOperatorDetails()` entries now include a `description`**: previously only `fieldRef`/`applicableTo`/`valueType`, which left operators with the same value shape indistinguishable, most notably `in` ("matches any of these values") and `all` ("contains all of these values"). Every field operator now carries a one-clause statement of what it means, matching the operator-selection table in `docs/reference/03-building-sqon-queries.md`. Additive: existing consumers of the function are unaffected, and get the new field automatically.

- **Fixed: a `between` filter with equal bounds silently lost one of them**: `reduceSqon`'s value deduplication ran unconditionally on every array-valued leaf, including `between`'s `[min, max]` pair, which is a fixed-position tuple, not a set of interchangeable options. `SqonBuilder.between('age', [30, 30])` deduplicated to `value: [30]`, one element short of what the schema itself requires (`length(2)`), so the result failed re-validation on the next `SqonBuilder.from()` or `SqonSchema.parse()` call, and would have failed to compile correctly wherever `between`'s bounds happened to coincide. Found by extending the property-based test to cover `between` (previously excluded, along with `all`, `some-not-in`, and `pivot`, now all covered). Deduplication now excludes `between` explicitly.

- **Fixed: `not-in` and `some-not-in`'s published descriptions each named the other's quantifier**: `getSqonFieldOperatorDetails()` described `not-in` as "Field does not match any of these values" and `some-not-in` as "At least one nested item is excluded (multi-valued, per-item)". On a nested field the two operators compile to opposite `must_not` placement (inside versus outside the `nested` wrapper): `not-in` is existential (at least one item outside the list is enough to pass), `some-not-in` is universal (every item must be outside the list). Each description read as the other operator's quantifier; on a flat field the two are identical, so the mismatch only surfaces on a nested field, where picking the operator by its description returns the wrong document set for any caller, and discloses withheld records for the minority of deployments that build an access-control predicate on one. Both texts already shipped in the published `1.0.0-rc.5` under the `rc` dist-tag; the `latest` dist-tag (`1.0.0-rc.1`) predates the description feature entirely and carried neither, so a consumer pinned to `rc` has already taken the wrong text, not merely been at risk of it. Corrected to "Field does not match any of these values. On a nested field, at least one nested item's value is outside the list." (`not-in`) and "Field does not match any of these values. On a nested field, no nested item's value is in the list." (`some-not-in`), each accurate for both the flat case and its own nested quantifier without depending on prose the description string doesn't carry, since it is served through `GET /introspection/sqon` to MCP clients with no surrounding context. The qualifying clause keys on nesting rather than on the field holding an array: `buildQuery` never receives a field's cardinality at all, and Elasticsearch's `terms` query already matches a flat field on "any value present" whether that field is single- or multi-valued, so `must_not(terms(...))` is universal there regardless of arrayness; only a `nested` wrapper introduces the existential quantification that flips `not-in`'s behaviour. The operator-selection table in `docs/reference/03-building-sqon-queries.md` and the operator table in `.dev/docs/build-sqon-tool.md` are corrected to match.

- **Fixed: same-field range bounds given as strings keep their value and type through reduction**: `reduceSqon` merges two same-field `gt`/`gte`/`lt`/`lte` bounds only when both are numbers, both are `YYYY-MM-DD` dates, whose text order is their date order, or the two are identical. Any other pair, such as quoted numbers, date math, other date formats or datetimes, is kept as two clauses, since how a string bound sorts depends on the field's mapping, which the reducer cannot see; applying both clauses gives the same result. A string bound stays a string. Only filters composed or parsed through `SqonBuilder` are affected. Arranger's own query building, network search included, compiles the filter it received rather than a reduced one.

- **An empty group keeps its meaning through `SqonBuilder`**: an empty group (`and[]`, `or[]`, `not[]`) means every document, whatever its pivot. The builder's reduction removes only an empty `and` directly under an `and`, where it changes nothing, and keeps every other empty group where it is, never flattened into a parent with the same operator. `SqonBuilder` treats a value holding no clause, its empty start or a group whose last clause was removed, as no filter yet, so combining it with anything yields just what was added. Filters and builder chains that contain no empty group build as they did.

- **A range bound must be a finite number, a non-empty string or a valid date**: `SqonBuilder`'s `gt`, `gte`, `lt`, `lte` and `between`, and `setFilter` with a range operator, throw a `RangeError` for any other value, such as `NaN`, `Infinity`, `null`, an empty string or a boolean, and `between` takes exactly two bounds. None of those can bound a range: `NaN` and `Infinity` serialize to `null`, which a search engine reads as no bound.

- **The SQON JSON Schema now describes the fields people and agents most often get wrong**: `pivot` on every node, `fieldName` and `value` on every single-field clause, and `fieldNames` on `wildcard`, served through `GET /introspection/sqon`. Each `value` description says what that clause kind takes, including that every bound in a list given to a range operator applies, so the strictest one decides. Descriptions only, so the schema accepts exactly the same SQONs.

### Infrastructure

- **Turborepo**: Build and test pipeline uses Turborepo for change detection: only affected packages and their dependents rebuild on each commit.
- **Published type declarations keep their documentation**: `@overture-stack/arranger-graphql-router`, `@overture-stack/arranger-types` and `@overture-stack/arranger-components` now build with `removeComments: false`, so their TSDoc reaches an editor's hover text, and an editor marks `getDefaultServerSideFilter` deprecated.
- **`npm run release:check`**: New script (`scripts/verify-pack.mjs`) verifies that no publishable package contains `file:` dependency references before release.
- **`@overture-stack/sqon` no longer reads the filesystem at runtime**: Its version constant was previously computed by `readFileSync`-ing the package's own `package.json` at module-init time, a Node-only API with no browser equivalent, breaking any bundler building for a browser target (e.g. Vite) that imports the package, directly or transitively through `arranger-types`/`arranger-components`/`arranger-charts`. The version is now stamped into a generated file at build/test time instead (`scripts/generateVersion.mjs`, wired via `pretest`/`prebuild`); the shipped bundle contains no `node:fs`/`node:path`/`node:url` references. Also added `"sideEffects": false` to the package now that its module graph has no remaining top-level side effects.
